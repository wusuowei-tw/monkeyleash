## 合起來的意思

> **每一次判定,都是「一份不進版控的設定」對「一份不進版控的輸入」做出的,
> 而結果也不進版控。** 三樣缺一就無法複現,而現在**三樣都缺**。

這不是「紀錄不夠詳細」,是**判定在原則上不可事後複驗**。
與 F-091「驗證的判準必須與程式實際的選法一致」是同一個方向的問題,
只是換成時間軸:**當時的判準是什麼,現在已經問不出來了。**

## 補述(2026-08-16):「輸入」那一樣**不是均勻缺失的**

上面說「設定 / 輸入 / 結果三樣都缺」。**「輸入」那一樣要拆開看,而拆開之後
結論會變得可操作。**

| 判定結果 | 它的輸入後來去了哪 |
|---|---|
| **通過** | 那份輸入變成了 commit —— **留得下來,而且進了版控** |
| **被擋(pre-commit)** | 那份輸入**從未落地**,工作樹隨後被改掉 |
| **被擋(前哨)** | **那筆寫入根本沒有發生過** —— 連工作樹都沒進去 |

> **輸入唯一留不下來的情況,正是最想事後複驗的那一種。**

通過的判定事後隨時查得到:`git show <commit>` 就是當時的輸入。
被擋的判定則什麼都沒有 —— 而**「為什麼那次被擋」正是會被爭論、
會被拿來質疑規則、會被當成放寬規則理由的那一種**。

### 這讓將來的機制範圍小很多

要記的不是「所有判定」,是「**被擋的判定**」:

- 通過的那些**已經有紀錄了**(就是 commit 本身),再記一次是重複
- 被擋的那些**一筆都沒有**,而它們是全部的爭議來源
- 量級差很多:本 repo 96 個 commit vs 未知但顯然少得多的攔截次數

**範圍從「每一次判定」縮到「每一次擋下」**,而那正好也是
頭條一(沒有攔截帳本)缺的那一半 —— **兩條頭條指向同一個東西**。

### 與最小可用一步的關係

上面登記四寫的最小步是「**判定時把當時的設定指紋寫進那筆紀錄**」。
配上這一節:那筆紀錄只需要在**被擋時**產生,而它要帶三樣 ——
**設定指紋 + 被拒的輸入 + 擋下的理由**。三樣同處,事後才複驗得動。

# 登記:三條進危險區 / 半死規則

## 登記一:R6 —— **守得最多,驗得最少**(全清冊最重的單一發現)

`test_the_shipped_gate_enumerates_all_of_its_rules` 驗的是
**規則代號有出現在列舉裡**,不是**規則會擋下違規**。
換句話說:**它證明 R6 存在,不證明 R6 會動。**

### 不對稱擺在一起看

| | R6 |
|---|---|
| **守什麼** | R3 的豁免入口 —— 本 repo **14 個受管 `.py` 裡有 9 個靠它豁免(64%)** |
| **有多少正對照** | **0 條**(唯一那條是「被列舉」) |
| 相比之下 R2 | 17 條 |
| 相比之下 R3 | 22 條 |

**它管的檔案比例是全清冊最高的,而驗它的測試是全清冊最少的。**

### 而失效的樣子與正常一模一樣

R6 的判定是 `git cat-file -e <go-live>:<path>` —— 對每一條逐一問「在不在那棵樹裡」。

- 名單是**空的** → 迴圈零次 → **零違規** → 通過
- 名單**讀不到** → 那一支有 fail-closed(回一條違規)—— 這半是對的
- **`go-live` 指向一個不存在的 commit** → 每一條都 `rc != 0` → **全部變違規** → 吵鬧,會被發現
- **`go-live` 指向一棵「什麼都在裡面」的樹** → 每一條都通過 → **靜默放行**

最後那一種就是票 39 分析「第四條路」時算出來的形狀:
新 repo 的 initial commit 樹包含全部檔案,於是**門檻對每個檔案都成立** ——
**規則還在跑、訊息不會出現、報告全綠,而它擋不住任何東西。**

**沒有任何測試會為那一種出聲**,因為唯一那條測試只問「R6 有沒有被列舉」。

> 不進版控、跟機器走。少了它的指紋,「只剩 N 筆」這個結論在別台機器上
> **不可複現,也無從證偽**。檔名是 `leak-patterns.local.txt`(點,不是連字號)——
> **指紋的價值在於能照同一路徑重算,路徑錯即作廢。**

**招式**:內容**不進版控**(照抄 = 假清單),但**指紋進版控**。
理由不是完整性,是**可複現性** —— 少了它,結論無從證偽。

### 搬過來的形狀(方向,不是設計)

九處各自的敏感度不同,**不會是同一種處置**:

| 類 | 例 | 可能的形狀 |
|---|---|---|
| 秘密內容 | `leak-patterns.local.txt`、`g1-protected.txt` | **只記指紋 + 條數**(dc-01 原樣) |
| 非秘密但綁機器 | `pipeline.json`、`shadow.json`、`upstream-roots.txt` | 指紋?或**判定時把值寫進判定紀錄** |
| 帳本類 | `test-runs.jsonl`、`gate-exemptions.jsonl` | 後者**已經進版控**,是現成的對照組 |

**最小可用的一步可能不是「全部進版控」,而是「判定時把當時的設定指紋寫進那筆紀錄」**
—— 那樣事後複驗需要的三樣(設定、輸入、結果)會落在同一個地方。
但那是設計,**不在本票**。

## A. `staged` 清單:同一個操作,兩個呼叫端,兩種輸入來源

pre-commit 情境下 git 會把 cwd 設在 repo 頂層,所以**現在剛好是對的** ——
但它是**環境給的,不是推導出來的**。**R1 / R2 / R3 / R8 在 pre-commit 都跑在這份清單上。**

## B. 六個 git 子行程全部指定了 repo(**這一項是乾淨的**)

# 方法論:**這份清冊自己犯過一次同族的錯**

第 3 欄第一版用「含 `subprocess.run` 的**那一行**有沒有 `cwd=`」判,
回報 **5 處沒帶 cwd**。**全部是假陽性** —— 那些呼叫是多行的,`cwd=ROOT` 在下一行。
改用 **AST**(看呼叫節點,與換行無關)重驗:**繼承 cwd 的 0 處**。

# 附錄一:`shadow-log.jsonl` 不存在的成因(**不是死規則**)

`gate.py:1834` 有 `SHADOW_LOG` 常數指著一個不存在的檔。
兩種可能長得一樣,拆開查:

**寫入點**:`log_shadow()` 只在三處被呼叫(`gate.py:1959 / 1992 / 2352`),
**三處都在 `if shadow_active():` 底下**。

**`shadow_active()` 的三個條件,逐一實測**:

| 條件 | 實測 |
|---|---|
| 1. 安全閥合法 | ✅ `read_shadow_clamp()` → `2026-09-15` |
| 2. **本 repo 宣告了影子** | ❌ **`.dev/shadow.json` 不存在**(`FileNotFoundError`) |
| 3. 今天 ≤ min(兩個到期日) | 到不了(前一條已 False) |

`shadow_active()` = **False**。

**結論:條件 2 未滿足 → 寫入路徑從未執行 → 檔案不存在是預期,不是死規則。**

**但要記一句**:`.dev/shadow.json`(本 repo 開沒開影子)也**不進版控**,
所以「本 repo 從未開過影子」這件事**沒有任何版控紀錄** ——
判斷它只能靠現場探測,而現場探測只反映**這台機器的此刻**。
與 R6 的 `go-live` 是同一個形狀:**決定某條規則行為的東西,住在不進版控的檔案裡**。
