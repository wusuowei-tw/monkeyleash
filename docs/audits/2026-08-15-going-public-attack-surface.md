## 背景(全部是量過的事實,不是估計)

- private repo,**71 commit / 376 blob 版本 / 481 tree 物件**,計畫轉公開
- 掃描器 `leak_scan.py` 的涵蓋 = **通用 pattern 10 條**(進版控)
  **∪ 個人 pattern 16 條**(**不進版控,綁機器**),另加副檔名判定擋憑證檔
- 全歷史掃描實測:**42 筆命中,100% 是掃描器掃到自己**;
  而**已知洩漏項一條都沒掃到**
- 已知項 **K1** = 一個真實資料夾名,存在於歷史 1 個 blob 版本。
  這台機器的 26 條 pattern **全部打不中它**(三種方法各驗一次,結論一致)
- 定性時另外找到兩筆,**都在現樹**:
  - **K2**:同一個檔案裡,`:348` 被修過(F-082),`:291` 的同類**沒被修**,隔 57 行
  - **K3**:路徑寫在引用的 JSON 裡(`C:\\Users\\…`,雙反斜線),
    **比對式對跳脫形式不匹配**,第一輪定性回報「現樹全是佔位符」

## 重點題:缺口二 —— 涵蓋的一半綁在一份看不見的清單上

掃描涵蓋的一半在一份**不進版控、綁機器**的個人 pattern 清單裡。
兩台機器的清單各自成長,而**沒有任何東西在比對它們**。
`leak_scan` 只在清單**整份不存在**時警告 —— **少幾條時完全無聲**。

於是「有跑掃描」與「涵蓋完整」在報告上長得一模一樣,
而 K1 正是這樣活下來的:報告全綠,已知的洩漏就在歷史裡。

**已裁決的緩解**:已知項回歸 —— 拿登記表逐筆去掃,**掃不到就 refuse**
(不是警告)。判準隨階段換邊:未清除時要「掃得到」,已清除時要「掃不到」。

**請攻擊這個設計。** 特別是:

1. 這個緩解**本身**有什麼失效模式?
2. 它只保得住**已登記**的項。「**未登記且未知**」的那一類,還有沒有別的槓桿?
   (「多寫 pattern」不算答案 —— 那正是失效的那條路。)

## 開放問句(本次審計的本行)—— 拆成兩軸

兩軸都要回答,而且**各自說明你的列舉來源**。
「想得到什麼寫什麼」不算列舉;我們要的是**可檢核的來源**。

### 軸一:入口軸 —— 掃描器**根本沒讀到**的資料面

> **還有哪些面向像「身分欄位」一樣,掃描器連入口都沒有?**

**指定的列舉來源(至少涵蓋這三個,可以再加)**:

- **git 物件型別表**(blob / tree / commit / tag 各自帶什麼欄位)
- **refs 命名空間**(`refs/heads`、`refs/tags`、`refs/notes`、`refs/stash`、
  `refs/remotes`、`refs/replace`…)
- **檔案系統中繼資料**(模式位元、時間戳、符號連結目標、擴充屬性…)

**已知的起點(不是答案,請補完)**:

- commit 訊息(已補入掃描)
- author / committer 姓名與 email —— **已確認含真名 + 私人信箱**
- tree 裡的路徑名(已裁決納入)
- tag、notes、其他 refs、reflog
- `.git/config`、submodule 指標、`.gitattributes`
- 檔案模式位元、時間戳、**作者時區**(可推斷地理位置與作息)
- 二進位與掃描器跳過的副檔名(**「跳過」不等於「乾淨」**)

### 軸二:比對軸 —— **讀到了但認不出**的形式

> **同一個秘密換一種寫法,現有的比對式就穿過去了。有哪些寫法?**

**K3 屬於這一軸**:路徑寫成 `C:\\Users\\…`(JSON 跳脫),
字面路徑的 pattern 打不中,而報告是綠的。

**指定的列舉來源**:**編碼與轉換的分類表** —— 跳脫語法、字元編碼、
正規化形式、大小寫映射、分段與重組。至少涵蓋:

- 跳脫形式(JSON / shell / regex / Python raw / YAML / Markdown)
- URL 編碼、Base64、Quoted-Printable、HTML entity
- 大小寫(以及 Unicode 大小寫映射的非對稱情形)
- **Unicode 同形字**(拉丁 / 西里爾 / 希臘的視覺相同字元)、
  正規化形式差異(NFC / NFD)、零寬字元
- **字串分段**(被換行、被字串串接、被註解切開,重組後才是秘密)

**這一軸的判準問句**:對每一種形式,回答
「**現有的字面 pattern 打得中嗎?若打不中,擋它的成本是什麼?**」

## 兩條約束,請一併檢查

### 約束 1:登記表是一張藏寶圖

登記表**不記字串本身**(它列的就是它要保護的東西),
但**仍然把搜尋範圍從 376 個 blob 版本縮到 1 個** ——
對想找東西的人,**縮小範圍就是主要的價值**。

已裁決的緩解:**公開前,登記表各筆對應的內容須已清除或泛化**。

**這個緩解夠嗎?**

### 約束 2:`filter-repo` 只跑一次

每跑一次**所有 sha 全變**(本 repo 大量交叉引用 sha:豁免清單的
`# go-live:`、provenance、票與 ADR 的散文引用),
而且**每跑一次就在遠端與既有 clone 留下一組舊物件** ——
改寫不回收已發布的物件,只讓新的 clone 拿不到。

所以順序被強制成:**先找齊,再動刀。**

**問題**:這個「只跑一次」的約束,會不會反過來製造壓力去
**草率宣告「找齊了」**?

**並且**:若「找齊」在原理上**不可證明**(我們傾向認為它不可證明),
請不要停在指出這一點 —— 改為給出
**「開刀前的最低證據門檻」**:哪些檢查跑過、哪些軸窮舉過、
哪些殘留風險被明確接受,才算**夠格動刀**。
要可檢核,不要「要謹慎」這種話。
