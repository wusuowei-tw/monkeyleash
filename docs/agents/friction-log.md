# Friction Log

流程本身卡住、繞路、或指示不清的地方。**框架自身的問題優先於任務結果。**
一則一事,格式:現象 → 影響 → 處置。已處置的留著不刪,那是為什麼要有這條規則的證據。

## 發號規則(裁決於 2026-08-13)

**本檔在 portable-manifest 裡標 `copy`** —— 整份被複製進每一個裝了框架的 repo。
所以編號不是本地的事:兩本 log 各自從 `F-001` 發號,合併時必然出現
**兩則同號的不同事**。已經發生過一次(台股影音把一則記成 F-046,
而本檔的 F-046 是另一件事,TradingAgents 的 F-046 又是第三件)。

規則:

1. **`F-` 這個命名空間屬於框架**,由 agent-gates 發號。本檔的 F-001..F-071 不動。
2. **每個安裝的 repo 用自己的前綴**,而且**前綴進號碼本身**:
   台股分析師影音 `TSA-001`、台股資訊收集 `TSI-001`。
   不寫成「F-001(影音)」—— 號碼要能單獨貼出來就自我識別,不依賴上下文。
   新 repo 取前綴的原則:三個字母、與既有前綴不撞、寫進該 repo 的 CLAUDE.md。

   **專案份住另一個檔:`docs/agents/friction-local.md`。**
   本檔標 `copy`,更新時會被整份覆蓋 —— per-repo 條目寫在這裡就會被刪掉。
   分檔的邊界正好就是發號規則本來就在畫的那條(框架層 vs 專案層),
   不是為了遷就工具而多切一刀。
   **不選「合併」**:合併是逐次判斷,而覆蓋是每次都跑;
   一個會出錯的合併比一個清楚的分檔糟。
3. **專案發現的框架層事實,回 agent-gates 開 framework-updates 票**;
   落地時才拿到 `F-` 號。專案那一則**不刪、不改號**,只在原地加一行指向新的 `F-` 號。
   歷史不為了整齊而動 —— 那則在當時的編號下被引用過,改號會讓引用斷掉,
   而「看起來整齊」不值得那個代價(與 wrapper commit 的歸屬同一條原則)。

判斷「這是框架層還是專案層」:**把這一則搬到另一個專案去,還成立嗎?**
成立就是框架層(回這裡開票),只在這個專案成立就是專案層(留在該 repo)。

## F-001 同一條 pipeline 的站名在四個檔案有四套寫法

- **發現於**:2026-08-09,`/code-review` Standards 軸(第一次真實跑,框架自身的 diff)
- **現象**:
  | 檔案 | 寫法 |
  |---|---|
  | `CLAUDE.md` | `/grill → /spec → /tickets → /implement → /smell-review → /arch` |
  | `docs/decisions.md` | `grill→spec→tickets→implement→smell-review→deep-modules` |
  | `.claude/hooks/gate.py`(R2 訊息硬編碼) | `/grill-with-docs -> /to-spec -> /to-tickets -> /implement -> /code-review -> /improve-codebase-architecture` |
  | `.dev/pipeline.json._stages` | `idle / grill / spec / tickets / implement / review / arch` |
- **影響**:沒有兩份對最後兩站的命名一致。任何人(或 agent)信任其中一份都會被誤導;
  改一個站名要手工改四處,漏一處就多一份「看似正確、實則描述錯誤」的文件——
  比沒有文件更糟,因為它讀起來像權威。
- **根因**:採用官方 skill 時只改了入口名稱,沒有意識到站名被複製到四個消費端。
  更深一層:**沒有任何一份被指定為定義,四份都是副本。**
- **處置**(已完成):
  - 新增 `.agents/pipeline-stages.yaml` 為**唯一定義**(純規格、唯讀、不被任何流程寫入)
  - 四個消費端全部改為引用:`gate.py` 的 R2 訊息與可寫站判定從 yaml 動態取;
    `CLAUDE.md` 不再複製站名清單、直接指過去;`docs/decisions.md` 引用之;
    `.dev/pipeline.json` 只留 `current_stage` 這個狀態值
  - 判準寫入決策表:**只被讀的是定義,會被寫的是狀態,兩者不同居**
- **殘留風險(已消除,2026-08-09)**:原本 yaml 讀取失敗時退回「只有 implement 可寫」的預設
  —— 那是 **fail-open**:定義檔被刪或改壞時,`current_stage=implement` 照樣放行,
  閘門壞掉反而變更鬆。已改為 **fail-closed**:定義不可用(檔案不存在/解析失敗/
  無有效 stages/沒有任何站宣告 `allows_src_write`)一律擋下原始碼寫入。
  三種失效情境皆有負向測試(exit=2)。

## F-002 `npx skills update` 靜默覆蓋本地 patch

- **發現於**:2026-08-09,判定正典路徑時順手跑 update
- **現象**:對 `code-review/SKILL.md` 的第三軸修改被整份還原,無任何警告;
  三處 `grep -c "Data Integrity"` 從 3 變 0。
- **影響**:「可編輯版」的編輯**不是持久的**。若沒有機器檢查,下一次 update 之後
  第三軸就靜默消失,而報告看起來一切正常——正是最難發現的那種壞法。
- **處置**(已完成):
  - `scripts/skills-update.sh` 包一層(更新 → 冪等重套 patch → 全規則驗證),
    定為唯一允許的更新入口
  - patch 改為「找錨點插入」而非「存一份改好的檔案蓋回去」——後者會把上游更新一併蓋掉;
    錨點消失時 exit 2 要人來看,不猜
  - `gate.py` R5:正典 code-review 缺掛載點即擋 commit。**不把判定交給記性。**
- **不驗內容(刻意)**:R5 的職責是偵測 patch 是否被 update 蓋掉,字串存在即完成判定。
  要它驗內容等於要它判斷 prompt 寫得好不好 —— 那是審查不是閘門。閘門只做布林判定。
- **補上的真缺口(2026-08-09)**:錨點插入法的失效模式不是「掛載點消失」,而是
  **上游改動錨點附近結構、patch 插進去但位置錯了** —— 此時字串全在、R5 全綠、
  第三軸卻掛在錯的地方。R5 已增加位置判定(仍是布林):3b 節必須落在「### 3.」與
  「### 4.」之間;Data Integrity prompt 必須落在「### 4.」與 aggregate 段之間。
  兩種錯位皆有負向測試(exit=1)。

## F-004 git bash 的 `ln -s` 產生實體複本而非 symlink

- **現象**:在 Windows/MSYS 手工重建 symlink 時,實際得到一個實體目錄。
- **影響**:鏡像目錄可能在使用者無感的情況下退化成實體副本,重新打開 drift 的門。

## F-005 `npx skills add -s "a,b,c"` 逗號清單不被支援

## F-008 文件與程式碼的數量不一致(38 vs 34)

- **現象**:`handoff/23_INTL_DATA.md` 三處寫 **38 series**(「原 14 + 新增 24」);
  實際 `fetch_us_macro_fred.py` 的 `SERIES` 清單以 `^\s*("` 計數為 **34** 條。
- **影響**:任務敘述沿用了文件的 38。分類表要蓋幾條,取決於哪個數字是真的。
- **已解決(2026-08-09,進 /to-spec 前)**:用 AST 解析 `SERIES` 賦值逐條列舉,不用正則。
  - `fetch_us_macro_fred.py` 的 `SERIES` = **34 條**(無重複 id),組成 = 原 10 + 2026-06-30 新增 24
  - 文件寫「原 14 + 新增 24 = 38」:**新增 24 完全吻合**,差異全在分母
  - 分母之謎:**另一支腳本 `fetch_us_vix_term.py` 也寫進同一張 `us_macro_daily`**,
    再加 4 條(`VIX9D`/`VIX3M`/`VIX6M`/`VXN`)。34 + 4 = 38 ✓
- **口徑判定**:
  | 問法 | 正確答案 |
  |---|---|
  | FRED 來源的 series | **34** |
  | `us_macro_daily` 表內 series | **38** |
  | 文件「FRED 层已补齐(38 series live)」 | **錯**:把 4 條 yfinance 來源的 VIX 期限結構算進 FRED |
- **權威**:程式碼(AST 逐條列舉)> 文件。文件的 38 是表的總數,不是 FRED 的條數。
- **對本輪的影響**:任務敘述「FRED 那 38 條」前提有誤。分類表的分母必須明寫是哪一種,
  且那 4 條非 FRED series 的修訂特性是**另一個問題**(yfinance 的 restatement,
  不是 FRED/ALFRED 的 vintage),不能混在同一張表用同一套判準。
- **這是「有資料、口徑卻壞」的教科書案例**:兩支腳本寫同一張表,文件只記得其中一支,
  數字就這樣錯了兩個月沒人發現。

## F-018 【可複用判準】偵測「X 沒發生」的機制,自己會不會被 X 略過

- **發現於**:2026-08-09,票 01 的驗收條件實測
- **現象**:涵蓋性不變式(每條在前哨評估的規則,權威層也要評估到)寫好之後,
  用 F-017 的手法重現自造 fail-open —— **它沒有紅**,紅的是另一條(宣告式分歧)。
  追下去發現 `trace.append("R3")` 那次替換根本沒套用上(錨點已變、替換靜默失敗),
  所以 R3 從來沒進過任何 trace。**涵蓋性測試從頭到尾對 R3 是盲的,而且全綠。**
- **診斷修正(比原判嚴重)**:原本記成「記錄點在 return 之後,跳過 return 就跳過記錄」
  —— 那是**條件性失效**。實際是 **`trace.append("R3")` 從來就不存在**:那次替換的錨點已變、
  靜默沒中,而檔案語法正確、測試全綠。**那條涵蓋性測試從誕生起就沒守過 R3**,是**全時失效**。
  兩者的差別很大:條件性失效在某些輸入下仍有效,全時失效是那條規則對它完全不存在。
- **形狀**:偵測「規則被跳過」的機制,自己被同一個跳過略過。
  修好之後記錄點若放在判定路徑上,仍會退化成條件性失效 —— 所以語意改為「職責範圍被進入」,
  記錄點提到判定之前。
- **這是第五次同一個病**(F-001 / F-009 / F-011 / F-017 / F-018),但這次獨特:
  **前四次是規則沒守到東西,這次是驗證規則的機制沒守到規則。**
  稽核往上長了一層 —— 從「規則有沒有洞」變成「檢查規則的東西有沒有洞」。
- **修法**:trace 的語意從「這條規則做出了判決」改為「**這條規則的職責範圍被進入**」,
  記錄點提到判定之前。涵蓋性問的是有沒有人負責,判決屬於第二條不變式的管轄。
- **並補一條測試守住偵測器本身**:斷言 trace 對每條規則都記得到。
  沒有這條的話,下次 trace 又漏一條規則,涵蓋性測試依舊全綠。
- **驗證**:修好後重現 F-017 → **兩條不變式都紅**(3 failed),復原 → 154 passed。
- **可複用判準(已加入稽核維度 4)**:任何「偵測 X 沒發生」的機制,
  都要問一次它自己會不會被 X 略過。同類:靠 log 判斷有沒有跑過、
  靠旗標判斷有沒有初始化、靠快取判斷有沒有變更 —— 記錄動作與被記錄動作
  在同一條路徑上時,一起消失。
- **維度 4 的第二層例子(現在不修,刻意留著)**:新加的「守住偵測器本身」那條測試,
  自己也適用維度 4 —— 它斷言 trace 的內容,而 trace 由被測物件產生;
  若有人讓 trace 變成硬編碼的常數列表,它照樣綠。
  **不再加第三層測試**。這條遞迴是有底的,**終點是人的審查,不是再加一層測試**:
  每加一層,新那層自己又需要被守,而每一層的成本是實的、抓到的東西越來越薄。
  停在這裡,並把「trace 由誰產生」列為 code review 要看的東西。
- **附帶教訓**:這是同一輪內第三次 heredoc 字串替換靜默失敗(F-014)。
  前兩次是語法錯誤、立刻可見;這次**替換沒中、檔案語法正確、測試全綠**,
  完全無聲。工具性摩擦升級成正確性問題。往後程式碼替換一律用 Edit,不用 heredoc。
  **但「一律用 Edit」靠的是記性,不可靠** —— 真正的解藥是票 06 的紅燈紀錄:
  替換沒中 → 行為沒變 → 測試不會從紅轉綠,機制自動抓到,不必有人記得。

## F-019 【維度 4 新變體】迭代來源決定了可見範圍

- **發現於**:2026-08-09,票 03 的測試抓到我的實作
- **現象**:R4 改寫成單一規則兩分支後,「斷裂的 symlink 要擋」那條測試仍然紅。
  原因不在判定邏輯 —— 迴圈以**正典目錄**為迭代來源,而正典項目消失正是斷裂最典型的成因,
  所以那個斷掉的鏡像項目**永遠不會被走訪**。判定寫得再對也沒用,它不在迭代範圍裡。
- **與前兩個變體的差別**:F-018 是記錄點的位置問題(跳過判定就跳過記錄),
  這個更隱蔽 —— **不是記錄點,是可見範圍**。規則本身健全、記錄點也對,
  但它從一開始就看不到出問題的那些項目。
- **共同病灶**:**用 A 當來源,去找「不在 A 裡的問題」。** 同類形狀,供未來對照:
  - 以資料庫現有列為來源,找缺漏的列
  - 以設定檔已列項目為來源,找未設定的項目
  - 以清單為來源,找不在清單裡的東西
  - 以正典為來源,找鏡像多出來或斷掉的東西(本例)
- **修法**:迭代來源改為正典與鏡像的**聯集**。
- **判準**:寫任何掃描式檢查時,先問「我的迭代來源涵蓋得到我要找的問題嗎」——
  要找的若是「缺少」或「多出來」,來源就必須是聯集,不能是其中一邊。

## F-022 紅燈要求的豁免條件必須是「無法自我服務」的

- **背景**:R3 的紅燈紀錄那半接上時,103 個既有 .py 會被追溯要求紅燈紀錄,
  而唯一「補紀錄」的方法是刪掉檔案、跑紅燈、再還原 —— 那正是本規則要擋的作弊樣式。
- **我先採的判準(a)**:紅燈要求只在「建立新檔」時適用。
- **被否決的理由(比「看得見」更硬一層)**:(a) 的豁免條件是「檔案已存在」——
  那是 **agent 隨時可以自己製造的狀態**,建一個空檔就進了豁免集合。
  正確的豁免條件必須是**無法自我服務**的:要進去得改一份凍結的清單,
  那是看得見、會被審查的動作。
- **這與票宣告式豁免完全同構**:豁免必須在前一站的產物裡宣告,不得在被擋住的當下新增。
  同一個原則第三次出現(gate 自我修改、票宣告接縫、既有檔案清單)。
- **處置(判準 b)**:
  1. 清單**用生成的**,不手寫 —— 手寫會漏
  2. 清單**只減不增**:以「存在於機制上線 commit 的樹」為權威,新檔案永遠進不去。
     這個條件**偽造不了,除非改寫歷史**
  3. 清單**要排水**:既有檔案一旦有了合格紅燈紀錄就從清單移除;
     測試守住「清單項目不得同時擁有紅燈紀錄」,債務隨時間縮減,不變成永久豁免名單

## F-023 收尾拆成兩個 commit 的理由

清單的權威是「機制上線 commit 的樹」,而那個 commit 就是機制本身 —— 雞生蛋。
硬要一個 commit 完成的話,只能把上線 sha 留成佔位符,那等於在驗證裡開一個洞。
拆成兩個:**A 讓機制上線,B 以 A 的樹凍結清單**。B 的測試檢查
「清單裡每個檔案都在 A 的樹裡」,A 已存在因此可驗證,且偽造需要改寫歷史。

## F-024 紀錄器把它要觀測的東西弄死了(比 fail-open 更糟的一級)

- **發現於**:2026-08-09,豁免清單接上後第一次跑**全套**測試
- **現象**:`INTERNALERROR ... ValueError: '...' is not in the subpath of '<ROOT>'`,
  session 在第 21 個測試中止。
- **原因**:conftest 外掛拿 `report.fspath` 去 `resolve().relative_to(ROOT)`。
  有些測試會 chdir 到暫存目錄,`fspath` 於是 resolve 到 repo 之外。
- **嚴重度高於 fail-open**:fail-open 是「該擋沒擋」,這個是
  **整個測試執行器停擺**。而 R3 的全部判定都建立在「測試真的跑完」上面 ——
  紀錄器一崩,連綠燈都沒有,紅燈紀錄也永遠不會產生。
- **為什麼一路沒被發現**:前面幾輪都只跑 `pytest tests/test_gate.py tests/test_redlight.py`。
  那兩個檔不 chdir,所以永遠碰不到。**「跑相關的那幾個測試」是一個取樣,
  而取樣不能用來宣稱全綠。**
- **根因與 F-019/F-021 同型**:`fspath` 是事後重建出來的路徑,而 `nodeid`
  本來就帶著相對 rootdir 的路徑 —— 現場已有的事實不用,去重建一個。
  第三次了(紅燈時序用時間戳 vs 當下觀測、impl 搜尋跳過點開頭目錄、這次)。
- **處置**:改取 `report.nodeid.split("::")[0]`,不做任何路徑解析。
  測試直接餵一個 fspath 在 repo 外、nodeid 正常的假 report,斷言不拋例外且鍵值正確。
- **判準**:宣稱「全綠」之前必須跑**全套**;子集合綠燈只能宣稱該子集合。

## F-025 選了「無法自我服務」的豁免條件,卻沒有東西守住那份清單

- **發現於**:2026-08-09,獨立 code review(未寫過這批碼的審查者)
- **現象**:凍結清單 `.agents/legacy-no-redlight.txt` 落在非原始碼目錄、副檔名 `.txt`,
  `is_source_path` 對它回 False,pre-commit 也不驗它的內容。
- **後果**:被 R3 擋下時,在清單末尾加一行就豁免到手,**完全不必碰 git 歷史**。
  而「無法自我服務」正是選這個設計、否決「檔案已存在就豁免」的**唯一**理由。
  守住它的只有一條測試,而**沒有任何機制強制那條測試被跑**。
- **判準(新)**:一條規則的**豁免來源**本身,必須跟規則同等級地被守。
  規則進權威層而它的豁免清單沒進,等於規則沒進 —— 攻擊面直接移到清單上。
  「有測試會抓到」不是守住;測試不在強制路徑上,它就只是文件。
- **處置**:新增 R6 進 `mode_pre_commit`,與 R4/R5 同構,驗每一筆都在上線 commit 的樹裡。
  另加一條測試釘住「R6 真的被權威層呼叫」—— 規則存在但沒人呼叫正是 F-017 的形狀。

## F-026 「債務會隨時間縮減」是一句沒被驗證就寫下的承諾

- **背景**:凍結清單的第三個約束是「要排水:既有檔案一旦有了紅燈紀錄就移除」,
  並加測試守住。測試寫了、綠了。
- **審查指出**:那條測試**依構造幾乎不可能失敗**。排水條件是該檔有合格紅燈紀錄,
  而合格紅燈要求紀錄當下實作不存在 —— 檔案還在,就產不出那種紀錄。
  清單因此接近永久,不會自己縮減。
- **問題不在測試,在我照著約束寫完就宣告完成,沒有回頭問「這條路徑走得通嗎」。**
  綠燈證明了「目前沒有違規」,不證明「這個機制會動」。
  一條永遠不會失敗的測試,讀起來跟一條有效的測試一模一樣。
- **判準**:寫下一條「隨時間會 X」的機制時,要能講出**具體一次 X 發生的完整路徑**;
  講不出來就不要把它寫成承諾,寫成絆線並註明。
- **處置**:測試保留(它仍能擋住同名撞號造成的假排水資格),但改述為絆線;
  ADR 0006 明寫清單接近永久、85 筆裡只有 7 筆真的在生效。

## F-027 要不要測「測試工具」——判準是失效吵不吵,不是它自不自己是測試

- **場景**:空 repo 實測腳本(verify-gates)要不要再為它寫單元測試。
- **我提的理由**:「它自己就是測試,對它再寫測試是同義反覆」——**不充分**。
  `tests/conftest.py` 的紅燈紀錄器同樣是測試基礎設施,我們照樣寫了 `test_redlight.py`,
  而 F-024(紀錄器把測試執行器弄死)證明那是對的。
- **真正的判準**:**這個工具失效時吵不吵**。
  - verify-gates 失效是**吵鬧的**:跑不起來立刻知道;跑完會印出每條規則各擋一次,
    少一條看得見 → 不必再寫測試
  - 紅燈紀錄器失效是**靜默的**:F-019 的 `impl_exists` 永遠 False,一路全綠沒人發現
    → 必須寫測試
- **可複用**:下次遇到「要不要測測試工具」,問的不是「它是不是測試」,
  是「它壞掉的時候會不會有人知道」。
- **連帶**:讓工具**保持吵鬧**本身是設計動作。verify-gates 的失敗訊息必須指出
  **是哪條規則沒擋到** —— 那句話就是它吵鬧的機制,不是錦上添花。

## F-028 heredoc 判準修正:不是「寫新檔用 Edit」,是「別讓 Python 字面量經過 shell」

- **第四次發生**(F-018 的同一個機制)。這次寫出的是**未閉合的字串**:
  `return ["[R6] ... 。` 後面直接斷行,`SyntaxError: unterminated string literal`。
- **為什麼前三次的教訓沒擋住**:前三次都發生在**寫新內容**時,
  於是防線被記成「寫新檔案用 Write/Edit」。這次是用 python 腳本做**字串替換**,
  不在那條防線的涵蓋範圍內 —— 同一個機制,不同的使用情境。
- **判準修正(採用)**:**任何會產生 Python 字面量的路徑都不要經過 shell heredoc,
  包含 sed / python 替換腳本。** 判準綁在「字面量會不會經過 shell」,
  不綁在「這是不是新檔案」。
- 另一個副作用:heredoc 替換是「找不到就靜默不動」,所以同一個指令裡
  一個替換成功、一個沒配對到,而回報只印了一個計數 —— 那正是 F-018
  第三次那種靜默失敗。替換腳本至少要斷言每個 pattern 都配對到。

## F-029 診斷工具本身的誤導:pytest 的錯誤行號屬於被 import 的模組

- **現象**:`ERROR collecting tests/test_gate.py ... SyntaxError ... line 310`。
  我照著看 `tests/test_gate.py` 的第 310 行,那裡完全正常,查了兩個指令才發現
  壞的是 `.claude/hooks/gate.py` 的第 310 行 —— test_gate.py 在模組層 import 它。
- **兩個檔案剛好都超過 310 行**,所以錯誤看起來合理,這是最花時間的一種。
- **這跟被診斷的問題無關,是工具的呈現方式**:collection error 的標題掛在
  測試檔上,traceback 裡的檔名才是真正出錯的地方。下次還會發生。
- **處置**:看 collection error 時,先讀 traceback 最後一行的**檔名**,
  不要只看標題那行。

## F-030 【層級:與「檔案已存在」當豁免條件同型】版控狀態當過濾器

- **發現於**:2026-08-09,票 01 第一次端到端
- **現象**:安裝跑完、R2 也確實擋下、輸出全綠。但目標 repo 裡**沒有**
  `manifest.py`、`install.py`、`tests/test_manifest.py` —— 裝出來的框架裝不動下一個專案。
- **原因**:來源集合取 `git ls-files`,而那三個檔還沒 commit 過。
- **這正是本票在防的那一類**:少帶是靜默的。沒有任何錯誤、沒有任何警告,
  只有「東西不在那裡」這個事實,而它要等到有人在新 repo 裡用到才會顯現。
- **判準**:任何「來源是什麼」的查詢都要問一次
  **它會不會漏掉還沒進版控的東西**。版控狀態不是內容的性質,
  拿它當過濾器就是把「這個檔案存不存在」換成「有沒有人記得 commit」。
- **處置**:改用 tracked ∪ (untracked ∧ 未被 ignore),並把未追蹤的**單獨列出來**
  (帶過去是吵鬧的、看得見的;漏掉是靜默的)。
- **層級(高於一般條目)**:這與「檔案已存在就豁免紅燈」**同型**(F-022)——
  兩者都是拿**人可以隨手改變的狀態**當判定依據。
  「有沒有 commit 過」跟「檔案存不存在」一樣,一個動作就能翻面,
  而翻面之後判定結果就變了,卻沒有任何東西記錄那個動作。
  判定依據必須是**內容的性質**或**無法自我服務的凍結事實**,不是可隨手製造的狀態。

## F-031 【層級:整套驗證方法的盲區,與 F-009/F-011 同家族】獨立涵蓋維度

- **發現於**:2026-08-09,把框架裝進空 repo 後跑它自己的測試:**223 passed, 6 failed**
- **六條全是同一個病**:斷言豁免清單 > 50 筆、拿 `macro_audit/classify.py` 當樣本、
  寫死 sha `9eeacc0`。這些在**這個 repo 裡全都是真的**,所以一路全綠。
- **為什麼比測試不存在更糟**:框架測試跟著框架走。新專案第一次跑測試就看到
  六個與自己無關的失敗,人學到的是「這套測試本來就紅」,整套測試的訊號價值歸零。
- **判準**:**框架測試只能斷言框架的性質。** 需要具體樣本時,樣本由測試自己造
  (tmp_path),不借宿主 repo 現成的檔案。
- **這條只有端到端會抓到**:單元測試在宿主 repo 裡跑,宿主的特徵永遠成立。
  「在別的環境跑一次」是一種**獨立的涵蓋維度**,不是同一批測試跑第二遍。
- **層級(高於一般條目)**:這不是某一條規則的缺陷,是**整套驗證方法的盲區** ——
  與 F-009(規則守錯路徑)、F-011(白名單對新模組 fail-open)同家族:
  三者都是「測了、綠了,而被測的東西根本不在測試的視野內」。
- **後果比失敗本身嚴重**:壞掉的訊號會**訓練人忽略訊號**。
  六個永遠紅的框架測試,教會使用者「這套測試本來就紅」,
  之後真正的紅燈也會被同一個習慣濾掉。一個永遠紅的測試比沒有測試糟,
  跟一條永遠不會失敗的測試(F-026)是同一枚硬幣的兩面。
- **與 F-033 分清楚,不要合併**:兩者都是「測試全綠但什麼都沒守」,成因不同 ——
  **F-031 是測試依賴了宿主的特徵**(換個環境就不成立);
  **F-033 是測試依賴了真實佈局裡根本不存在的前提**(觸發條件製造不出來)。
  前者要換環境跑才看得到,後者要在真實佈局裡跑才看得到。

## F-032 【可複用判準】套套邏輯的三種形狀,判準統一

三種形狀,同一個病:**測試綠了,而它並沒有在檢查實作對不對。**

1. **期望值用實作的方式算出來。** 測試自己重跑一遍實作邏輯再比對,
   實作錯的時候期望值也一起錯,永遠相等。
2. **實作針對測試輸入寫特例。** 分支在具體識別碼上(某個 series_id、某個檔名),
   測試的那幾個輸入走特例路徑,其餘走沒被驗過的路徑。
3. **斷言剛好跟預設值重合。**(2026-08-09 新增)
   標記表的目錄前綴測試寫成「目錄標 `copy` → 底下的檔案是 `copy`」,
   而 `copy` 就是預設值 —— 前綴比對**根本沒實作**也會綠。
   改成標 `ask` 之後才真的紅。這一種最難察覺:測試看起來在測新功能,
   斷言也確實成立,只是成立的理由不是那個功能。

4. **綠的原因不是你以為的那個原因。**(2026-08-10 新增)
   G1 的 18 條驗收斷言 `exit == 2 and "G1/保護清單" in err` ——
   驗的是「有命中**某條**保護路徑」,不是「命中的是**這一條**」。
   清單若被讀成別的內容(權限、編碼、檔名大小寫)而**仍然可讀**,
   每條探針都可能命中同一條無關項目,18 條全部通過。
   **實際製造過一次**:把清單換成只有 `D:\` 一條,舊斷言全綠,
   新斷言(帶著各自應命中的路徑)全部紅、結束碼 1。
   這一種與前三種的差別:前三種是斷言太弱,這一種是**斷言問錯了問題**。

**統一判準:測試必須在【實作錯誤】時會紅,而不只是在【實作缺席】時會紅。**
第四種形狀補一句:**還要問「它紅/綠的理由是不是我要的那個理由」** ——
斷言要指名道姓,不要只驗「有東西發生了」。

缺席會紅是低標(import 失敗、AttributeError 都能達成)。
寫完一條斷言就問一次:**把實作換成一個最笨的錯誤版本,這條會不會紅?**
第三種形狀的檢查最直接 —— 斷言的期望值**不得等於預設值/空值/恆等結果**。

## F-033 R4 只驗得出「內容不同」,驗不出「東西不見了」—— 兩層疊起來它是空的

- **發現於**:2026-08-09,票 02 第一次跑機器列舉實測:**六條規則裡只有 R4 沒擋下自己的情境**
- **現象**:實體副本分支有一行
  `if not os.path.exists(src) or not os.path.exists(m): continue`
  —— **兩邊任何一邊缺檔就靜默跳過**。從鏡像刪掉 `tdd/SKILL.md`,R4 判乾淨。
- **兩層疊加才是完整的故事**:
  1. R4 只在「兩邊都有、內容不同」時觸發
  2. 而硬連結 / symlink 佈局下,兩邊是**同一個實體檔**,內容不可能不同(票 10)
  於是 R4 在實務上**沒有任何情境會觸發** —— 它讀起來在守鏡像,實際什麼都不守。
- **為什麼單元測試沒抓到**:既有的 R4 測試都在測「內容不同會不會擋」,
  而那個前提在本 repo 的佈局下製造不出來,測試是用人工造的 tmp 目錄驗的。
  **真實佈局下的實際行為,只有真實佈局跑一次才看得到** —— F-031 的同一個判準。
- **處置**:少檔案、少目錄、鏡像多出正典沒有的東西,三種都改為違規;
  「鏡像整個不存在」維持不違規(那是還沒裝,由安裝流程負責,不是 drift)。
  五條測試,含兩條「應該乾淨」的正向案例 —— 沒有它們,這組測試會變成恆真。
- **可複用**:一條規則若只有一種觸發條件,要問**那個條件在真實佈局下製造得出來嗎**。
  製造不出來的話,它是一條讀起來在守、實際不守的規則,比沒有規則危險。
- **與 F-031 分清楚,不要合併**:F-031 是**測試依賴宿主特徵**(換個環境就不成立);
  本則是**測試依賴真實佈局裡不存在的前提**(觸發條件在真實佈局製造不出來)。
  兩者都長成「全綠但什麼都沒守」,但一個要換環境才看得到,一個要在真實佈局裡才看得到。

## F-034 偵測「沒被部署」的機制,自己也需要被部署 —— 這條遞迴有底

- **票 03 的形狀**:要偵測「權威層沒裝」。而偵測本身住在哪裡?
  - 前哨(隨 `.claude/settings.json` 走)→ 只涵蓋 **AI 路徑**
  - 測試(隨 `tests/` 走)→ 涵蓋所有人,但**沒有機制強制它被跑**(F-025)
  - 安裝時強制驗證 → 只涵蓋「有跑安裝的人」
  三者都碰不到 **clone 下來直接手動 commit 的人**。
- **維度 4 的自我適用**:偵測「X 沒發生」的機制會不會被同一個 X 略過?
  這裡答案是**會**,而且**關不掉** —— git 刻意不讓 clone 自動執行任何東西,
  零接觸安裝在設計上就不存在。
- **處置不是繼續往下追,是明寫**:
  `not_installed_notice()` 的訊息裡直接寫「本偵測只在 AI 走前哨、或有人跑測試時
  會出聲 —— clone 下來直接手動 commit 的人碰不到它,那個缺口關不掉」。
  沒有這句的話,訊息讀起來像「裝好就全部關上了」,而那是假的。
- **這條遞迴有底,終點是人的審查。** 同閘門自身免紅燈(ADR 0004)、
  同刻意偽造證據(ADR 0006):**擋不住就明說擋不住**,不假裝擋得住。
  假裝擋得住比擋不住危險 —— 你會停止注意它。

## F-035 去宿主化的四種形狀,以及「兩個環境都綠」為什麼必須是機器驗的

- **票 07 實際改掉的六條**,成因分四類:
  | 形狀 | 例子 | 換掉成什麼 |
  |---|---|---|
  | 斷言宿主的**規模** | `len(清單) > 50` | 清單 = 生成集合扣掉已排水的(兩邊都成立,而且更強) |
  | 借宿主**現成的檔案**當樣本 | `macro_audit/classify.py` | `fake_repo` fixture 自己造 `pkg/thing.py` + `tests/test_thing.py` |
  | 寫死宿主的 **sha** | `9eeacc0...` | `gate.read_go_live()` 讀 repo 自己的 |
  | 比對宿主**設定檔的寫法** | `"/.cache/" in .gitignore` | 問 `git check-ignore` —— 要驗的性質是「被忽略」,那件事只有 git 說了算 |
- **第一條換完之後比原本強**:原本只擋「清單是空的」,現在同時擋
  「手加一筆」(超出生成集合)與「生成不完整」(缺一片又沒有排水證據)。
  **去宿主化不是把斷言放寬,是把斷言換到對的層次上。**
  放寬的話會變成 F-032 第三種形狀(斷言與預設值重合)。
- **驗收不能是「宿主 repo 全綠」** —— 它本來就綠,證明不了任何事。
  必須是**兩個環境各跑一次**,而且那件事不能靠記性:
  已接進 `verify_gates`,新 repo 裡框架測試不是全綠就整個失敗。
- **為什麼值得插隊做**:04/05/06 是把做完的事寫下來,拖一天沒有代價;
  07 是**每多裝一個 repo 就多汙染一次**。壞掉的訊號會訓練人忽略訊號,
  而那個習慣一旦養成,之後真正的紅燈也會被同一個習慣濾掉。

## F-036 票 04 的前提是我沒查證就寫下的 —— 同 symlink 那次

- **票 04 原文**:「CLAUDE.md 同時裝著框架規範與台股專屬規範,整份複製會汙染」。
- **查證結果**:`grep 台股|TradingAgents|FRED|macro_audit|策略|local_db` 全部 **0 命中**。
  七個小節**全是框架規範**,一句專案專屬內容都沒有。
- **同型**:與「鏡像是 symlink 靜默回退還是腳本本來就複製」那次一樣 ——
  **在 spec / 票裡寫下一個沒查過的事實描述**,而它讀起來像已知條件。
  差別是那次寫成了問題(至少會被問),這次寫成了**前提**(不會被問,只會被實作)。
- **判準補充**:grill 站的「先查清 X 不是問題,是待辦」只涵蓋**寫成問句**的情況。
  寫成陳述句的假設更危險 —— 沒有人會去驗證一個看起來像事實的句子。
  **票與 spec 裡的每一個事實描述,都要能指出它是查來的還是猜的。**
- **處置**:票 04 的實質從「拆內容」改為「**建立界線**」——
  今天沒有東西要拆,但將來有人寫下「台股收盤 13:30」時,
  它有一個明確不會被帶走的位置。`framework_section()` 找不到界線時**丟例外不退化成整份**:
  失敗方向與標記表相反(標記表往多帶倒,這裡往不帶倒),因為帶錯的規矩不會報錯,
  只會讓 agent 照錯的規矩工作。

## F-046 描述系統性質的句子,會被後來的人讀成功能宣告

- **現象**:`CLAUDE.md` 與 `g1_guard_draft.py` 都寫著
  「R 系列是流程規則、**可組裝**、每個專案自己決定要不要」。
  後來要決定「框架 repo 自己受不受管」時,那句話被當成
  **「已經有 per-repo 啟用機制」**的依據,並據此推論「選 C 不是新複雜度」。
- **查證結果**:全域搜尋 `組裝|啟用哪|RULES_ENABLED|rule_enabled` ——
  只有那兩處散文,**沒有任何實作**。`gate.py` 的 R1–R7 全部無條件生效;
  最接近的 `rule_codes()` 與 `SCENARIOS` 都是**列舉**,不是**啟用控制**。
- **當時那句話沒有錯**:R 規則在**性質上**確實各自獨立、可以分開裝。
  錯的是「性質上可以」被後來的人(包括寫下它的我自己)讀成「機制上已經可以」。
- **為什麼特別容易發生**:性質描述與功能宣告在文法上長得一模一樣 ——
  「X 是可組裝的」既可以是設計評價,也可以是功能清單的一行。
  讀的人沒有理由懷疑,而且**寫的人隔一段時間也會忘記自己當時在說哪一種**。
- **判準**:**寫系統性質時標明它不是實作。**
  「性質上可以 / 目前未實作」兩句一起寫,不要只寫前半。
  反過來也成立:讀到一句聽起來像功能的描述時,先問**它有沒有對應的程式碼**,
  不要把它當成前提(F-036 的同一條紀律,對象從「票裡的事實描述」擴到「文件裡的性質描述」)。
- **處置**:兩處都補上「目前沒有 per-repo 開關,R1–R7 全部無條件生效」。

## F-037 手寫進正典而不登記 = 把持久性交給記性

- **現象**:2026-08-09 把「先查清 X 不是問題,是待辦」寫進
  `.agents/skills/grill-with-docs/SKILL.md`,**沒有登記進 `apply_patches.py`**。
  下一次 `npx skills update` 會靜默蓋掉它 —— 而那正是 wrapper 與 R5 存在的理由(F-002)。
- **我當下就知道**,還開了票 06 記著。但「開票記著」本身就是把持久性交給記性的一種:
  票沒做完之前那段內容是**隨時會消失的**,而消失時不會有任何訊息。
- **判準**:往正典寫東西的當下就登記,不留「之後補」——
  中間那段時間的長度不由你決定,由上游什麼時候發版決定。
- **處置**:`patch_grill_question_triage()`,冪等;實測跑兩次不重複、
  模擬上游蓋掉後重套得回來(出現次數 1)。
  這個 skill 短到沒有結構性錨點,改為附加到尾端 —— 語意上也對,
  它是本地補充,不是插進上游流程的中間。

## F-038 R3 只看**這次改動的檔案**,所以一支沒測試的舊檔可以躺很久

- **現象**:commit 票 04/05/06 時被擋:
  `[R3] .claude/patches/apply_patches.py:找不到對應測試`。
  但這支檔案在機制上線那次 commit 就存在了,一直沒被擋過。
- **原因**:`mode_pre_commit` 掃的是 `git diff --cached --diff-filter=ACM` ——
  **只看這次改動的檔案**。沒被碰過的舊檔永遠不會被評估。
- **這不是缺陷,是設計**:每次 commit 掃全 repo 會把每一次提交變成大掃除,
  而那會讓人開始用 `--no-verify`。但要知道它的**實際涵蓋範圍**:
  R3 保證的是「**被碰過的檔案**都有測試」,不是「repo 裡所有檔案都有測試」。
  兩者差很多,而 R3 的訊息讀起來像後者。
- **實際效果是好的**:債務在**下一次有人動它時**被討回來,而那時剛好有人在讀那段碼。
  但這件事要寫下來,否則會有人以為全綠等於全都有測試。
- **處置**:補 `tests/test_apply_patches.py`(冪等、上游覆蓋後可回復、
  檔案不在時出聲不靜默跳過)。不用 `--no-verify` 繞過 —— 這支檔案本來就可測。

## F-039 【新維度】零涵蓋不會產生任何訊號 —— gate.py 的 matcher 裡沒有 Bash

- **現象**:`.claude/settings.json` 的 PreToolUse matcher 是
  `Write|Edit|MultiEdit|NotebookEdit`。**沒有 Bash,也沒有 PowerShell。**
- **實際意思**:R1–R6 只擋得住用**檔案工具**寫的東西。
  用 `python - <<EOF` 或 `Set-Content` 寫進原始碼目錄,六條規則**一條都不會被評估**。
  本輪就用過好幾次 heredoc 寫檔案 —— 那些寫入全部沒有經過閘門。
- **為什麼前四個維度看不到它**:那四個維度問的都是「規則有沒有洞」,
  而洞至少會在某條規則上留下痕跡(判決錯、時點不一致、前提失效)。
  **零涵蓋沒有痕跡**:沒有規則被評估 → 沒有規則會出錯 → 測試全綠 → trace 是空的 →
  涵蓋性不變式看到「前哨沒評估、權威也沒評估」,兩邊一致,**判定合規**。
  我們花了一整輪稽核 fail-open,而最大的那個洞不在任何一條規則裡。
- **判準(維度 5)**:**列出工具,不是列出規則。**
  從「規則有沒有洞」出發永遠看不到零涵蓋,因為那裡沒有規則。
  要從另一端列舉:agent 手上有哪些工具,逐一問「碰這個工具時有沒有東西會被評估」。
- **同型**:與 F-025(規則進了權威層而它的豁免清單沒進)、
  ADR 0007(規則存在但整層沒被部署)是同一家族 —— **涵蓋範圍的邊界本身沒有被檢查**。

## F-040 使用者層 hook 掛上去不會立刻生效,而且是靜默的

- **現象**:把 G1 寫進 `~/.claude/settings.json` 之後,立刻在同一個 session 裡
  跑 `ls "/d/<受保護目錄>"`(受保護路徑)—— **正常執行,hook 沒有觸發**。
- **原因**:settings.json 在 session 啟動時讀取;新增的 hook 要重開 Claude Code 才載入。
- **這件事本身就是 ADR 0007 的形狀**:規則寫好了、邏輯驗過了、
  掛載設定也寫進去了,**但那一層在這個 session 裡不存在** —— 而沒有任何東西說它不存在。
  我如果沒有做端到端實測,會以為它已經在守。
- **判準**:**「設定檔寫好」不等於「機制生效」。** 掛載完必須用真實的工具呼叫驗一次,
  而不是只驗 hook 腳本本身的邏輯 —— 後者證明的是「如果被呼叫,它會擋」,
  不是「它會被呼叫」。這兩件事差一整層。
- **處置**:G1 的邏輯已逐條驗過(18 條保護路徑各擋一次、清單自我保護、fail-closed),
  但**部署尚未生效**。重開 Claude Code 後要重跑一次端到端才算完成。

- **【家族:規則存在但不在流量路徑上】現在有三個成員,位置一次比一次外面**:

  | 成員 | 規則在哪裡失聯 |
  |---|---|
  | F-009 | **規則內** —— R1 守 `docs/specs/`,而 spec 實際產在 `.scratch/` |
  | ADR 0007 | **整層** —— pre-commit 不進版控,clone 的副本上權威層不存在 |
  | F-040 | **載入時機** —— 設定檔寫好了,但 session 啟動時才讀,這個 session 沒有它 |

  三者的共同點不是「規則錯了」,是**規則沒有出現在實際的流量路徑上**,
  而且三次都靜默 —— 沒有規則被評估,就沒有東西會說話。

- **統一判準**:
  **驗邏輯證明「如果被呼叫,它會擋」,證明不了「它會被呼叫」。**
  這兩件事差一整層,而差的那一層每次都在更外面:先是路徑、再是部署、再是載入時機。
  下一個會在哪裡未知 —— 所以每一次掛載都要用**真實的工具呼叫**收尾,不是驗腳本本身。

## F-041 「找不到證據」有兩種,而我把其中一種當成另一種

- **現象**:查 hook 為什麼沒觸發時,`~/.claude/debug/` 不存在。
  我的結論是「日誌裡沒有 trust 相關事件,所以信任假設沒有被確證」。
- **錯在哪**:那個目錄**只有跑 `claude --debug` 才會有內容**。
  它不存在的意思是**除錯日誌從來沒被開啟**,不是「開著而沒有記到東西」。
  我把「證據來源沒接上」當成了「證據不存在」。
  | 我以為的 | 實際的 |
  |---|---|
  | 查過日誌 → 沒有 trust 事件 → 假設未被支持 | 日誌從來沒產生 → **零資訊**,假設既沒被支持也沒被推翻 |
- **代價**:在零資訊的狀態下做了實驗(改 trust flag、跑探針)。
  探針失敗時我無從分辨是「信任不是原因」還是「設定要重開才生效」——
  **失敗給了零資訊,那一輪是浪費的。**
- **判準(可複用)**:做實驗之前先問**證據來源接上了沒有**。
  「查了沒有」與「從來沒開」在日誌、metrics、trace 上長得一模一樣,
  而它們的資訊量一個是 1 一個是 0。分辨方法:**問這個來源是預設開啟的嗎**;
  不是的話,先開啟再實驗,否則實驗的失敗分支沒有資訊。
- **與 F-031/F-033 的關係**:那兩則講的是「測試全綠但什麼都沒守」,
  本則是「觀測為空但根本沒在觀測」。三者同一個家族:
  **機制看起來在運作,而它的輸入或輸出其實不在場。**

## F-042 【本輪最大的一個】整個前哨層靜默失效,原因是一行編碼假設

- **現象**:R1–R7 的前哨從來沒有擋過任何東西。這一輪看到的所有擋下訊息
  ——`[R2/commit]`、`[R3]`、`[R6]`——**全部來自 pre-commit**,一次 `[六站閘門/前哨]` 都沒有。
- **根因**(用 hook 自己寫的 trace 抓到的):

  ```
  PARSE_FAIL  JSONDecodeError('Invalid \escape: line 1 column 252 (char 251)')
  ```

  `json.load(sys.stdin)` 在 Windows 上用**主控台編碼(cp950)**解 payload。
  而 payload 是合法的 UTF-8 JSON,裡面有中文路徑
  (`"cwd":"***整行已遮罩(真實路徑,票 39 K3,裁決者授權)***"`)。
  <!-- K3:原文是一段含真實使用者名與工作區資料夾名的 JSON 跳脫路徑。
       票 32 整行遮蔽形式,留此記號 —— **遮的是內容,不是這件事發生過**。
       歷史裡的那一份留待票 39 開刀一併清除。 -->

  技術要點不依賴那個路徑本身:**關鍵是它含中文**,而 cp950 解 UTF-8 位元組
  會產生不合法的跳脫序列。換成任何含非 ASCII 的路徑都會重現。
  cp950 解出來的位元組序列讓 json 看到不合法的跳脫字元 → 例外 →
  **`except Exception: return 0`** → 放行。

- **三個條件疊起來才會這麼難查**:
  1. 例外被吞成 `return 0`(fail-open),沒有任何輸出
  2. `hook_event_name` 這類 payload 只在真實工具呼叫時才有,**測試裡永遠測不到**
     —— 測試呼叫的是 `check()`,不是 `mode_hook()`
  3. `--debug` 日誌只涵蓋啟動,不記錄工具呼叫;`~/.claude/debug/` 預設根本不存在(F-041)

  **三層觀測全部不在場**,所以它可以一直「看起來在守」。

- **我走過的三條錯誤路徑,每一條都因為缺證據而無法證偽**:
  未信任(改了 trust flag,沒用)→ 需要重開(重開了,沒用)→
  `settings.local.json` 的 "Broken symlink"(取完整行才發現那是本來就不存在的檔)。
  **真正有用的一步是讓 hook 自己記錄它收到什麼** —— 在缺觀測的那一層補觀測,
  而不是在有觀測的層繼續猜。

- **處置**:
  - `sys.stdin.buffer.read().decode("utf-8")`,不靠平台預設編碼
  - `except` 改為 **fail-closed(exit 2)**:讀不懂輸入不代表沒事
  - 所有 stderr 輸出走 `_err()` 明確 utf-8 —— 擋下訊息在 cp950 終端機上是亂碼,
    而讀不懂的訊息人會照著繞不會照著修
- **可複用判準**:**跨行程邊界時,不要相信平台預設編碼。**
  stdin / stdout / subprocess / 檔案,四個地方都要明寫 encoding。
  而 `except: return 0` 這個組合在**任何**閘門裡都是禁忌 ——
  它把「我不懂發生什麼事」翻譯成「沒事」。

- **附帶被證偽的兩個假設**:`$CLAUDE_PROJECT_DIR` 在 hook 環境裡**有**被設定
  (先前以為沒有,那是我的 Bash 環境沒有);設定檔是**熱重載**的
  (日誌 `Settings changed from userSettings, updating app state`),不需要重開。

## F-045 【新形狀】一個時點 fail-closed、另一個時點 fail-open

- **位置**:`load_stage()` 讀不到 `pipeline.json` 時回 `("idle", None)`。
- **兩個時點的失效方向相反**:

  | 時點 | R2 問的問題 | 讀不到時的結果 |
  |---|---|---|
  | 寫入 | 「現在這一站可以寫原始碼嗎?」 | idle 不可寫 → **擋下**(fail-closed) |
  | 提交 | 「你是不是還停在前置站?」 | idle **不在**前置站集合裡 → **放行**(fail-open) |

  所以:`pipeline.json` 壞掉或被刪,寫入時看起來一切正常(它會擋),
  而 **R2 在提交時無條件通過**。
- **為什麼這不是一般的 fail-open**:先前每一則都是**單一方向**的 ——
  某條規則放行了不該放行的東西。這一則是**兩個各自正確的設計疊起來變成一個洞**:
  - ADR 0005:R2 在兩個時點問不同的問題(正確,否則會擋掉每一次合法提交)
  - 「讀不到就當 idle」:在寫入時是保守的選擇(正確)

  兩者單獨看都對,合起來在提交時開了一個門。
  **它是 F-017 家族(時點語意)與 fail-open 家族的混種。**
- **為什麼難發現**:寫入時的擋下會讓人以為「這個情況有被處理」。
  **一個時點的正確行為會替另一個時點的錯誤行為背書。**
- **判準(可複用)**:
  **一條規則在多個時點被評估時,每個時點的失效方向都要分別問過。**
  不能因為「這個 fallback 在某個時點是保守的」就認為它整體保守 ——
  fallback 的方向是相對於「當下在問什麼問題」而定的,而問題會隨時點改變。
- **處置**:`load_stage()` 回 `UNREADABLE_STAGE` 哨兵而不是 `"idle"`,
  R2 增加一條**與時點無關**的分支:站別讀不到時兩個時點都擋。
  這是 R2 唯一與時點無關的分支,理由是「你停在哪一站」這個問題本身沒有答案時,
  兩種問法都答不出來。

## F-044 【S6 判準修正】「只是接線,不測」兩次都放過同一條要命的程式碼

- **背景**:`mode_hook()` 的進入點分派被歸類為「不測」,理由是它只是接線 ——
  讀 stdin、取欄位、呼叫 `check()`。第二次審視時我又用同一個理由跳過。
- **而那條接線裡就是 F-042 那一行**:`json.load(sys.stdin)`。
  **整個系統最要命的一行,住在被宣告為「沒有行為」的地方。**
- **判準修正(採用)**:
  **進入點若包含解碼、解析、格式轉換,它就不是接線。**
  接線是把 A 原封不動傳給 B;一旦中間有轉換,它就是有行為的程式碼,要測。
  轉換 = 可能失敗 = 有分支 = 有行為。
- **處置**:抽出 `parse_hook_payload(raw)`,四條測試,
  **語料含中文路徑與非 ASCII** —— 只用 ASCII 語料測的話,這個缺陷永遠不會現身。
  另加一條「payload 形狀對照基準」,把 2026-08-10 實際觀測到的頂層鍵釘住,
  形狀變了要有人知道,而不是靠 `payload_text` 回空字串然後靜默放行。
- **可複用**:「這只是接線」是一個**需要證明的宣稱**,不是免測理由。
  證明方式:指出它沒有任何轉換、沒有任何可能失敗的步驟。做不到就要測。

## F-063 憑證檔的假陰性:掃內容的 pattern 攔不到二進位憑證

- **來源**:F-062 收尾時暴露、使用者裁決要求補的洞。
- **紅燈(raw)**:260-byte 二進位憑證檔(PKCS#12 magic + 隨機位元組)

## F-064 【F-042 第三次】同一個編碼假設,在四個位置各犯一次

- **觸發**:收 grill 站時,一份**中文檔名**的計畫書被 R2 誤擋,同批的 ASCII 檔名文件全部通過。
- **原因**:git 對非 ASCII 檔名預設回傳 **C-quoted** 路徑(`"docs/plans/\345\217\260….md"`)。
  拿 `--name-only` + `splitlines()` 取路徑的地方全部收到帶引號與 octal escape 的字串;
  下游 `replace("\\", "/")` 把 escape 的反斜線一起換掉 —— 路徑徹底壞掉。
- **`replace("\\", "/")` 不是元兇,查清楚才動它**:它絕大多數用在 `os.path.relpath()` 結果上,
  Windows 回反斜線、要轉正斜線比對,**正當且必須保留**。真正的錯是把 C-quoted 的 git 輸出
  餵進一個假設「反斜線 = 路徑分隔符」的函式。**修輸入,不動判定。**
- **四個位置,三種失效方向**(同一假設散開,正是 F-042 的形狀):

  | 位置 | 方向 |
  |---|---|
  | `gate.py` staged 清單 | R2 誤擋 —— **fail-closed,看得見** |
  | `leak_scan.py` staged 清單 | 路徑壞 → `io.open` 失敗 → `except: continue` → **中文檔名檔案裡的金鑰完全不掃、一聲不吭(fail-open)** |
  | `install.py` ls-files | 中文檔名檔案**靜默漏帶**(F-030/F-031 家族) |
  | `install.py` ls-tree | 壞路徑寫進 legacy 清單,R6 事後 `cat-file` 查證必失敗 |

- **處置**:三支各自加取路徑的正確做法(`-z`,NUL 分隔),`install.py` 收斂成 `git_paths()`。
  `status --porcelain` 也改 —— 那些路徑是**要給人看的**,C-quoted 的話使用者認不出自己的檔案。
- **為什麼是 `-z` 不是 `core.quotePath=false`**:後者只關掉引號,檔名含**換行或引號本身**時仍有歧義。
  NUL 是唯一不可能出現在路徑裡的位元組。**選結構上正確的解,不要選剛好夠用的。**
- **測試撞到的老坑再現**:釘住「不准用 quotePath」的測試 grep 字面,結果把 docstring 裡
  **解釋為什麼不用它**的句子也算成「用了」。字面比對分不出**使用**與**討論** ——
  與 F-062 的「防禦清單長得像洩漏」同一形狀。改成偵測 Python 字串常數形式。
- **可複用**:
  1. **同一個錯誤假設會在多個位置各犯一次,修一處等於沒修** —— 找到一個,立刻全域列舉同類呼叫。
  2. 非 ASCII 語料要進測試常備語料庫。只用 ASCII 測,這族缺陷永遠不現身(F-042 原文已寫過一次,
     這次證明「寫過」不等於「做到」—— 新寫的 git 呼叫沒有人拿中文檔名測過)。
  3. 失效方向要逐位置問:同一個壞路徑,在閘門是誤擋(吵),在掃描器是靜默放行(致命)。

## F-065 「照上游同款」在 self-governance 例外處會裝出一個靜默缺口

- **場景**:裝進新專案時補 `bootstrap.sh`(理由:沒有它,重 clone 後洩漏 hook 不接線,F-055 白學)。
  直覺做法是「照 agent-gates 同款」複製 `.githooks/pre-commit`。
- **陷阱**:`bootstrap.sh` 設 `core.hooksPath=.githooks` 之後,**`.git/hooks/` 被 git 整個忽略**。
  而 agent-gates 的 `.githooks/pre-commit` **只跑 leak_scan** —— 因為 ADR 0010 裁決它
  **不自管**(選項 B),六站權威層本來就不該在它自己身上跑。
- **後果(若照抄)**:目標 repo 的 `.git/hooks/pre-commit`(install.py 寫的、含 gate)被
  hooksPath 蓋過 → **跑過 bootstrap.sh 的那一刻六站權威層靜默消失**。
  前哨照跑、測試照綠、install 的驗證早就跑完了 —— 沒有任何東西會說它不在。
- **處置**:目標 repo 的 `.githooks/pre-commit` **兩層都掛**(leak_scan 先、gate 後)。
- **可複用**:**上游檔案帶著上游的例外一起過來。** 複製一個檔案時要問的不是
  「上游長怎樣」,而是「上游為什麼長那樣、那個理由在這裡成不成立」。
  self-governance 例外(這個 repo 刻意不管自己)是最容易被照抄成缺口的一類 ——
  它在來源端是正確的,在目的端是洞。
- **框架待辦(未做,待裁決)**:`install.py` 應該直接產生目標 repo 的
  `.githooks/pre-commit`(兩層)+ `bootstrap.sh`,讓權威層跟著 clone 走 ——
  那會**部分關掉 ADR 0007 說的那個缺口**(clone 下來直接手動 commit 的人)。
  現在是人工補的,下一個安裝的人不會知道要補。

## F-066 框架替自己挖的坑:安裝器叫專案建 .env,測試卻掃 .env

- **現象**:裝了框架的專案跑 `test_the_shipped_tree_is_clean` 必紅,而且
  **把使用者的真 API key 印進測試輸出**(log、CI 畫面、對話紀錄都算外流面)。
- **因果鏈**(值得完整記,因為兩端各自都對):
  1. F-062 讓 `install.py` 把 `.env` 寫進目標 repo 的 .gitignore —— 正確。
  2. 專案照做,把金鑰放進 `.env` —— 正確。
  3. `test_the_shipped_tree_is_clean` 用 `os.walk` 掃整個工作目錄 —— **它不理 gitignore**,
     於是掃到 `.env`,報「發布來源含洩漏」。
  **每一步都對,合起來是錯的。** 這類缺陷不會出現在任何單一步驟的審查裡。
- **根因**:「發布來源」這個集合被用檔案系統定義,但它的真正定義是 **git 的**。
  問題是「會被推出去的東西乾不乾淨」,而 `.env` 依定義不會被推出去。
- **處置**:改用 `git ls-files -z` 列舉。一次解決兩件事 —— 假陽性消失,
  真金鑰也不再被印出來。另加一條「列不到檔案就失敗」的斷言:
  掃不到東西的綠燈不算綠燈(否則 ls-files 哪天回空,這條測試會安靜地變成裝飾)。
- **可複用**:
  1. **當一條規則叫別人建立某個東西,要回頭問自己的檢查會不會撞到那個東西。**
     安裝器與測試是同一套框架的兩隻手,它們對 `.env` 的假設相反了七十二小時沒人發現。
  2. 掃描器的輸出本身是外流面。設計「印出命中內容」這種好心功能時,
     要先問它會不會在失敗時把秘密印給所有看得到 log 的人。

## F-067 掃描器把它要防的東西印出來

- **接續 F-066**。那一則修的是**掃哪些檔**(改用 git ls-files,別再掃 `.env`),
  但沒修**輸出**。實測時仍必須在外面接一層遮罩才敢看 —— 那是權宜,不是修好。
- **兩處都在洩**:
  1. `內容:` 印出命中的整行,秘密原樣在裡面。
  2. `命中 pattern:` 印出 pattern 原文 —— 而**個人 pattern 往往就是秘密本身**
     (使用者名稱、往來對象、甚至金鑰字面)。等於在報告裡再洩一次。
- **時機最壞**:那一刻是 commit 被擋、開發者在看終端機、CI 在記 log、
  agent 在寫對話紀錄 —— 眼睛最多的時候。
- **處置**:命中的那一段換成「已遮罩 N 字」(前後文保留,還定位得到);
  個人 pattern 只顯示編號不顯示內容,通用 pattern(公開清單裡的形狀)照印全文。
  兩條測試釘住,並且順便釘住「不要遮過頭」—— 遮到定位不了的話,
  下一個人會去把遮罩拿掉。
- **可複用**:**防護措施的輸出是它自己的攻擊面。** 設計「印出細節幫你定位」
  這種好心功能時,要先問:這段輸出會出現在哪些眼睛前面?失敗路徑上的
  診斷資訊,比成功路徑上的更容易被複製貼上到 issue、chat、log 聚合器裡。

## F-068 對帳只做了一個方向:票宣告的欄位有查,裁決宣告的欄位沒查

- **場景**:記錄庫 schema 交裁決前,逐一核對「17 張票宣告的欄位,schema 是不是都有」。
  結果全中、零缺口 —— 看起來很乾淨。
- **漏掉的是反方向**:**裁決文件宣告了、但沒有任何票宣告的欄位**。
  實際掉了一條:「未成熟樣本要有獨立狀態(持有期未滿)」在裁決記錄裡白紙黑字,
  但 spec 沒有、17 張票沒有一張宣告它。拆票時整條掉了,而拆票時我是照 spec 拆的 ——
  **spec 漏了,票就跟著漏,而票對得上 spec 所以怎麼查都是綠的。**
- **附帶災害**:那個掉了的狀態日後補回來時,差點跟隔離區的狀態撞名(兩個 `pending`,
  一個是「還沒複核」一個是「持有期還沒到」)。掉出去的東西回來時不會自動避開既有命名。
- **可複用**:**對帳要雙向。**
  - 正向:下游宣告的,上游有沒有?(票 → schema)
  - 反向:上游宣告的,下游接了沒?(裁決 → spec → 票)
  只做正向會得到一個自洽但不完整的系統 —— 自洽是因為兩份文件是同源的,
  完整與否要拿**第三份**(更上游的那份)來對。

## F-069 自我審查的假陽性:把正確的裁決誤判成自己的偽造

- **場景**:發現裁決文件寫 A、而 spec/票/詞彙表三份都寫 B。我判定「這是我寫裁決文件時
  把自己的量測參數誤植成裁決」,並準備照 B 修正 —— 理由編得很順:我確實跑過一次
  用 A 當參數的量測。
- **實情相反**:A 是使用者後來明確更新的裁決,裁決文件忠實記錄;B 是被推翻的舊值,
  漂移在下游三份文件。**我差點把正確的真相源改成錯的。**
- **根因**:查證方向單一。發現不一致時我只問「我是不是搞錯了」,沒問
  「是不是裁決被更新過、而下游沒跟改」。前者符合「對自己嚴格」的直覺,
  但它預設了一種特定的錯誤形狀,於是只找得到那一種。
- **可複用**:**不一致的查證不能只往「我犯錯」的方向查。** 至少要列三種可能:
  (a) 我記錯/寫錯;(b) 上游變更後下游未跟改;(c) 兩邊各自對、但適用範圍不同。
  三種的處置完全不同 —— (a) 改上游,(b) 改下游,(c) 補說明範圍。
  只查 (a) 的話,遇到 (b) 會**朝錯的方向修**,而且修得理直氣壯。

## F-070 寫下觀測結果,改變了被觀測的對象

- **場景**:備份完成後自動做還原驗證(逐表比對原庫與快照的筆數與內容雜湊)。
  流程寫成:產生快照 → 發布 → **記一筆「備份成功」** → 驗證。
- **現象**:每次都驗不過,而且只差一張表 —— `backup_status` 原庫 1 列、快照 0 列。
- **原因**:那一列就是「備份成功」本身。**記錄觀測結果的動作,讓被觀測的對象變了。**
  快照是在記錄之前拍的,所以它不可能含有那一列;而比對要求兩邊完全相同。
- **處置**:驗證移到寫任何狀態之前。狀態記錄是驗證的**結果**,
  結果不能先於它所描述的事發生 —— 這不是風格問題,是因果順序。
- **回歸測試釘的是行為不是順序**:「一個乾淨的庫跑完整流程要能通過」+
  「連跑兩天也要通過」。有人把記錄搬回驗證之前,這兩條就會紅;
  而如果只斷言「呼叫順序是 A 再 B」,重構一次就失效了。
- **可複用**:**任何「檢查完就記一筆」的機制,都要問記錄本身算不算在被檢查的範圍裡。**
  這一族的其他形狀:掃描器把自己的輸出檔掃進去、健康檢查把自己的心跳寫進被檢查的表、
  審計日誌記錄「審計執行了」然後下次審計對不平。共同點是**測量工具與被測物共用儲存**。
  處置有三條路:測量在寫入之前做(本次選的)、把測量的紀錄排除在測量範圍外
  (要小心那是在挖豁免)、或測量與被測物分開儲存。

## F-071 長期紅的測試會意外滿足 R3 的紅燈要求 —— 長紅不只是噪音,它是一把萬能鑰匙

- **發現於**:2026-08-12,R3 判準改成「紅燈要對著改動前的碼發生」之後,
  順手驗證它對 `gate.py` 有沒有真的在守。
- **現象**:
  ```
  最後一筆 tests/test_gate.py 紀錄:
    result = red   ticket = 07
    紅在哪些 = TestLegacyNoRedlightList…、TestTheListItselfIsGuarded…(共 4 條)
    hash = 6e2c85db…   HEAD = 6e2c85db…
  redlight_missing(gate, ticket=07) = None(合格 -> gate.py 可寫)
  ```
  R3 放行了,而那盞紅燈是**票 02 的 4 條**,與這次要做的 R8 修改毫無關係。
- **根因**:**紅燈的粒度是「測試檔」,不是「行為」。** 紀錄只說
  「tests/test_gate.py 這一輪是紅的」,說不出紅在哪個行為上。
  於是任何一個長期紅的測試檔,都會讓它對應的實作檔**永久滿足** R3 的後半。
- **這改變了對「長紅」的定性**。票 02 把那 4 條紅定性成 F-031(壞掉的訊號
  訓練人忽略訊號)—— 那只說對一半。它同時是**解鎖鑰匙**:
  R3 對框架自己的閘門實質關閉,而且沒有任何東西會說出這件事。
  於是票 02 的嚴重度從「第一印象被汙染」升級為「規則在最該生效的地方被關掉」。
- **與 legacy 清單的關係**:同一輪剛把 legacy 那條出口關掉(ADR F-0013),
  這條出口卻還開著,而且更隱蔽 —— legacy 清單至少是一份看得見的名單,
  長紅不是名單,它是副作用。
- **可複用**:**「有紅燈」與「這次改動有紅燈」是兩件事。**
  任何以「某個集合曾經失敗過」當通行證的機制,都要問集合的粒度夠不夠細到
  綁住這一次的改動;不夠細的話,集合裡有一個長期壞掉的成員就等於整個集合免檢。
  同一家族:整包 CI 只要有一個 flaky 就沒人看紅綠、
  覆蓋率門檻用整個 repo 的平均值、健康檢查只要有一項恆綠就拉高總分。
- **處置**:本則先記錄,未處置。兩條候選路徑 ——
  (a) 紀錄下沉到測試節點層級(哪幾個 test id 紅的),R3 比對這次改動宣告的行為;
  (b) 先把票 02 收掉,長紅消失,這把鑰匙自然不存在。
  (b) 便宜但不治本(下一個長紅出現時它會回來),(a) 才是判準本身的修正。

## F-072 上游的偵測缺陷會讓下游的量測樣本**偏掉**,而樣本看起來是滿的

- **發現於**:2026-08-13,同步前的唯讀盤點。
- **現象**:量化 repo(整個住在中文路徑底下)的 `gate.py` 對不上任何框架版本,
  少了 `staged_paths` 的 `-z`(F-064 修的那條)。後果是**中文檔名的 staged 檔案
  靜默不掃**。而那個 repo 正在**影子期** —— 影子的用途是量測誤擋率,
  用量到的數字決定要不要晉升成正式擋。
- **真正的問題不是那個洞,是它污染了量測**:shadow-log 現在有 3 筆。
  那 3 筆是「掃得到的那些檔案」產生的;掃不到的那些**不會產生任何紀錄**,
  也不會產生任何錯誤。**樣本看起來是滿的**(有數字、有紀錄、可以做統計),
  實際上它的涵蓋範圍被一個上游缺陷裁掉了一塊,而被裁掉的那塊剛好是
  這個 repo 最常見的檔名形態。
- **所以晉升門檻在同步完成前不算數。** 拿偏掉的樣本去算誤擋率,
  算出來的數字會很好看 —— 因為漏掉的那些本來就不會產生誤擋紀錄。
  「證據不足」與「證據顯示沒問題」在這裡長得一模一樣。
- **曝險窗口**:自 2026-08-11 裝機起約一天,直到同步完成。
- **可複用**:**任何「先量測、再依量測結果放寬」的機制,都要先驗量測器本身的涵蓋。**
  量測器漏掉的東西不會出現在樣本裡,而樣本的沉默會被讀成「沒事」——
  這是 F-041(「找不到證據」有兩種)在量測情境的形狀,
  也是 F-031 的反面:那則講壞掉的訊號訓練人忽略訊號,這則講**缺席的訊號
  被讀成正面訊號**。
  同一家族:A/B 測試的事件上報在某些裝置上失敗、
  抽樣稽核只抽得到有 log 的那些請求、
  漏斗分析裡「沒進到下一步」與「沒回報下一步」混在一起。
- **處置**:同步路徑(票 09)修好那個洞;影子期的晉升判斷在同步後**重新起算**,
  現有 3 筆不作為晉升依據。這一則也要抄進量化 repo 的影子期紀錄
  ——**但那要在它自己的 session 做**,不在這裡順手改別的 repo。

## F-073 框架的出貨檔案,在下游是被掃描的資料,不是自己人

- **發現於**:2026-08-13,影音 repo 的 D21 cookie 護欄擋下了框架出貨的
  `tests/test_scanner.py` —— 它拿 cookie 選項名當正控樣本,**靜置成文**,
  pattern 直接比中。
- **現象**:框架寫這個測試時想的是「我在測掃描器」;下游看到的是
  「一個含有違禁字串的檔案」。**同一個檔案,兩種身分**,而下游的守衛只認後者。
- **通則**:**框架出貨的檔案必須在任意內容守衛底下惰性。**
  框架不知道下游裝了哪些守衛,也不該知道 —— 所以正控字串只能執行時拼裝,
  不得靜置成文。
- **拼接點的選法不是隨便切。** 原本的寫法把切點放在選項名的尾段之前,
  於是前半仍是一個完整的選項名,下游的短 pattern 在連字號處成立詞邊界,
  照樣比中。**切點必須落在第一個詞的中間。**
- **本輪把同一個字面重新種回去三次**:說明它的註解裡、pattern 清單裡、
  長度斷言的 `len("完整字串")` 裡。三次都是在寫「不要靜置」的當下靜置的。
  **所以這條靠的是機器檢查,不是紀律** —— 加了兩層:
  (a) 通則:本檔不得含有自己用到的樣本字串字面量(用執行期組出的值比對原始碼);
  (b) 具體:整棵出貨樹(非散文)對已知下游守衛的 pattern 零命中。
- **散文的邊界是決定,不是疏漏**:`friction-log.md` 自己也含那串字(F-061 的內文),
  目前無害**只因為下游守衛豁免散文**(`DOC_SUFFIX`)。那是下游的一個決定,
  不是框架能倚賴的性質。改寫散文以規避字面,正是那個豁免存在要避免的稅
  ——「規則的說明本身必須寫得出來」。所以散文留著,代價寫在這裡:
  **若哪天有下游守衛不豁免散文,框架的 friction log 會在那裡擋住它自己。**
- **可複用**:**任何會被複製到別人地盤的東西,都要用「對方的掃描器」讀一次。**
  同族:公開範例含看似金鑰的字串、SDK 的測試 fixture 含測試信用卡號、
  文件裡的範例 token 被密鑰掃描器攔下。共同點是
  **產出者用「意圖」分類,消費者用「形狀」分類**,而形狀不看意圖。

## F-074 同步過來的成品撞上 R3:紅綠燈迴圈在上游,規則卻在下游要證據

- **發現於**:2026-08-13,影音 repo 收到框架同步的實作,R3 擋下。
- **現象**:R3 要求本地紅燈紀錄(測試曾在實作不存在時紅過),
  而下游從來沒有那個時刻 —— 它拿到的是**成品**。
  上游做完紅綠燈,下游只收結果。
- **三條現成的路都不對**:
  - legacy 名單只減不增,入場券是「在機制上線 commit 的樹裡」,
    新收到的成品**正確地**進不去;硬塞會把名單變成許願池
  - 本地補跑紅燈要先刪掉剛收到的實作 —— 規則又在改變行為,而且改得更差(F-046 的形狀)
  - 關掉 R3 是稅太高的規則的下場,關掉之後沒人記得它守什麼
- **形狀**:**規則的證據要求綁在「誰做了那件事」上,而那件事發生在另一個 repo。**
  這不是規則錯,是規則的**責任歸屬**沒有跨 repo 的表達方式。
- **處置**(ADR F-0014):`sync` 產 provenance(上游 commit + 路徑),
  R3 改判「與上游那個 commit 的物件逐位元組相同 ⇒ 紅燈責任在上游」。
  關鍵在**驗證對到上游的 git 物件**,不採信 provenance 宣稱的 hash ——
  手寫一筆造不出上游沒有的 blob,偽造要改上游。
  **provenance 是控制不是證據**,而控制不得可自助。
- **可複用**:**跨邊界的規則要問的是「這件事誰負責」,不是「這裡有沒有證據」。**
  在本地找不到證據時,先問那件事本來就該不該發生在本地。
  同族:vendored 依賴撞上「每個檔案都要有測試」、
  產生的程式碼撞上覆蓋率門檻、上游 base image 撞上「每層都要掃描」。

## F-075 【判錯對象第四例】惰性檢查掃的是「repo 裡有什麼」,而問題是「會出貨什麼」

- **發現於**:2026-08-13,F-073 的惰性檢查上線後。
- **現象**:檢查用 `git ls-files ROOT` 當掃描集合。那回答的是
  **「這個 repo 裡有什麼」**,而規則要問的是**「會被搬到下游的是什麼」**。
- **後果**:本 repo 自己的東西(工作票、專案測試,將來還有守衛的 pattern 定義檔)
  都被算進去。而**守衛的 pattern 檔本來就寫著要偵測的字樣** ——
  把它算進出貨集合,規則會要求一個**永遠不可能滿足**的條件,
  而稅太高的規則最後會被整條關掉(F-046 走過的路)。
- **處置**:掃描集合改為 manifest 的 `copy` 桶推導。判定對象與規則的問題對齊。
  另補一條測試釘住「本 repo 自己的票不在出貨集合裡」——
  沒有它,集合退化回「全部」也一樣綠,而那正是這次要修的東西。
- **這是同一個形狀的第四例**,四例的共同結構是
  **「規則問的問題」與「它實際量的東西」在多數情況重合,在邊界分岔**:
  | | 規則要問 | 實際量 | 何時分岔 |
  |---|---|---|---|
  | F-046 R8 | 檔案最終內容有沒有 import | 編輯**片段**能不能解析 | 片段是縮排的時候 |
  | ADR F-0013 R3 | 這個**實作**寫之前紅過嗎 | 這個**檔案**當時存不存在 | 檔案已存在時 |
  | F-074 R3 | 誰負責這次紅燈 | **本地**有沒有紀錄 | 成品來自上游時 |
  | 本則 | 會**出貨**什麼 | repo 裡**有**什麼 | 本地檔案含敏感字面時 |
- **可複用**:**寫下一條規則時,把「要問的問題」與「打算量的東西」分兩行寫出來,
  再問它們在哪裡會分岔。** 多數情況重合正是危險的地方 ——
  重合讓實作看起來對,分岔只在邊界出現,而邊界就是規則最該生效的地方。

## F-076 我從一次失敗推論出「規則缺一條出口」,而失敗的是我的指令形狀

- **發現於**:2026-08-13。原本記成「R7 把寫入收口了,卻沒有給刪除一條出口」,
  並據此把兩個改名判為做不到。**那個結論是錯的**,由裁決者指出後實測推翻。
- **事實**:`git` 本來就在 `BASH_ALLOWED_CMDS` 裡,乾淨的
  `git mv A B` 直接通過。我先前寫的是 `cd "<repo>" && git mv A B` ——
  而 `bash_write_violation()` 的許可比對是**逐段**的:
  第一段 `cd "..."` 不以任何許可前綴開頭,整條就落出許可清單,
  掉進寫入構造檢查,`mv` 命中,擋。
  逐段比對本身是對的:少了它,`git status && rm -rf x` 會整條被許可。
- **我犯的錯有兩層**:
  1. **樣本數一**。一次被擋就推論出規則的性質,而那次的變因是我自己的指令形狀。
  2. **習慣蓋過觀察**。整個 session 我都用 `cd X && ...` 的形狀,
     它在別的指令上從沒出事(那些沒有寫入構造),所以我沒有把它當成變因。
     **一個長期無害的習慣,在規則邊界上變成了變因,而我對它是盲的。**
- **代價**:一張寫錯前提的票、一個沒必要的重複測試檔、
  一條差點被改掉的守衛(票 13 原本的候選方向之一是「開窄口讓 git mv 過」——
  而它本來就過得了)。**差一點就為了一個不存在的問題去放寬守衛。**
- **真正的缺陷是訊息**:擋下時說「請改用 Write / Edit」,而檔案工具沒有刪除,
  於是照著訊息做的人會得出「這件事做不到」。現場是「你的 `cd` 前綴讓許可失效」,
  訊息卻指向另一個方向 —— 與 F-046 同一個形狀:**擋得對,但把人指去檢查
  一個沒問題的地方。** 票 13 改成處理這個。
- **可複用**:
  - **從單一次失敗推論規則的性質之前,先把自己的輸入變成變因試一次。**
    「規則擋了我」與「規則沒有出口」是兩件事,而前者比後者常見得多。
  - **要放寬一條守衛之前,先證明它真的擋住了正確的做法。**
    這次差一點就用「規則缺出口」當理由去開窄口,而缺的是我的指令形狀。
  - 同族:把環境設定錯誤讀成函式庫的 bug、把權限問題讀成 API 不支援、
    把自己的快取讀成上游沒更新。共同點是
    **我方的變因不在我方的視野裡,因為它一直都在那裡沒出過事。**

## F-077 消滅重複實作時,我搬了分類器,沒搬讓它安全的那兩道護欄

- **發現於**:2026-08-13,影音 repo **第三輪** dry-run。前兩輪沒撞。
- **現象**:sync 要覆蓋目標的六個根目錄檔,其中 `.githooks/pre-commit`
  會從**三層掛載降成只剩 leak_scan** —— **權威層靜默消失**。
  hook 還在、還會跑、還會擋洩漏,只是不再呼叫 `gate.py --pre-commit`,
  而整個過程看起來像**一次成功的更新**。
- **為什麼第三輪才爆**:批次二(`79bfe22`)為了消滅 F-058(同一件事兩份實作),
  讓 `sync.mark_for` 改呼叫 `manifest.mark_in`。兩者對**未命中任何前綴**的檔案處置相反:

  | | 未命中任何前綴 |
  |---|---|
  | 舊 `sync.mark_for` | 回 `None`,而 `None != "copy"` → **跳過** |
  | `manifest.mark_in` | 回 `DEFAULT_MARK` = `"copy"` → **覆蓋** |

  前兩輪跑在合一之前,所以沒撞。**行為改變沒有被任何測試接住** ——
  我的 sync 測試用的標記表把相關檔案都明確標過了,
  於是「未分類走哪條路」這格從來沒被走到。
- **根因不是預設值本身,是我只搬了一半。**
  「未標記 → copy」在安裝器是**對的**,而它安全的理由是兩道護欄:
  1. `classify()` 先過 `in_scope()`,範圍外的檔案根本不進任何桶
  2. `uncovered_neighbours()` 把未涵蓋的鄰居列出來讓人確認

  我把分類器搬過去,**那兩道一道都沒搬**。更新路徑既沒有範圍過濾,
  也沒有人確認的環節,而它的寫入對象是**別人 repo 裡已經存在的檔案**。
- **同一個預設,兩邊的風險方向相反**:
  安裝器裡「多帶」是吵鬧的(空 repo,看得到、可以刪);
  更新路徑裡「多帶」是**覆蓋**,而覆蓋是靜默的 ——
  被蓋掉的內容沒有第二份。整份 manifest 的「代價不對稱」那句話,
  在更新路徑上**方向是倒過來的**,而我照抄了原本的方向。
- **處置**(票 15):`explicit_mark()` 不帶預設,預設由各呼叫端明確選;
  sync 遇未分類**拒絕**並點名檔案與缺的前提(票 13 判準)。
  另補一條測試:上游 `git ls-files` 的每一筆都要有標記 ——
  實測當下有 **8 筆**未分類,其中一筆(`docs/agents/adr-numbering.md`)
  是我批次二自己新增卻忘了分類的。
- **可複用**:
  - **把兩份實作合成一份時,要合的不只是邏輯,還有「未命中時怎麼辦」。**
    預設值往往不寫在函式名裡,而兩邊的預設可以剛好相反。
  - **搬一段邏輯之前,先問它現在為什麼是安全的。** 讓它安全的常常是
    **它周圍的東西**,而周圍的東西不會跟著 import 一起走。
  - 同族:把驗證函式抽出來共用,但呼叫端原本先做的空值檢查沒跟著抽;
    把 retry 邏輯統一,而其中一邊原本外面有 timeout。

## F-078 R7 的寫入偵測命中中文技術文字裡的 `->`

- **發現於**:2026-08-13,本 session 撞到兩次。

  同族:commit message 裡的 `#` 被當成註解、log 訊息裡的 `${}` 被 shell 展開、
  搜尋關鍵字裡的 `--` 被當成參數結束。共同點是
  **同一段位元組同時是「要被執行的東西」與「要被閱讀的東西」**,
  而規則只看得到前者。

## F-079 PowerShell 5.1 用 ANSI 讀 `.ps1`,腳本裡的中文路徑當場壞掉

- **發現於**:2026-08-14,票 22 R1d 打包備份 zip 時。
- **現象**:把打包腳本寫成 `.ps1`(UTF-8 無 BOM),Windows PowerShell 5.1
  執行時報一長串 parser error。實際壞的不是語法 —— 是腳本裡的中文路徑
  被讀成 `AI撌乩??豹?啗鈭斗?隞??` 之類的亂碼,引號因此配對不上,
  parser 才在完全無關的行號上炸。**錯誤訊息指向語法,現場是編碼。**
- **根因**:PowerShell 5.1 讀 `.ps1` **檔案**時預設用 ANSI(這台機器是 cp950),
  不是 UTF-8。要它讀對必須存成 **UTF-8 with BOM**。
  對比:同樣的中文路徑**直接當指令字串傳**進去完全正常 —— 差別只在
  「經過檔案」這一步。
- **歸屬**:**F-042 家族**(cp950 編碼假設),但現身位置是新的:
  前幾次都在**資料**被讀進來的路徑上(stdin payload、git 輸出、原始碼檔),
  這次在**腳本檔自己被直譯器讀取**的那一步。
  也就是說:這一族不只影響「程式讀的東西」,也影響「程式本身」。
- **處置**:改用 Python 重寫(有 `# -*- coding: utf-8 -*-` 宣告,讀自己不吃這個坑)。
  **不改用「路徑全部改成英文」繞過** —— 那是把問題藏起來,而下一個寫
  `.ps1` 的人會再撞一次。
- **可複用**:
  - **「同一段文字直接傳沒事、寫進檔案再讀就壞」是編碼問題的指紋。**
    先問「它經過了哪一個讀取器」,不要先讀語法錯誤指的那一行。
  - 選直譯器時,**能自我宣告編碼的比不能的安全**。Python 有 coding 宣告、
    `.ps1` 沒有(只能靠 BOM),而 BOM 是**檔案怎麼被存**的性質 ——
    存檔的人與寫程式的人常常不是同一個工具。
  - 同族:`.bat` 的 `chcp`、CI 上 `LANG` 沒設、
    editorconfig 沒管到的檔被另一個編輯器存成別的編碼。

## F-080 動守衛碼之前沒搜既有實作,寫了一份重複的偵測

- **發現於**:2026-08-14,票 27 收尾要把「金絲雀」接進 `verify_gates.py` 時。
- **現象**:票 27 的核心交付本來寫成「新增一條檢查:權威層未接上要大聲失敗」。

  接 `verify_gates.py` 時才看到 **`gate.authoritative_layer()` 早就存在**:
  已處理 `core.hooksPath`、已判內容而非只判檔案存在、已有測試,
  而且已經被 `sentinel_footer()`、`mode_hook()`、`install.py`、
  `verify_gates.py` 四處呼叫。我寫的是它的第二份實作。
- **影響**:兩份實作回答同一個問題,而它們**會分岔** ——

     「**有東西說了,但被節流到每 4 小時一次、在 stderr、實務上沒人看見**」。

- **可複用**:
  - **「新增一個檢查」這種票面用語要先翻譯成「這個能力在不在」再動手。**
    前者假設答案是「不在」,而那個假設正是要被驗證的東西。
  - **診斷可見度問題與診斷缺席問題,修法完全不同**
    (提高可見度 vs 接上缺的那層)。搞錯方向的症狀是:
    做完之後原本的東西還在,只是多了一份。
  - 同族:重寫一個「還沒有的」utility 而它在隔壁模組、
    為既有設定項新增一個同義的設定項、把既有 flag 換個名字再實作一次。

## F-081 什麼時候可以自己還原檔案,什麼時候要停下來問

- **發現於**:2026-08-14,票 25 關票前。`tests/test_g1_guard.py` 整個**收集失敗**,

  而這裡要做的是 `git restore` —— 它**寫**一個檔案,字面上落在那條規則裡,
  但實質是把一個本來就該在的東西放回去,**不可能失去任何東西**。
  停下來等,代價是整個測試集在那段時間無法收集。
- **判準(已裁決鑄為正式規則,2026-08-14)**:
  三條**同時**成立時,agent 可以自己還原,**但必須自報**:
  1. 是**追蹤檔**(git 認得它)
  2. **沒有未提交的修改**(`git status` 是 ` D` 而不是 ` MD`)
  3. **HEAD 即權威**(要還原的內容就是 HEAD 的內容,不是某個推測版本)
  **缺任何一條 → 停,等裁決。**
- **為什麼三條缺一不可**:
  - 缺 1(未追蹤)→ 沒有權威來源,「還原」其實是**重建**,而重建靠的是記憶
  - 缺 2(有未提交修改)→ 還原會**覆蓋掉那些修改**,那才是真的破壞
  - 缺 3(要還原成別的版本)→ 那不是還原,是**選擇**,而選擇是裁決者的事
- **可複用**:
  - **「這個動作會不會寫檔案」不是好判準,「這個動作能不能失去東西」才是。**
    前者把 `git restore` 與 `rm -rf` 歸成一類,而它們的風險差了無限倍。
  - 判準要能**機器化**:上面三條都是 `git status` 一行看得出來的,
    不依賴「我覺得這樣沒問題」。憑感覺的安全判斷會在疲勞時失效。
  - 同族:`git checkout --` 還原、`git stash pop` 回復、把備份檔複製回原位 ——
    每一個都要問同樣三條。
- **附帶觀察**:這次失敗的方向是**整個測試集無法收集**,不是某一條紅。
  所以它會立刻被發現 —— 這是好的失敗方向。
  相對地,如果被搬走的是一個**沒有測試載入它**的檔案,同樣的手滑會靜默存活很久。

## F-082 修好偵測器之後沒有回頭重掃,而舊資料已經推上遠端

- **發現於**:2026-08-14 換機器演練(卡點 #16)。
- **現象**:個人 leak pattern 清單修好(卡點 #13)之後,新的 pattern 回頭掃既有檔案,
  照出票 22 的演練文件把**真實備份資料夾名**寫進版控 —— 而且**已經推上遠端**。
- **為什麼舊 pattern 沒抓到**:原文**遮了使用者名稱、沒遮資料夾名**。
  **遮一半比完全沒遮更容易過關**:完全沒遮會被個人 pattern 攔下;
  遮掉使用者名稱之後,剩下的資料夾名不在當時的 pattern 裡,於是**掃描全綠**。
  部分遮蔽騙過的不是人的眼睛,是**機器的比對** —— 而人看到「有遮」就放心了。
- **判準**:**修好一個偵測器之後,回頭重掃既有資料。**
  新規則的第一次全量掃描,問的不是「以後會不會再犯」,是「**以前犯過幾次**」。
  規則變動之後**舊世界不會自動重新受檢**,而已經推出去的東西不會等你想起來。
- **處置**:不改寫歷史(repo 為 private,協調成本大於收益),
  改立門 —— 「轉公開前置 = 歷史審查」(票 33),該筆預先登記為已知項。
- **可複用**:
  - 每一次擴大偵測範圍,**同一個 commit 裡就跑一次全量掃描**,
    不要等下次順手 —— 「下次」與「從來沒有」在紀錄上長得一樣。
  - **部分處理的東西要特別看**:遮一半、轉義一半、驗證一半的輸入,
    比完全沒處理更容易通過檢查,因為檢查往往只問「有沒有做」。
  - 同族:密碼只遮中間幾碼、log 只脫敏第一次出現、URL 只清 query 不清 fragment。

## F-083 收了一個入口,卻沒回頭問它的同類入口在哪

- **發現於**:2026-08-14 換機器演練(卡點 #11)。**繞路撿到的,不是腳本要找的** ——
  當時探針四被 R7 搶答,我去找「哪個動詞能穿過 R7 以隔離 G1」時量到的。
- **現象**:R7 的 `WRITE_CONSTRUCT` 收了 PowerShell 的寫入動詞
  (`New-Item` / `Set-Content` / `Add-Content` / `Out-File` / `Clear-Content`),
  **漏掉 `Remove-Item` / `Move-Item` / `Copy-Item` / `Rename-Item` 整個刪改家族**。
  而 G1 第二級**刻意只管專案外**(專案內刪除放行是寫在註解裡的設計)。
  **兩層的空隙疊在一起:專案內 `Remove-Item` 同時穿過 R7 與 G1。**
- **為什麼特別貴**:漏掉的是**刪除**。寫入被漏掉還留著檔案可以事後看,
  刪除被漏掉之後**沒有東西可以看** —— 與 G1 保護清單把備份排第一的不對稱同一條。
- **判準**:**收了一個入口,就回頭問它的同類入口在哪。**
  問法是「這個東西還有哪些同類」,不是「我還想得到什麼」——
  **想不到不等於不存在**。要去列舉來源:語言的動詞表、API 的方法清單、副檔名標準、
  shell 的重導向形式。列舉得出來的東西不該靠回憶。
- **與 F-082 的關係**:F-082 是**資料側**(規則變了,舊資料沒重掃),
  這一條是**規則側**(收了一類入口,同類沒收)。
  共同形狀:**規則變動之後,舊世界不會自動重新受檢。**
- **可複用**:同族 —— 擋了 `eval` 沒擋 `exec`、驗了 `POST` 沒驗 `PUT`、
  清了 `<script>` 沒清 `<iframe>`、限了副檔名沒限大小寫變體。

### 第三標本(2026-08-14,票 36):**收窄抽取必須同時鋪底**

F-082 講的是**資料側**(規則變了,舊資料沒重掃)。這一則是它在**規則側**的對偶:
**收窄一個入口之後,回頭問誰接住漏下來的。**

票 29 為了避免票 21 的垃圾目標(`-Value hello` 被當成寫入目標),
把 PowerShell 的抽取收窄成「只認可列舉的位置」。**收窄本身是對的**,
錯在沒有配 fail-closed 的底 —— 收窄之後「抽不到」變成常態,
而底層仍然是「抽不到 → 回空 → 放行」。

實測穿過去的:`rm -- -weird.py`、`Copy-Item .cache/x.json pkg/thing.py`
(第二條會寫進 `pkg/`,而 R7 完全沒出聲)。

- **具名教訓**:**收窄抽取必須同時鋪底,否則「不亂猜」退化成「不擋」。**
- **為什麼會漏掉**:收窄的動機永遠是**訊息品質**(別報垃圾目標),
  而收窄的代價落在**涵蓋率**(報不出來的東西變多了)。
  **兩者不在同一個人的注意力裡** —— 改的時候在看訊息,而破的是攔截。
- **票 29 當天問了 F-083(「還有哪些同類動詞」),沒問「抽不到的時候誰接住」。**
  兩個問題長得像,但一個是**廣度**、一個是**底**。
- **可複用**:
  - 任何「讓判定變精確」的改動,同時問:**判不出來的時候會怎樣?**
    精確化幾乎總是把「判不出來」的集合變大。
  - 同族:白名單改嚴、正則收邊界、型別檢查加細 ——
    每一次都會多出一批「不符合新規則也不符合舊規則」的輸入,
    而它們預設落到哪一邊,往往沒有人決定過。
  - **症狀相同不代表根因相同**:本票的洞有一半是「抽不到」、
    一半是「**抽到了錯的**」(取到來源、漏掉目的地),
    只修前者會留下後者。

## F-084 臨時排除的產物沒有命名慣例,事後看起來像檔案遺失

- **發現於**:2026-08-14,票 30 落地後檢查匯出包。
- **現象**:`dotfiles-export\` 裡少了 `settings.json` 與 `leak-patterns.local.txt`,
  而留下的三個檔 mtime 是原本的匯出時間、目錄 mtime 卻晚了兩小時。
  **看起來完全像檔案遺失。**
- **實情**:演練時人工把它們移進 `_excluded\`,後續依卡點 #4 的裁決
  把整個 `_excluded\` 移出匯出目錄。**沒有任何東西不見**。
- **成本**:一輪查證 —— 逐項排除「是不是我的碼刪的」
  (`grep os.remove/shutil.move` 零命中、期間只跑過 dry-run、R7 本來就擋刪檔),
  然後回報請人確認。**排除自己花的力氣,比找出真相花的多。**
- **根因**:**臨時排除的產物沒有命名與位置慣例。**
  它既不在「正式產物」的語彙裡,也不在「垃圾」的語彙裡,
  所以它落在哪裡、叫什麼名字,每次都是臨場決定 ——
  而臨場決定的東西,兩小時後就沒有人記得它是刻意的還是意外的。
- **處置**:立慣例 —— **排除物一律放匯出目錄之外,名稱帶日期**
  (例:`dotfiles-export-excluded-2026-08-14\`)。
  寫進票 30 與 `machine-init.md`。
- **可複用**:
  - **「刻意移走」與「意外消失」在檔案系統上長得一模一樣。**
    唯一能區分它們的是**命名與位置的慣例**,不是記性。
  - 判準:**任何會讓正式產物「看起來變少」的動作,要在名字上留下意圖。**
    帶日期是最便宜的一種 —— 它同時說了「這是刻意的」與「什麼時候」。
  - 同族:改名成 `*.bak` 卻放在原目錄、暫時註解掉的設定沒寫原因、
    為了測試而清空的資料表沒有標記。**每一個都會在幾小時後變成疑案。**

### 具名原則候選:**順序決定安全性**(2026-08-14,票 21)

兩個動作各自都對,**顛倒就錯** —— 而顛倒之後看起來完全一樣。

| 標本 | 正確順序 | 顛倒的後果 |
|---|---|---|
| **一:先備份後手術** | 異地副本 → 清理/改寫歷史 | 手術先做,失敗就沒有回頭路 |
| **二:先 refuse 後遮蔽**(票 21) | 引號不成對 → refuse;走到遮蔽的必然成對 | **遮蔽仍然是猜** —— 同一段程式碼、同一個效果,而安全性完全取決於誰先誰後 |

標本二值得展開:R7 原本拒絕「剝掉引號內容」,理由是
「shell 引號規則有轉義、巢狀,**半套的解析器比零涵蓋更危險**」。
E/F 的 refuse 落地之後,**那個理由不再成立** ——
因為不成對的引號已經在上游被擋掉,下游拿到的輸入必然是良構的。

> **一個上層的收口,可以把下層原本危險的做法變成安全的。**
> 反過來說:**評估一個做法危不危險,要連它的前置條件一起評估** ——
> 同一個做法在不同的前置下,是「良定義」與「猜」的差別。

- **可複用**:
  - 看到「這個做法太危險」的結論時,問一句:**危險是它自己的性質,
    還是它的輸入的性質?** 後者可以靠上游收口消掉。
  - 建立了新的上游保證之後,**回頭看有沒有因為舊前提而被否決的方案** ——
    那是 F-082「重掃既有資料」在**設計決策**上的對偶。
  - 同族:先驗證再刪除、先鎖定再讀取、先建索引再查詢 ——
    每一對的兩個動作單看都無害,而順序錯了就是資料遺失或競態。

### 配對句:**廣度與底是兩個問句**(F-082 / F-083 共用)

這兩則常常被當成同一件事,而它們問的東西不同:

| | 問句 | 漏掉的後果 |
|---|---|---|
| **F-083(廣度)** | 「這個東西**還有哪些同類**?」 | 收了一族,漏了另一族 |
| **F-082 第三標本(底)** | 「**判不出來的時候會怎樣?**」 | 收窄之後,漏下來的沒人接 |

**票 29 問了廣度,沒問底** —— 它去查了 PowerShell 動詞表(廣度做得很徹底,
甚至跑了兩個列舉軸),卻沒問「抽不到的時候誰接住」。
結果是**動詞收得更全,而洞更大**。

> **收窄的動機永遠是訊息品質(別報垃圾目標),代價落在涵蓋率。
> 兩者不在同一個注意力框裡** —— 改的時候眼睛在訊息上,而破的是攔截。

判準:**任何「讓判定變精確」的改動,同時問兩句** ——
「同類還有誰」與「判不出來時往哪倒」。只問前者會做出一個又寬又漏的規則。

### 修正案(2026-08-14,票 29 收尾):**列舉軸也要列舉**

上面說「去列舉來源,不要憑印象」。實際執行票 29 的第三類調查時發現
**那句話還不夠** —— 因為**列舉本身要選一個軸,而軸也會有盲區**。

當天跑了兩個軸,結果**它們互相看不見對方**:

| 軸 | 查法 | 漏掉什麼 |
|---|---|---|
| **動詞軸** | `Get-Command \| Where Verb -in (Set/New/Remove/Export/…)` | `Invoke-WebRequest -OutFile` —— 動詞是 `Invoke`,**語意上完全看不出在寫檔** |
| **參數軸** | `Where Parameters 含 OutFile / FilePath / DestinationPath` | `Set-Item` —— 用**位置運算元**,沒有具名輸出參數 |

**一個軸的「查完了」是另一個軸的盲區。**

只跑動詞軸,會漏掉「動詞不帶語意、參數才決定行為」的那一整類;
只跑參數軸,會漏掉「參數是位置的、沒有名字可比對」的那一整類。
**而兩者都會給出「我查過了」的感覺** —— 那個感覺是自信而錯誤的。

- **可複用**:
  - 列舉之前先問:**這個軸看得見什麼、看不見什麼?** 至少跑兩個正交的軸。
  - 正交軸的常見對:**名字 vs 型別**、**呼叫端 vs 定義端**、
    **靜態宣告 vs 執行期註冊**、**動詞 vs 參數**。
  - 判準:**兩個軸的結果如果完全一樣,其中一個大概沒選對** ——
    正交的軸本來就該各自撈到對方沒有的東西。這一輪各撈到一個,是健康的訊號。

## F-085 修好一個命中之後,沒有在同一個檔案裡找它的同類

- **發現於**:2026-08-15,票 33 的 ADR F-0015 做 C4 定性時。
- **現象**:`22-machine-recovery-drill.md:348` 是 F-082 修掉的那一行
  (真實備份資料夾名 → `<備份資料夾>`)。定性時發現
  **同一個檔案的 `:291` 是同一類字串,沒有被修** —— 隔 57 行,
  而且從 F-082 那天起一直在遠端上。登記為 K2。
- **成本**:目前是零(repo 仍私有),但它讓**階一「全樹掃描乾淨」不成立** ——
  而那個階段本來已經被當成過了。
- **根因**:修復的注意力停在**那一行**。
  F-082 已經立了「回頭重掃既有資料」,F-083 已經立了「同類入口在哪」,
  **而兩條都沒有涵蓋最近的那一圈** —— 同一個檔案內的同類。
  重掃靠的是偵測器,而偵測器打不中這一筆(見 K3 與缺口二);
  「同類入口」問的是規則側,不是資料側。**中間那一圈沒有人守。**
- **處置**:立原則(下方「可複用」),寫進 CLAUDE.md 常駐檢查項。
- **可複用**:
  - **命中修復後,搜尋半徑至少是「同檔同類」,再往外問跨檔家族。**
    順序是由近而遠 —— 最近的那一圈最容易被跳過,
    因為修的時候人就在那個檔案裡,**「我剛剛看過這個檔案」感覺像是查過了**。
  - 這一則與 F-082 / F-083 的分工:

    | | 問句 | 半徑 |
    |---|---|---|
    | **F-085(本則)** | 「**這個檔案裡還有幾個一樣的?**」 | 同檔 |
    | **F-082** | 「以前犯過幾次?」(全量重掃) | 全庫,靠偵測器 |
    | **F-083** | 「這個東西還有哪些同類?」(規則側) | 規則家族 |

  - **F-082 的重掃依賴偵測器,而偵測器可能正是打不中這一類的那個** ——
    K2 就是這樣活下來的:全量掃描回 0,因為沒有 pattern 打得中它。
    **同檔目視是唯一不依賴偵測器的那一圈**,所以它不能省。
  - 同族:改好一個 SQL 注入點沒看同檔其他查詢、修好一處 encoding
    沒看同檔其他 IO、補了一個 null check 沒看同一函式其他解參照。

- **根因**:**教訓被當成「這一次的修法」,而不是「一條掃描全庫的規則」。**
  F-082 說「修好偵測器之後回頭重掃**資料**」,F-083 說「回頭問**規則**的同類」,
  F-085 說「回頭看**同一個檔案**」—— 三條都沒有涵蓋這一格:
  **回頭問**隔壁的模組**有沒有同一個洞**。
  而這一格特別容易漏,因為 docstring 寫下來的那一刻,
  **感覺已經處理完了** —— 寫下判準的動作被誤認為套用判準的動作。
- **可複用**:
  - **在 docstring 或 log 裡命名一個缺陷族之後,立刻用那個名字全庫搜一次。**
    命名是為了讓它可搜尋;**只命名不搜尋,等於把索引建好然後不查**。
  - 具體查法:把判準裡出現的**受害字串**(這裡是 `skills/`、`/tmp`)
    當成 grep 目標,而不是把「邊界」這個概念當成 grep 目標 ——
    概念搜不到,字串搜得到。
  - 判準:**同一份判準寫在 A 模組的註解裡,不會讓 B 模組變安全。**
    註解不是機制。要嘛抽成共用函式,要嘛在每一處各補一條測試。

### 併記:**寫錯數字比沒寫更糟**

同一輪的另一則。F-082 回掃的第一版報告我寫成
「只活在歷史裡的 27」——查證後那 27 個是 **tree(目錄)**,不是消失的檔案;
只活在歷史裡的 blob 路徑其實是 **0**。

- **為什麼比沒寫更糟**:落地紀錄**會被引用**,而**引用的人不會回頭重驗**。
  「沒寫」會讓下一個人去量;「寫錯」會讓下一個人拿著錯的數字往下推 ——
  而錯誤在傳遞時**會失去它的出處**,於是沒有人知道該回頭查哪裡。
- **可複用**:
  - 報告裡的每一個數字,問一句:**它數的是什麼單位?**
    這一則的錯就是單位錯(物件 vs 檔案),不是算術錯 ——
    **算術錯會被看出來,單位錯不會**。
  - 凡是「N 個東西」的敘述,把 N 與**東西的型別**寫在一起
    (「39 blob + 27 tree」而不是「66 個」)。
  - 同族:把「命中數」寫成「有問題的檔案數」、把「掃描的檔案數」
    寫成「涵蓋的檔案數」、把「測試數」寫成「涵蓋率」。

## F-087 對封閉集合用 pattern —— 不是防線弱,是選錯工具

- **發現於**:2026-08-15,票 39 條件 2(入口面窮舉)補做身分欄位那一列。
- **現象**:把 86 個 commit 的 author/committer 共 **172 筆**物化成文字、
  走完整掃描管線(跳過清單未濾、審查白名單允許)—— **命中 0**。
  而那 3 個身分裡**有一個是真名 + 私人 gmail**,它就在那 172 筆裡。
- **原因**:通用與個人 pattern **都沒有「人名 / 私人信箱」這一類**。
  管線跑了、報告是零、東西還在那裡 —— 缺口二的形狀第三次出現。
- **根因**:**沒有先問這一面的集合是開放還是封閉。**
  身分欄位的集合是 `git log --format=%ae` 的值域 ——
  **封閉、可窮舉、而且極小(3)**。對這種集合寫 pattern,
  是拿一個為**開放集合**設計的工具去解一個**封閉集合**的問題。
- **處置**:驗收改用枚舉 —— 開刀後 `%an <%ae>` 與 `%cn <%ce>` 的聯集
  **必須只剩 `noreply` 那一種**。不加 email pattern。
- **可複用**:
  - **動手守一個面之前,先問:這一面的集合是開放還是封閉?**

    | | 開放集合 | 封閉且可窮舉 |
    |---|---|---|
    | 例 | 檔案內容裡的秘密 | commit 身分、ref 名稱、檔案模式位元、副檔名 |
    | 工具 | 比對(pattern / 熵) | **枚舉** |
    | 漏的性質 | **未知**(不知道自己漏了什麼) | **不存在**(全集就是那份清單) |

  - **比對的漏是未知的,枚舉的漏是不存在的。** 這是兩者不對稱的全部理由,
    而不是「枚舉比較嚴格」這種程度差異。
  - **對封閉集合用 pattern 不是防線弱,是選錯工具。**
    加強那條 pattern 不會讓它變對 —— 它會抓到全世界的 email,
    而真正要確認的是**這個 repo 裡只剩哪幾個**。
  - 判準句(同條):
    > **「沒有入口」與「我沒去造入口」是兩件事,而前者聽起來像事實。**

    本則的第一版把身分欄位標成「掃描器**無入口**」。那不是事實 ——
    入口是可以造的(把欄位物化成文字送進去就有了),
    只是**我沒去造**。用「無入口」描述,會讓一個**可以做而沒做**的事
    看起來像**做不到**,於是沒有人會再回來看它。

## F-088 判準錨在 `git show HEAD:`,而 gitlink 底下沒有那個物件

- **發現於**:2026-08-15,下游(量化)實測回報;落地於 agent-gates 票 41。
- **現象**:`data_collector` 是 submodule(gitlink,mode `160000`)。
  parent 的 `git cat-file blob HEAD:data_collector/<檔>` 回 fatal ⇒
  `head_content_hash` 回 `None` ⇒ `redlight_missing` 的**兩個**合格出口
  (`impl_exists is False` / `impl_hash == head`)對既有檔案同時走不到 ⇒
  **submodule 底下任何既有檔案永遠拿不到合格紅燈**。該處只因影子模式開著才沒被擋。
- **原因**:F-0013 把錨點放在 HEAD 是對的(時點不變),
  但它**假設 `git show HEAD:<路徑>` 對任何受版控的路徑都讀得到**。
  gitlink 那一格存的是一個 commit id,不是子樹 —— 沒有那個 blob 物件。
- **根因**:錨點選對了,**沒有問「這個錨點的取得方式有沒有取不到的合法情形」**。
  而且缺席是**無聲的**:`head_blob` 用同一個 `None` 表示
  「不在 HEAD(新建未提交)」與「問不到」,兩種意義擠在一個回傳值裡,
  於是規則看起來還在,實際上對整個 submodule 失效。
- **處置**:偵測 gitlink 前綴後委派 `git -C <submodule> cat-file blob HEAD:<相對路徑>`;
  委派後仍讀不到**維持 fail-closed**。gitlink 判定用 tree 的 mode 枚舉(`160000`),
  不讀 `.gitmodules`、不做 pattern 比對(F-087)。
- **可複用**:
  - **一個判準的錨點,要跟它的取得方式一起檢查。**
    「錨在 HEAD」是判準,「`git show HEAD:<路徑>`」是取得方式 ——
    前者正確不保證後者對每一種受版控的物件都成立。
    問法是列舉那個 API 的**回傳形態**(blob / tree / commit / symlink),
    不是問「這樣寫夠不夠嚴」。
  - **fail-closed 的缺陷是隱形的,而「隱形」正比於回傳值的多義程度。**
    `None` 同時表示「合法的不存在」與「問不到」時,後者永遠不會被查 ——
    因為前者是日常,而兩者長得一模一樣。
  - **判準寫「錨在 HEAD」的時候,HEAD 是誰的 HEAD 也要寫出來。**
    修法選 submodule 自己的 HEAD,不選 parent 記錄的 gitlink sha:
    紅燈紀錄的 hash 取自工作樹,工作樹跟著 submodule 的 HEAD 走,
    parent 的指標只在有人 bump 時才動 —— 拿它當錨會讓
    「submodule 內已提交、parent 還沒 bump」這個最常見的中間狀態永遠對不上。
  - 併記(範圍誠實,票 42 已收其中兩個入口):
    **權威層對 submodule 內 staged 檔案零涵蓋** ——
    parent 的 pre-commit 只列 parent 的索引,submodule 自己的 hook 只跑 `leak_scan`。
    本則修好之後,submodule 底下的 R3 仍然**只有前哨那一層**。
    這是下游 `data-collector-full-gate` 票的完成定義缺口,
    寫在這裡是為了讓它有出處 —— 屬於「可以做而沒做」,不是「沒有入口」(F-087)。

## F-089 mode 160000 在三個入口各被當成一次「檔案」,而三次都是無聲的

- **發現於**:2026-08-15,票 41(第一個入口)與票 42(第二、三個,下游實測回報)。
- **現象**:同一件事 —— **git 的 gitlink 那一格記的是 commit sha,沒有 blob** ——
  在三個判定裡各造成一次失效,而三次的表面症狀完全不同:

  | 入口 | 把 gitlink 讀成 | 後果 |
  |---|---|---|
  | `gate.head_blob`(R3 紅燈半) | 「HEAD 讀不到」 | submodule 底下**既有檔案永遠拿不到合格紅燈** |
  | `scanner.staged_paths`(leak_scan) | 「檔案內容讀不到」 | **bump 永遠擋下**(`open()` 得 PermissionError) |
  | `gate.staged_paths`(權威層) | 「一支沒有副檔名的原始碼」 | 前置站 bump 被 R2 當成「提交原始碼」擋下 |

- **原因**:三處都在問「這個**檔案**怎麼樣」,而那一格**不是檔案**。
  每一處的 fail-closed 方向都對(讀不到 → 擋),但**判定的對象錯了** ——
  於是產生**永遠無法滿足的條件**:使用者沒有任何合法動作能讓它變乾淨,
  因為沒有東西可以洗。這是 F-046 / F-0013 那個形狀的第三、四、五次。
- **可複用**:
  - **「沒有內容」與「內容讀不到」是兩件事,而它們共用同一個回傳值。**
    `None` / 例外同時表示「合法的不存在」與「問不到」時,前者是日常、後者永遠不會被查。
  - **判準句**:一條規則如果**沒有任何合法動作能滿足它**,那不是嚴格,是判錯對象。
    嚴格的規則有出口(去修好它);判錯對象的規則沒有。
  - **收了一個入口,就回頭問它的同類入口在哪**(CLAUDE.md 常駐檢查項)——
    這次是照著做才找到第三個:`staged_paths` 在本框架有**兩份實作**,
    下游只回報了 portable 那份,另一份在權威層。
    下游沒撞到它,只因為 hook 的順序是 `leak_scan || exit 1` 在前,**還沒走到 gate**。
    **「沒有人回報」不是「沒有問題」,可能只是前面那道先擋住了。**
  - 處置附帶:兩份實作**不共用程式碼**(一份隨 `.claude/hooks/` 安裝,
    一份屬 portable 掃描器骨架),所以加一條測試釘住兩者對同一個 repo 給出相同答案
    (`test_both_staged_listings_agree_on_a_gitlink`)——
    **同時修好不會自己維持下去**,漂開是無聲的(F-058 家族)。

## F-090 那個 fail-closed 分支從來沒有被走到過,而它前面的分支剛好蓋住了它

- **發現於**:2026-08-15,票 42 (b) 放寬第二格之後,負控當場變紅。
- **現象**:`gitlink_unsettled` 的第三態是「內嵌 repo 讀不到 → 當髒」,
  實作是 `git -C <內嵌路徑> rev-parse HEAD` 的退出碼。
  **git 找不到 repo 時會往上走** —— 它回答**外層** repo 的 HEAD 並回 0。
  那個分支的條件**永遠為假**,整格從來沒有被執行過。
- **為什麼一直沒被發現**:它被下一個分支遮著。舊版接著比
  `index_sha != inner_sha`,而逃到外層拿回來的 sha 幾乎必然不等於 index 記的,
  於是**照樣判髒** —— 結論對,理由錯。守著它的測試也綠 ——
  綠的原因是被遮蔽的那一格,不是它自己。
- **原因**:`git -C <路徑>` 不是「在這個 repo 裡執行」,是
  「**從這個路徑開始往上找 repo**」。把它當成前者,就等於假設
  「路徑底下沒有 repo」會變成一個錯誤 —— 而它會變成**另一個 repo 的正確答案**。
- **處置**:改問 git「你認為的工作樹根在哪」再確認那就是這個路徑本身
  (`rev-parse --show-toplevel` 與路徑比對)。
  **不改用 `os.path.exists('.git')`**:真正的 submodule 的 `.git` 是一個**檔案**
  (指向 `../.git/modules/…`),用 `isdir` 判會漏掉每一個標準 submodule ——
  而且那又是把判定交給檔案系統。
- **可複用**:
  - **一條 fail-closed 分支的價值,等於它被走到的次數乘以它擋對的比例。**
    從沒被走到的那條,價值是零,而它讀起來與有效的那條**一模一樣**。
  - **拿掉一個分支之前,先問它有沒有在遮著後面那一格。**
    放寬的當下是唯一會發現這件事的時機 —— 因為那正是遮蔽消失的一刻。
    這次是負控接住的;**沒有那條負控,這次放寬會靜默把整格變成 fail-open**。
  - 判準句:**綠燈要問「它綠的理由是不是我以為的那個」。**
    這與票 41 的 `rmtree(ignore_errors=True)` 是同一天的同一課
    (那條測試綠的理由是「`HEAD`/`config` 剛好可寫、被刪掉了」,
    不是「`.git` 真的不見了」)—— 兩者都是**測試對了、理由錯了**。
