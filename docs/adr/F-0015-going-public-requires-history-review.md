## 問題

這個 repo **原本就是為了公開而寫的**(`machine-init.md` 的紅線寫著這件事)。
但它的 71 個 commit 是在「私有」這個前提下長出來的:
路徑、資料夾名、機器名、個人習慣一路寫進去,沒有人在每一次 commit 時
用「這會被陌生人讀到」的標準看過。

已經有一個確認的實例:票 22 的演練文件把**真實備份資料夾名**寫進版控並推上遠端。
`git` 的性質決定了後果 —— **現在的樹乾淨,不代表歷史乾淨**;而
`git clone` 帶走的是歷史。

## 決定的形狀(這一段本身不是判斷題)

> **公開不是一個動作,是一道有前置條件的閘門。**

前置條件**按順序**,前一階不過就不談下一階:

| 階 | 條件 |
|---|---|
| 一 | **全樹掃描乾淨** —— 現在的 `HEAD` 樹 |
| 二 | **全歷史掃描乾淨** —— 所有 blob 版本 + 見下方「掃描面」判斷題 |
| 三 | 才討論**改寫要不要做**(改寫是手段,不是前置條件本身) |

順序不能倒:先討論改寫會變成「改寫完就算乾淨」,而改寫只處理**已經找到的東西**。

### 為什麼是「立門」而不是「現在洗」

與 TradingAgents ADR 0011 同一條不對稱:

- 保持私有、將來想公開 → 那時再做歷史審查,**成本可控**
- 先公開、之後發現有東西 → **收不回來**(clone、fork、快取、封存站)

**選擇要看不對稱,不是看機率。**

## 本檔最重要的一件事:閘門現在會給假綠燈

起草時把本 repo 的全歷史實際掃了一遍(376 個 blob 版本 + 71 則 commit 訊息)。
結果**不是**「乾淨」,也不是「找到東西」,而是第三種:

> **掃描回報 42 筆命中,全部是掃描器掃到自己;
> 而我們已經知道存在的那一筆,一條都沒掃到。**

三個數字都量過(方法見下方各節):

| 量到的 | 值 |
|---|---|
| 全歷史命中 | 42 |
| 其中是 `leak_scan.py` / `leak-patterns.txt` 自己的歷史版本 | **42(100%)** |
| 已知項(`#16` 的資料夾名)被掃到 | **0** |

所以**照票面直接執行「全歷史掃描乾淨」這個條件,結果會是:
一堆雜訊、然後在人工排除雜訊之後回報「乾淨」—— 而那句乾淨是假的。**

這與 F-082 是同一個形狀,只是升了一層:那次是**資料**遮一半騙過比對,
這次是**閘門本身**看起來在跑、實際上守不到它宣稱守的東西。

下面三節各講一個成因,每一個都附判斷題。

## 缺口一:自我豁免是**路徑判定**,而歷史裡有很多份

`leak_scan` 用 `SELF_PATHS` 把掃描器自己排除掉:

```
SELF_PATHS = ('.claude/portable/leak_scan.py', '.claude/portable/leak-patterns.txt')
```

理由是對的 —— pattern 檔的工作**就是**列出秘密的形狀,掃它必然全中。

但那是**工作樹**的路徑。歷史裡同一個檔案有 N 個版本,還原之後路徑是
`<sha7>/.claude/portable/leak_scan.py`,**不等於**清單裡那一條,於是自我豁免整條失效。
量到的 42 筆全部由此而來,分佈在三條憑證副檔名 pattern 上(25 / 11 / 6)——
命中的都是 `leak_scan.py` **註解裡在解釋憑證判定**的那幾行。

### 活標本:這一段自己撞上了它在描述的東西

本檔第一版把那三條 pattern 的原文寫進上面那一行。`leak_scan` 擋下了它:

```
docs/adr/F-0015-…md:82
     命中 pattern:(三條憑證副檔名)
     內容:***整行已遮罩(同一行 3 條命中,分段遮罩可拼回)***
```

**擋得對。** 一份講「掃描器掃到自己」的文件,本身就是同一類檔案 ——
它列出秘密的形狀,於是必然全中。處置是**改寫這一行、不加豁免**:
文件不需要那三個字面值,寫「三條憑證副檔名 pattern」意思一樣。

順帶量到票 32 的整行遮蔽在真實情境下運作:同一行 3 條命中 → 整行遮掉,
而不是遮三段讓人拼回去。

這一則是判斷題 1 的實證:**豁免一旦按名字給,新的同類檔案就拿不到** ——
而這份 ADR 正是一個新的同類檔案。

**判斷題 1:歷史掃描的自我豁免怎麼判?**

| | 做法 | 差別 |
|---|---|---|
| **A** | 用**歷史路徑**判自我豁免(還原時把歷史路徑帶著,比對時剝掉 sha 前綴) | 報告乾淨,42 筆雜訊消失。代價:**豁免範圍變大了** —— 歷史上任何時期叫這個名字的檔案都免掃,包含它還不是掃描器的時期 |
| **B** | 歷史掃描**不做**自我豁免,42 筆登記為「已知良性」 | 沒有新豁免,而且下次數字變成 43 時會被看見。代價:每次審查都要對 42 筆做一次比對,人會開始略過它 |

**這題的實質是:雜訊與豁免哪一個先殺死這道閘門。** A 的風險是靜默的,
B 的風險是吵鬧的 —— 而本 repo 一路的判準是**寧可吵鬧**(ADR 0003)。
但 B 有一個 A 沒有的問題:42 這個數字**會隨著歷史增長**,而「登記已知良性」
的清單一旦超過人願意讀的長度,它就等於 A 了,只是多花了時間。

### 裁決:**B + 聚合**

不做自我豁免。已知良性登記表**按「歷史路徑 × pattern 類」聚合**,不逐筆記:

```
.claude/portable/leak_scan.py        憑證副檔名 pattern   39
.claude/portable/leak-patterns.txt   憑證副檔名 pattern    3
```

**兩行,而且不隨歷史成長** —— 再加一百個版本仍是兩行。
B 原本那個「清單長到沒人讀」的代價因此消失,而 B 的好處留著:
**新出現的第三類會是新的一行**,A 則會靜靜吞掉它。

聚合鍵刻意是「歷史路徑」而不是 sha:sha 會變(見 Q3 開刀),路徑不會。

## 缺口二:個人 pattern **綁機器**,而缺一條是**完全無聲**的

`leak_scan` 的涵蓋是兩組的聯集:

- **通用**:`.claude/portable/leak-patterns.txt`(進版控,10 條)
- **個人**:`~/.claude/leak-patterns.local.txt`(**不進版控**,這台 16 條)

個人清單刻意不進版控 —— 它本身就是秘密(使用者名稱、資料夾名、往來對象)。
代價是它**跟著機器走**。

而這正是已知項掃不到的原因。實測(三種方法各一次,結論一致):

```
scan_paths(e34ce21 刪掉的那一行)            -> 命中 0
通用組 10 條 pattern 逐條比對那一行          -> 0 條打中
個人組 16 條 pattern 逐條比對那一行          -> 0 條打中
```

F-082 說那個資料夾名是「新 pattern 回頭照出來的」。**那條新 pattern 不在這台機器上。**
發現它的是演練那台(筆電),而個人清單不同步。

**leak_scan 只在個人清單「整份不存在」時警告,清單存在但少幾條時什麼都不說。**
於是「有跑掃描」與「涵蓋完整」被混為一談 —— 而報告上兩者長得一模一樣。

### 更正(起草後查證):搬運機制**已經存在**,壞掉的是別的東西

第一版把這一節寫成「個人清單沒有搬運方案」。**那是錯的。**
`.agents/user-layer-manifest.txt:51` 早就有:

```
leak-patterns.local.txt         age!
```

票 22 建的 `user_layer.py export --recipient` 會把它**加密後帶走**,
`!` 還額外標了「搬完要回頭看」。所以問題不是「搬不過去」——

> **搬得過去,但兩台的清單各自長了,而沒有任何東西在比對它們。**

`age!` 的 `!` 要求的正是人回頭看一眼,而那一眼**沒有攔住這次** ——
因為新 pattern 是在演練**之後**才加到筆電上的,匯出當下它還不存在。
**單次搬運的檢查點,擋不住搬運之後才發生的分歧。**

**判斷題 2:審查時怎麼保證個人清單是完整的?**

| | 做法 | 差別 |
|---|---|---|
| **A** | 規定審查只能在**指定那台**機器上跑 | 最省事。代價:賭那台機器與那份清單都在,而票 22 整張票就是在防這件事 |
| **B** | 審查前先做一次**清單對帳**:兩台各出一份「條數 + 每條的雜湊」(不出原文)比對,不一致就先合併 | 直接打在成因上。代價:要有第二台在手,而換機器演練的前提正是「可能只剩一台」 |
| **C** | 不管清單怎麼同步,審查**必須先跑一次「已知項回歸」**:拿登記表每一筆去掃,掃不到就 refuse | 不解決分歧,但讓「涵蓋不足」**出聲**。代價:只保得住已經登記的那些 |

**A 與 B 是同步/對帳方案,C 是偵測方案 —— 不互斥。**
本檔傾向把 C 當**必要條件**(它是唯一能讓「假綠燈」出聲的),
A/B 則是另一個決定。理由:C 之外的組合都有同一個性質 ——
**當它們失效時,報告仍然是綠的**。

而 C 有一個 A/B 都沒有的性質:**它不要求清單完整,只要求清單能證明自己
守得住已知的那些。** 這正是本次的失效點 —— 涵蓋不足,而報告全綠。

### 裁決:**C 為必要條件,B 並行且不阻塞,A 排除**

- **C(已知項回歸)是必要條件**:登記表每一筆都要能被當時的掃描器打中,
  打不到就 **refuse**,不是警告。理由是它是唯一「失效時會出聲」的。
- **B(清單對帳)並行**:兩台各出「條數 + 每條雜湊」(**不出原文**)比對。
  它打在成因上,但**不擋 C** —— 只剩一台時 C 照跑。
- **A 排除**:把審查綁在特定機器上,與票 22 的整個立場相反。

**C 依賴 Q6-C** —— 回歸要跑,登記表就必須是一份機器讀得到的獨立檔,
而不是散在 ADR 散文裡的表格。這條依賴是裁決的一部分,不是實作細節。

#### C 與藏寶圖條款的時序張力(必須寫下來)

C 要求「拿登記表每一筆去掃,**掃得到**才放行」——
而 Q6 的藏寶圖條款要求「公開前那些內容**已經清除或泛化**」。
**清完之後就掃不到了**,C 照字面會永遠 refuse。

所以 C 的判準**隨階段換邊**,而換邊的時點就是那一筆被清掉的時候:

| 該筆狀態 | C 要驗的 |
|---|---|
| 未清除 | 掃**得**到 —— 證明掃描器涵蓋守得住它 |
| 已清除 / 已泛化 | 掃**不**到 —— 證明它真的不在歷史裡了 |

兩邊都是 fail-closed:**登記表的每一筆在任何時點都有一個明確的期望值**,
而「說不出期望值」本身就是 refuse 的理由。

## 缺口三:blob 不是全部 —— commit 訊息與身分欄位不在裡面

「全歷史掃描」如果指的是 blob,那它看不到:

| 面 | 為什麼看不到 | 本 repo 實測 |
|---|---|---|
| **commit 訊息** | 存在 commit 物件裡,不是 blob | 71 則。粗篩:1 則含絕對路徑(是 `C:\Users\fake\…` 佔位符)、1 則含 `OneDrive` 字樣(是**描述** F-082 事件那則) |
| **author / committer 姓名與 email** | commit 物件的欄位,連訊息都不是 | **3 個身分**,其中一個是**真實姓名 + 私人 gmail** |
| **路徑名本身** | 存在 tree 物件裡 | 147 條路徑曾經存在,現在 144 條 —— **3 條只活在歷史裡** |
| **tag / notes / reflog** | 各自獨立的物件 | 本 repo 目前無 tag、無 notes |

本 repo 的實測掃描(見上)**已經**把 commit 訊息納入了(還原成 `.txt` 一起掃),
身分欄位則是另外列出來的 —— 因為它根本不是文字檔,掃描器沒有它的入口。

**判斷題 3:身分欄位怎麼處理?**

| | 做法 | 差別 |
|---|---|---|
| **A** | 接受。真名 + gmail 是公開 repo 的常態 | 零成本。代價:那是**個資**,而且是不可撤回的 —— 一旦公開,鏡像站會保存 |
| **B** | 轉公開前用 `git filter-repo` 把身分改成 GitHub 的 `noreply` | 個資移除。代價:**所有 commit sha 全變** —— 而本 repo 到處引用 sha(legacy 名單的 `# go-live:`、provenance、票裡的 `@ 3a265f2`、ADR 互引)。這是一次**跨整個 repo 的參照失效** |
| **C** | 現在起改用 `noreply`,歷史不動 | 止血但不清創。歷史裡的舊 commit 仍有真名 |

**B 的代價比看起來大得多。** `.agents/legacy-no-redlight.txt` 的入場券是
「在機制上線那個 commit 的樹裡」—— 改寫歷史會讓那個 sha 不存在,
而**那份名單是 gitignore 的、重新產生時會拿當下的樹**,於是名單可能整個變形。
這件事必須在做 B 之前先量,不能在做完之後才發現。

### 裁決:**分兩段(調停案)—— 立刻止血,單次開刀**

不選 A/B/C 任一項。理由是三個選項共用一個錯誤前提:
**把「止血」與「清創」當成同一個決定。** 拆開之後兩邊都變便宜。

#### 第一段:立刻(不等審計)

| # | 動作 | 為什麼是「立刻」 |
|---|---|---|
| ① | **凍結下游 sync** —— B 完成前,量化 / 影音**不跑 sync** | 下游 provenance 記的是**上游 sha**。多一個下游同步過,開刀的代價就跳一階,**而且那一階是跨 repo、事後修不動的** |
| ② | **兩台的 git 設定改 `noreply`** | 止血。從此不再產生新的個資 commit,與開刀是否發生無關 |
| ③ | **帶日期的 zip 備份** | 開刀是不可逆的。備份不是為了回滾決定,是為了**回得去原始事實**(登記表的每一筆都要能複驗) |

①的順序性要講白:**它不是準備工作,它是一道閘門。**
開刀的成本由「已同步的下游數」決定,而那個數只增不減。

#### 第二段:開刀 —— `filter-repo` **只跑一次**

> **等定性完成 + Gemini 審計完成,把身分欄位與所有裁定要清的歷史項
> 併進同一刀。死線 = 公開前。**

「只跑一次」是這一段的核心約束,不是效率考量:

- 每跑一次,**所有 sha 全變**,而 sha 是本 repo 大量交叉引用的錨點
  (`# go-live:`、provenance、票與 ADR 的散文引用)。跑兩次就要**修兩次**,
  而第二次修的時候第一次的對照表已經沒人記得
- 更要緊的:**每跑一次就多一組舊物件留在遠端與既有 clone 裡**。
  改寫不會回收已經發布的物件,只會讓新的 clone 拿不到 ——
  跑兩次等於**在外面留兩份不同的舊歷史**

所以順序是強制的:**先把要清的東西全部找齊(定性 + 審計),再動刀。**
先動刀會變成「刀下去之後才想到還有一項」,而那時只剩下第二刀。

開刀前要量的清單見下方專節 —— 那些數字現在就量得到,不必等審計。

**判斷題 4:tree 裡的路徑名要不要當成掃描面?**

3 條只活在歷史裡的路徑(兩份 ADR 改名前的檔名、一個併回去的測試檔名)
本身沒有敏感內容。但**F-082 那一筆洩的就是一個「名字」** ——
只是它剛好寫在檔案內容裡,而不是檔名裡。

- **A**:把全歷史路徑清單也丟給同一組 pattern 掃
- **B**:不掃,理由是檔名由開發者命名、不會是外部秘密

差別在於:A 多一次幾乎零成本的掃描(147 條字串);
B 賭的是「敏感的東西不會被拿來當檔名」—— 而演練那次證明了**敏感的東西會被拿來當資料夾名**。

### 裁決:**A**

全歷史路徑清單(147 條)也丟給同一組 pattern。
B 賭的那件事**已經發生過一次**,而 A 的成本是 147 條字串跑一次正則。

### C10 要單獨講:跳過不等於乾淨

`SKIP_SUFFIX` 讓 `.zip`、`.pdf`、圖片整個不掃 —— 在 pre-commit 那個情境是對的
(掃二進位必然是雜訊)。但**公開審查的問題不一樣**:那裡「沒掃」與「掃過沒事」
不能混為一談。本 repo 歷史裡剛好 0 個這種檔,所以**這次沒有代價**;
但這是運氣,不是設計。

**判斷題 5:審查時二進位怎麼辦?**

- **A**:沿用 `SKIP_SUFFIX`,並在報告上**列出被跳過的清單**(數量 + 路徑)
- **B**:審查模式不跳過,對二進位改用別的判準(副檔名、大小、熵)

差別:A 把判斷交還給人,但人要真的去看那份清單;
B 不依賴人,但會產生大量無法判定的命中。
**A 的關鍵是那份清單必須是報告的一部分,不是選項** —— 否則就退化成靜默跳過。

### 裁決:**A,而且「被跳過的清單」是報告的必要部分**

沿用 `SKIP_SUFFIX`。但**報告缺了那份清單就不是一份合格的報告** ——
不是「建議附上」,是**沒有它就不算跑過**。

差別在誰負舉證責任:清單在,人看到「跳過 3 個 zip」會去想那三個是什麼;
清單不在,「跳過」這件事根本不存在於報告上,於是等同沒發生。
本 repo 目前這份清單是**空的**(歷史裡 0 個二進位)——
**空清單也要印出來**,因為「印出來是空的」與「沒印」是兩件事。

## 已知項登記表

**格式刻意只記「sha + 類別 + 現況」,不記字串本身。**
理由與個人 pattern 不進版控同一條:清單本身列的就是它要保護的東西。

| # | commit | 類別 | 範圍(實測) | 現況 |
|---|---|---|---|---|
| K1 | `3a265f2` | 個人資料夾名(C3) | 全歷史**僅此 1 個 blob 版本**;該檔另有 7 個版本不含 | 現樹已修正(`e34ce21`),歷史仍在 |

K1 的範圍是量出來的,不是估的:該檔在歷史裡 8 個版本,逐一比對後只有一個含那一行;
全歷史 376 個 blob 版本裡也只有那一個。**登記一個 sha 是準確的,不是簡化。**

**判斷題 6:登記表放哪?**

- **A**:放本 ADR 裡(現在這樣)—— 跟決定同一個檔,不會走失
- **B**:放獨立檔並 gitignore —— 但那樣它**不進版控**,換台機器就沒了,
  而票 22 的整個教訓就是「不在版控裡的東西會消失」
- **C**:放獨立檔、進版控、內容照本格式(不含字串)

差別只在**它會不會跟著 repo 走**。A 與 C 都會;B 不會。
A 與 C 的差別是:登記表會成長,而 ADR 的性質是「決定寫下來就不太動」。

### 裁決:**C**,登記表移到 `docs/going-public-known-items.md`

本 ADR 從此**定義格式**,不承載資料。理由是兩者的變動節奏不同:
混在一起會養出「不敢改 ADR」或「習慣 ADR 會變」——**兩個都是壞習慣,
而且是同一個檔案養出來的**。上面 K1 那張表保留為格式範例(F-036)。

#### 藏寶圖條款

> **公開前,登記表各筆對應的內容必須已清除或泛化。**

登記表即使不含字串,它仍然是一張**藏寶圖**:它告訴讀者
「`3a265f2` 這個 commit 的某一行是個人資料夾名」。對想找東西的人來說,
**縮小搜尋範圍就是主要的價值** —— 從 376 個 blob 版本縮到 1 個。

所以登記表與公開**不能並存**在「內容還在」的狀態。兩條出路:

- **清除**:那一筆的內容不在歷史裡了(開刀處理)
- **泛化**:內容改寫成不具識別性的形式,登記表指過去也問不出東西

這一條與 Q2-C 的時序張力已在上面寫明:**清除前後,C 要驗的方向相反。**

## 掃描要用**當時**的上游 `leak_scan`

票面這一條的理由:規則會長。用寫 ADR 時的版本掃,等於用 2026-08 的涵蓋
去審一個 2027 才公開的 repo。

但這裡有一個起草時才看見的皺褶:**本檔上面所有「✅ 已量」的數字,
用的就是今天的版本。** 它們是**現況快照,不是驗收結果** ——
真的要公開時得重跑,而且屆時的數字可能不同(pattern 變多 → 命中變多)。

**這不是缺陷,是這份清單的正確讀法**:它告訴你**哪些類別已經有入口**、
哪些還沒有(C9 就沒有),不告訴你「repo 是乾淨的」。

**判斷題 7:如果當時的上游版本比現在**少**守一條呢?**

- **A**:規定用「當時的上游」,信任規則只會長不會縮
- **B**:規定用「當時的上游 **∪** 本 ADR 記載的類別」,少掉的類別要補回來

差別在於有沒有假設「規則單調成長」。ADR 0003 記著三次 fail-open 都源自
某種形式的「預設它有涵蓋」。

### 裁決:**B**

用「當時的上游 **∪** 本 ADR 記載的 C1–C12」。少掉的類別要補回來並說明。

多的那道步驟只有 12 行,而它擋的是「掃描器退化而沒人發現」——
**而且現在就有一個成立的實例**:C9(內網主機名)在通用清單裡根本沒有
對應 pattern。即使今天就公開,A 也會漏掉一整類。

# 妥協聲明(定稿,2026-08-15)

回件 4.2 條件 3 要求**於 ADR 中明確宣告**。以下為定稿全文。

## 一、核心宣告(回件原句)

> **本機制不防禦刻意混淆(如 Base64 隱藏、字串分割拼接),
> 僅防禦開發過程之意外洩漏。**

劃定這條防線的理由**不是能力不足,是收斂性** ——
追求「100% 絕對涵蓋」會讓整理作業無限延宕,而**無限延宕的清理等於不清理**。

## 二、防禦範圍:**逐項列舉,不用「等等」**

「等等」會讓讀的人自行補完,而每個人補的都不一樣。

### 已防禦(每一項都有常駐測試)

| 形式 | 測試 |
|---|---|
| 明文(未經任何變形) | 通用 + 個人 pattern |
| NFKC 相容性差異(全形、連字) | `test_scanner.py` |
| 零寬字元(ZWSP / ZWJ / ZWNJ / U+FEFF) | `test_scanner.py` |
| 大小寫(含 Unicode 大小寫映射) | `test_scanner.py` |
| **路徑分隔符重複**(JSON 跳脫的 `\\`) | `test_known_items_regression.py` |

### **不**防禦

| 形式 | 說明 |
|---|---|
| URL 編碼(`%5C`)、雙重編碼 | 有常駐反控釘住 |
| Base64、Quoted-Printable、HTML entity | |
| **字串分段 / 串接**(重組後才是秘密) | 需資料流分析,超出正則的能力 |
| **同形字**(西里爾 / 希臘 / NFC-NFD) | **NFKC 折不動它** —— 需 TR39 confusables 表 |
| shell · regex · YAML · Markdown 的其他跳脫語法 | |
| 高熵值偵測(無特徵的隨機字串) | 由第二引擎 `gitleaks` 承擔,自家引擎不做 |

> **「分隔符重複」被涵蓋,不等於「跳脫形式」整族被涵蓋。**
> 差一個量詞,而讀的人會自動把後者讀成前者 —— 所以寫死在這裡。

## 三、掃描面的明文排除(分格版)

驗收範圍 = **「push 會帶走的」有限清單**。以下**明文排除**:

| 排除項 | 理由 |
|---|---|
| `reflog` | **push 不傳輸** |
| `refs/stash` | **push 不傳輸** |
| `.git/config`、`.git/hooks`、`.git/info/exclude` | **push 不傳輸** |
| 偽 ref(`FETCH_HEAD`、`ORIG_HEAD`…) | **push 不傳輸**,且非物件圖的一部分 |
| xattr / ADS | **git 不傳輸**檔案的擴充屬性 |

以上五項歸**本機衛生**,不是公開審查的對象。
**明文寫出來,是為了讓「沒查」與「查過沒事」在報告上分得開。**

## 四、接受的殘留風險

| 風險 | 決定 |
|---|---|
| **時間戳與時區**(`+0800`,可推斷作息與大致地理位置) | **接受** —— 改寫會讓整段歷史失去時序意義,代價大於收益 |
| **個人 pattern 清單綁機器**,少幾條完全無聲 | 以**已知項回歸**(Q2-C)偵測,而非以完整性假設迴避 |
| `filter-repo` **不回收已發布的物件** | 只讓新 clone 拿不到;既有 clone / fork 不受影響。**這正是排在「公開前」而非「公開後補救」的理由** |

## 五、引擎與版本(驗收要說得出用的是哪一個)

| 引擎 | 版本 | 來源 |
|---|---|---|
| 自家 `leak_scan` | 本 repo `HEAD` 當時的版本 | 審查模式 `--review` |
| `gitleaks` | **v8.30.1** | GitHub 官方 release,sha256 逐字驗過 |
| `git-filter-repo` | **2.47.0** | PyPI |

> **「雙引擎共識」若說不出版本,就是一句沒有內容的話。**

## 六、這份聲明的**失效條件**

聲明會過期。以下任一發生,**本節必須重寫**,不得沿用:

- 掃描器擴張到任何「不防禦」欄的形式 —— **對應的常駐反控會先變紅**
- 引擎版本更換
- 新增任何掃描面(軸一新增一列)
- 已知項登記表新增一筆

**每一條失效條件都對應一個會出聲的機制**,而不是靠人記得回來看。
