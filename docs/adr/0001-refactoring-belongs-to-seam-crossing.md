# ADR 0001:重構歸屬以「是否跨越接縫」劃分

- 狀態:已採納
- 日期:2026-08-09
- 追記說明:此決定在採用官方 skills 當下就已拍板,ADR 為事後補記(編號 0001,因為它是第一次覆寫上游)。

## 背景

上游 `tdd` skill 明寫:「Refactoring is not part of the loop. It belongs to the review stage」——
重構完全不在紅綠燈迴圈內,一律留給 review 階段。

傳統 TDD 教科書則是紅→綠→重構三步一體。兩者衝突,必須擇一,否則實作站的行為會隨當下心情擺盪。

## 決定

**不完全照上游,以「是否跨越本票宣告的接縫」劃分:**

- **跨越接縫的重構** → 不在紅綠燈迴圈內做,留給 `/code-review` 與 `/improve-codebase-architecture`
- **不跨接縫的重構**(改名、抽本地 helper、消除剛剛製造出來的重複)→ 留在紅綠燈迴圈內

## 理由

上游把重構整包移出迴圈,是為了讓 implement 站保持單純快速,並讓重構在有完整視野時才做。
這對跨模組的結構性重構成立;但對「剛寫完三行、發現有重複」這種局部整理,
強制留到 review 反而會累積一批瑣碎債務,而且那時已經失去當下的上下文。

以接縫為界的好處是它與測試邊界一致:不跨接縫的重構,現有測試就是安全網,當場做最安全;
跨接縫的重構會動到測試本身該測什麼,那才需要完整視野。

## 後果

- `CLAUDE.md` 需明列此規則(已列於「重構歸屬」節)
- implement 站的行為與上游 `tdd` skill 的文字有出入,採用者需知道這是刻意的
- 接縫必須在 spec/ticket 階段就談定,否則「是否跨越接縫」無從判斷 ——
  這也是 `/to-spec` 要求逐一確認接縫的原因
