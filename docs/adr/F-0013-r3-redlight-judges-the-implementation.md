# 0013 — R3 的紅燈半判定「實作」,不是「檔案」

**日期**:2026-08-12
**狀態**:已採用
**取代**:不取代 0006,而是把 0006 的豁免從「唯一出口」降級為「不再需要的出口」

## 背景:一個實測出來的死結

在 agent-gates 本身跑:

```
redlight_missing("edit_result") = None(合格)
redlight_missing("gate")        = 不合格 …「沒有任何一筆是紅燈且當時實作不存在」
```

同一次執行、同一份紀錄檔、同一輪紅燈。差別只在 `find_implementation()`
找不找得到實作檔:`edit_result.py` 不存在 → `impl_exists: false` → 合格;
`gate.py` 存在 → `impl_exists: true` → **永遠**不合格。

規則要問的是「**這個實作**寫之前,測試紅過嗎」,
它量的是「**這個檔案**當時存不存在」。

新檔案兩者重合;既有檔案永遠分岔。後果是:

- 每一支既有 `.py` 的紅燈先行**在機制上寫不出來** —— 不是難,是不可能
- 唯一出口是 `legacy-no-redlight.txt`,而那是把 R3 從那些檔案上**整條移開**
- 於是規則最嚴的地方是新程式碼(風險最低),最鬆的地方是既有判定核心(風險最高)

`tests/test_gate.py` 裡早就寫下了這個觀察的一半:
「合格紅燈要求紀錄當下實作不存在,而檔案還在就產不出那種紀錄 —— 清單因此接近永久。」
當時的結論是接受清單永久化;本 ADR 的結論是**判準本身問錯了對象**。

這與 F-046(R8 解析編輯片段而不是編輯後的結果)是同一個形狀:
**fail-closed 只保證失敗的方向,不保證問對了問題。** 同一輪撞到第二次。

## 決定

合格的紅燈紀錄 = 紅燈 **且** 屬於當前這張票 **且**(實作當時不存在
**或** 紅燈是對著這支檔案**在 HEAD 的內容**發生的)。

### 為什麼錨定 HEAD,不是磁碟現況

判準必須**時點不變**。前哨評估時檔案還沒被寫,提交時已經被寫 ——
拿磁碟現況當錨,同一筆紀錄在兩個時點會得到相反的答案,而
「權威層比前哨鬆」就是缺陷(F-017 的形狀)。HEAD 在這兩個時點都沒動。

### 為什麼一定要票號

`impl_hash == HEAD` 單獨用,會把方向從「永遠不合格」翻成「**永遠合格**」:
一筆三個月前的紅燈,只要該檔案自那次之後沒被提交過,就永久解鎖後續每一次修改。
票號讓紅燈有時效 —— 每張票要有自己的紅燈。

### 自我服務的路徑被關住了

唯一可能的偽造是「先寫實作、再補跑紅燈」。那樣產生的紀錄,`impl_hash`
是改動**後**的內容,對不上 HEAD,擋。這與 0006 選擇凍結清單的理由同源:
豁免條件必須是無法自我服務的。

### 行尾正規化

雜湊在計算前把 `\r\n` / `\r` 正規化成 `\n`。理由是這個值要跟 git blob 比對,
而 `core.autocrlf=true` 的 Windows 上工作樹與 blob 的位元組不同。
本 repo 目前靠 `.gitattributes` 的 `*.py text eol=lf` 讓兩者相同,
但**那個檔案不在 portable-manifest 裡**,不保證跟著裝到別的 repo。
少了它,兩邊 hash 永遠對不上 → R3 對每一支既有檔案無條件擋:
方向是 fail-closed,擋的卻是做對事的人,而那種規則最後會被整條關掉。
判準不掛在一個沒被宣告帶走的檔案上。

## 分時點語意(已宣告)

提交時 `ticket_id` 已清空(一輪做完站別會往前走),因此**提交時不比對票號**。
已登記在 `gate.RULE_DIVERGENCE["R3"]`。

實質保證在兩個時點相同:都要求「紅燈發生在這次改動之前」(HEAD 雜湊那一半)。
提交時少的只是「屬於哪一張票」這個歸屬,不是紅燈本身。

## 後果

- 既有檔案第一次做得到紅燈先行 —— 對每個裝了本框架的 repo 都成立
- `legacy-no-redlight.txt` 不再是既有檔案的唯一出口。本 repo 因此**不建立**它
- 舊紀錄沒有 `ticket_id`,一律不合格(fail-closed)。跑一次測試就會長出新紀錄
- 紅燈的粒度仍然是**檔案**,不是行為:同一支檔案在同一張票內的第二次修改,
  沿用同一條紅燈。要縮到行為粒度需要另一個機制,本 ADR 不處理

## 殘留

`.gitattributes` 不在 portable-manifest 裡。正規化讓 R3 不再依賴它,
但別的地方可能依賴 —— 該獨立盤點。

**這個決定當時就已經不可行,只是沒被發現。**

`check_legacy_list()` 對「清單檔不存在」是 fail-closed(回一項違規),
而它**自根 commit `5180678` 起就存在、無條件掛在 pre-commit 路徑上**,
從未修改過。本 ADR 寫於 2026-08-13 10:06,比那個要求晚了兩天。

兩者的差別不是措辭:前者代表世界變了,後者代表當時的檢查沒做完 ——
只有後者能讓下一次少犯一次。

### 為什麼兩天沒有人發現

因為那項違規**從來沒有擋過任何一次 commit**:agent-gates 的
`.git/hooks/pre-commit` 只接了 `leak_scan`,沒有接 `gate.py --pre-commit`
(見票 27)。手動呼叫 `gate.py --pre-commit` 會看到它擋 ——
但**手動呼叫一支檢查,不等於那支檢查在通行路上**。

唯一的訊號是 `tests/test_gate.py` 的 4 條紅,而它們混在既有的
skip/xfail 裡,沒有東西指出「這 4 條紅代表權威層對本 repo 是壞的」。

### 現行決定(票 26)

本 repo **建立**它,10 筆,`# go-live: 5180678`,由生成器產出。
三條理由:

1. **對守衛檔要求「出生前紅燈」等於要求不可能的歷史。** 那 10 支在根 commit
   的樹裡就存在,而該測試的排水判定只認「紅燈時實作不存在」——
   它們永遠排不掉。與 F-0014「上游自己做不到的紀律不得要求」同尺。
2. **零筆會造成永久紅**,F-031 / F-071 明文禁止:永遠紅的測試會教人
   「這套測試本來就紅」,然後整套被忽略。
3. 三個減輕因素:只豁免 R3 **後半**(前半「對應測試檔須存在」照常適用);
   清單**只減不增**且凍結於 `5180678`,排水方向是移除;
   這 10 筆正是 `install.py` 對任何目標 repo 都會生成的標準產物 ——
   建立它等於 agent-gates 終於自己吃自己的狗糧(ADR 0010 的自我治理實踐)。

## 補訂(票 41,2026-08-15):錨點對,取得方式有洞

本 ADR 的判準(錨在 HEAD,因為時點不變)不變,**取得方式**補一條:

本 ADR 假設 `git show HEAD:<路徑>` 對任何受版控的路徑都讀得到。
**gitlink(submodule,mode `160000`)不成立** —— parent 的樹在那一格存的是
一個 commit id,不是子樹,沒有那個 blob 物件。於是 `head_content_hash` 回 `None`,
而上面那條「合格 = 實作當時不存在 **或** impl_hash == HEAD」的**兩個出口對
submodule 底下的既有檔案同時走不到**:永遠不合格,唯一出口 legacy 清單
只減不增且入場券綁 parent 的樹 —— 也就是沒有出口。

這與本 ADR 開頭那個死結是**同一個形狀的第二次**:方向 fail-closed 沒錯,
擋的卻是做對事的人。下游(量化)實測到,而該處只因影子模式開著才沒被擋。

處置:`head_blob` 偵測 gitlink 前綴後委派
`git -C <submodule> cat-file blob HEAD:<相對路徑>`;
**委派後仍讀不到維持 fail-closed**。判定 gitlink 用 tree 的 mode 枚舉,不讀
`.gitmodules`(mode 是 git 自己的權威)。錨點是 **submodule 自己的 HEAD**,
不是 parent 記錄的 gitlink sha —— 理由見票 41 與 F-088。

範圍誠實:這一補訂只修**判定**。**權威層對 submodule 內 staged 檔案零涵蓋**
(parent 的 pre-commit 只列 parent 的索引),所以 submodule 底下的 R3
仍然只有前哨那一層 —— 那是下游票的缺口,不是本 ADR 的。
