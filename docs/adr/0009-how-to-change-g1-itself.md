# ADR 0009 — 改 G1 自己的流程:草稿在專案內、覆蓋只有人能做

日期:2026-08-10
狀態:已採納

## 背景

G1(`~/.claude/hooks/g1_guard.py`)把自己與保護清單都列在保護清單裡,
所以 agent 改不動它 —— 那是設計要的(「豁免來源不可自我服務」的同一個遞迴)。

但「改不動」不等於「不用改」。需要一條**人在迴圈裡**的流程,
而且這條流程本身要寫在檔案裡:只活在對話裡的約定,下一個 session 就沒了。
F-006 量化過那個成本 —— 光是「FRED 在哪」這一件事,每個新 session 要重付四輪搜尋。

## 流程

| 步驟 | 誰做 | 內容 |
|---|---|---|
| 1 | agent | 在**專案內**改 `.claude/portable/g1_guard.py`,**不碰 `~/.claude/hooks/` 底下任何東西** |
| 2 | agent | 跑 G1 那 18 條驗收。**草稿必須全綠才交件**;交件附 **diff**,不是整份檔案 |
| 3 | **人** | 備份現行版本為 `g1_guard.py.working`,再把專案內那份**複製**(`cp`,**不是 `mv`**)覆蓋過去。**覆蓋後跑 `git status`,確認 repo 正本沒有變成 ` D`** |
| 4 | agent | 立刻跑一次 **live 探針**(真的觸發一次,不是跑測試)。沒擋 → 立刻請人用備份還原 |

## 第 2 步的前提:草稿必須解析到與正式檔相同的資源

**否則驗收測的是別的東西,而且會偽裝成綠燈。**

第一次跑就撞到:`HOME` 原本從 `os.path.dirname(__file__)` 推導,於是
專案內的草稿去找**專案裡**的 `g1-protected.txt`(不存在),正式檔去找家目錄裡的。
結果 18 條驗收全部 fail-closed 通過 —— 每一條都 `exit=2`,看起來像全綠,
而實際上測到的是「清單讀不到」,**比對邏輯一行都沒被執行**。

處置:定位點改用 `os.path.expanduser("~")`,草稿與正式檔指向同一份清單。

**通用形式:凡是「在別的位置跑同一份程式碼」的驗收,先確認它的外部相依
(設定檔、清單、資料庫、環境變數)解析到的是同一個東西。**
位置一變、相依跟著變的話,驗收與正式執行是兩件不同的事,
而 fail-closed 的設計會讓那個差異看起來像成功。

## 修訂註記(2026-08-14,票 25):第 3 步是**複製**,而且覆蓋後要查一次

**舊文**:第 3 步原本寫「把草稿**複製**覆蓋過去」,沒有指定指令、也沒有查核步驟。

**為什麼要補**:實測手滑了一次 —— 用 `mv` 而不是 `cp`,
於是 repo 正本 `.claude/portable/g1_guard.py` **從工作樹裡消失**,
`tests/test_g1_guard.py` 整個收集失敗。HEAD 裡完好,`git restore` 零損失還原。

「複製」與「搬移」在手動操作時只差一個字,而**這一步依設計就是人做的**,
所以不能靠「記得用 cp」——要有一個做完就能查的動作。
新查核項:**覆蓋後 `git status`,repo 正本不得出現 ` D`。**

失敗方向是好的(整個測試集無法收集 → 立刻被發現,不是靜默)。
但那是這次剛好有測試載入它;換成一個沒有測試載入的檔案,同樣的手滑會活很久。
**查核項不依賴「剛好有測試會炸」。**

還原本身的判準見 **F-081**(追蹤檔 / 無未提交修改 / HEAD 即權威,
三條同時成立才可自行還原,且必自報)。

## 修訂註記(2026-08-14,票 25):第 1 步不再另立 `_draft` 檔

**舊文**:第 1 步原本寫「改草稿 `.claude/portable/g1_guard_draft.py`」。
照 F-036 保留原始寫法在此,上表已改為 `.claude/portable/g1_guard.py`。

**為什麼改**:agent-gates 裡 `.claude/portable/g1_guard.py` **本身就滿足這條規則
要的全部條件** —— 它在專案內、受 R1–R7 管、有 `tests/test_g1_guard.py`
(那個測試檔的 docstring 也是這樣寫的:「這份是 repo 內的版本,正式檔在
`~/.claude/hooks/g1_guard.py`,只有人能覆蓋過去」)。

再開一個 `_draft.py` 會產生**第三份副本**(正式檔、portable 正本、草稿),
而三份會分岔 —— **F-080** 記的正是「動守衛碼前沒搜既有實作,寫了一份重複的偵測」,
那一次的代價是兩份實作回答同一個問題。這裡預先避掉同型的錯。

`_draft.py` 的歷史來源是 TradingAgents:G1 最初在那個 repo 裡開發,
當時沒有 portable 正本可改,所以才需要一個草稿檔。**agent-gates 有了正本之後,
草稿檔的角色由正本承擔** —— 名字不同,滿足的條件一樣。

下面「為什麼草稿放在專案內」整段的理由**完全不變**,只是「草稿」現在指的是
專案內那份正本。

## 為什麼草稿放在專案內

專案內 → **R1–R7 照常適用**。草稿是 `.py`,所以 R3 要求它有測試、
R2 要求它在 implement 站才能寫、R7 要求用檔案工具寫。
放在 `~/.claude/` 底下的話這些一條都不適用 ——
**防護機制的修改反而是整個系統裡管得最鬆的地方**,那個方向是錯的。

## 為什麼第 4 步是 live 探針而不是測試

**檔案語法正確不等於它在守。**

這條不是原則,是實錄:F-042 的前哨層通過了全部測試、
`python -c "import gate"` 也正常,而它一整輪沒擋過任何東西 ——
壞的是 `mode_hook()` 裡的一行編碼假設,而測試呼叫的是 `check()`,碰不到那一行。

**驗邏輯證明「如果被呼叫,它會擋」,證明不了「它會被呼叫」**(F-040 家族的統一判準)。
只有真的觸發一次才回答後者。

## 第 4 步的前提:一次觀測只能放一個受測項

**任何 fail-fast 的機制,一次觀測只能放一個受測項。**

一次放兩個,你只會知道「至少有一個中了」,不會知道是哪一個 ——
而輸出**看起來像是其中特定一個被擋**,因為 fail-fast 在第一個命中就停下,
訊息只提那一個。它不會說「另一個我根本沒看」。

同一條流程裡已經犯過兩次:

| 情況 | 混了什麼 | 看起來像 | 實際是 |
|---|---|---|---|
| `rm -rf D:/notes1_old/` | 第一級(前綴比對)與第二級(破壞性動詞) | 前綴比對誤擋鄰居 | 第二級正確發作 |
| `ls D:/notes123; ls D:/保管庫/2023` 同一指令 | 「應放行」與「應擋下」兩個案例 | 相鄰名稱被誤擋 | 第二個案例命中,第一個沒被量到 |

兩次都得拆開重跑才拿到真實結果。

**適用範圍不只 G1。** R7(第一個寫入構造命中就擋)、R2(第一條規則命中就返回)
都是 fail-fast,同樣適用:一個探針指令裡只放一個要驗的東西,
要驗兩件事就跑兩次。

## 不變的部分:第 3 步只有人能做

**不得寫任何 agent 叫得動的腳本代勞。**

一支「自動覆蓋 g1_guard.py」的腳本會讓整條路徑重新變成 agent 可以自己走完的 ——
保護就沒了。中間那道人工步驟不是流程摩擦,**它就是保護本身**。

同理:不要為了方便而把 `~/.claude/hooks/` 移出保護清單,
也不要加「改自己時豁免」的條件 —— 那正是這份 ADR 存在的理由。
