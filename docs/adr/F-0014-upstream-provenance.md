# 0014 — 同步成品的紅燈責任在上游(provenance)

**日期**:2026-08-13
**狀態**:已採用
**相關**:ADR 0013(R3 判定實作不是檔案)、票 09(更新路徑)、票 10(R2 的內容豁免)

## 問題

下游 repo 收到 `sync` 帶進來的實作時,R3 要求**本地**紅燈紀錄 —— 而紅綠燈迴圈
在上游。下游拿到的是**成品**,它從來沒有機會讓那些測試在實作不存在時紅過。

現有的三條路都不對:

- **legacy 名單**:只減不增,入場券是「在機制上線 commit 的樹裡」。
  新收到的成品不在那棵樹裡,正確地進不去。硬塞就是把名單變成許願池。
- **本地補跑紅燈**:要先刪掉實作才紅得起來。叫人為了滿足規則去刪剛收到的檔案,
  規則就開始改變行為,而且改出來的行為更差(F-046 的形狀)。
- **關掉 R3**:那是稅太高的規則最後的下場,而關掉之後沒有人記得它守什麼。

## 決定

`sync` 寫入時同步產 **provenance** 紀錄(上游 commit hash + 路徑),
R3 對其中的檔案改判:

> **與上游那個 commit 的物件逐位元組相同 ⇒ 紅燈責任在上游。**

### provenance 是控制,不是證據

這個區別決定了整個設計。證據可以被竄改(shadow-log 就是,F-057);
**控制不行** —— 能自助的控制等於沒有控制。

所以驗證**必須對到上游的 git 物件**:

```
git -C <upstream_root> show <upstream_commit>:<upstream_path>
```

取回內容自己算雜湊,與本地檔案比對。**不採信 provenance 檔案裡宣稱的
`content_hash`** —— 那個欄位是給人看的,不是判定依據。

理由用一句話說完:**手寫一筆 provenance 造不出一個上游沒有的 blob。**
偽造需要改上游,不是改本地檔案。這是「豁免條件必須無法自我服務」的第五次出現
(閘門自我修改、票宣告接縫、legacy 清單、R3 的 HEAD 錨點,以及這裡)。

負控是這條設計的驗收:**自己手寫一筆 provenance 給一個上游沒有的新檔案,必須被擋。**
另有一條分得開兩種實作的測試 —— 宣稱的 hash 與本地相符、但上游物件不同:
採信宣稱值的實作會放行,對到 git 物件的實作會擋。

### 邊界

- **只豁免 R3 的紅燈半。** 前半(對應測試檔要存在)照常適用 ——
  同步本來就把測試一起帶過來,那一半不需要放寬。
- **不碰 R2。** 那是票 10 的窗口問題。一個豁免同時鬆兩條規則的話,
  爆炸半徑就不再是它宣稱的那個。兩者同族但各自獨立。
- **本地一改就失效。** 內容與上游物件不再逐位元組相同的那一刻,
  紅燈責任回到本地 —— 這正是想要的:改過的就不是「上游的成品」了。
- **雜湊前正規化行尾。** `git show` 給的是物件裡的位元組(LF),
  工作樹在 autocrlf 的機器上是 CRLF。不正規化的話永遠不相等(ADR 0013 同一個坑)。

### fail-closed

沒有紀錄、讀不動、上游問不到、內容對不上 —— 一律不給豁免。
「問不到」不等於「相同」。

## 殘留

- **上游指標的可信度。** provenance 記著 `upstream_root`;指向一個受控的 repo
  就能造出任意「上游物件」。目前靠的是「誰能改那個路徑」這個系統外的假設,
  與 ticket 01 的「來源指標可不可信」是同一題,未解。
- 上游 repo 不在同一台機器時整條路徑不成立(現況是本機多 repo)。
