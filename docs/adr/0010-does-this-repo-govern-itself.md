# ADR 0010 — agent-gates 自己受不受這套框架管

日期:2026-08-10
狀態:**暫定 B(不自管)**,解鎖條件見下

## 三個選項

| | A. 完全自管 | B. 完全不管 | C. 部分自管(R3 + G1,不裝 R2) |
|---|---|---|---|
| 做法 | 裝上自己的閘門,改框架也走六站 | 只當發布來源,不裝 hook | 只裝測試先行與災難防護 |
| 最大好處 | 框架自己是最大的驗收案例 | 修 bug 快 | 保住最有價值的一條,去掉最煩的 |
| 最大壞處 | **自相矛盾**(見下) | 少一個驗收案例 | **凍結來源不存在**(見下) |

## A 被排除:為了自管而放寬自管

選 A 要把 `install.py` / `verify_gates.py` / `g1_verify.py` 擴進 `GATE_SELF`
(閘門自我修改豁免名單),否則改它們時會被自己擋住而無法修復。

**而擴充豁免名單就是放寬閘門** —— 方向與 ADR 0004 相反。
ADR 0004 的名單刻意是**具體檔案**而不是「`.claude` 底下的 .py」這種籠統類別,
理由正是後者是白名單思維的變形。為了自管而把名單擴大,是用放寬換取自管,自相矛盾。

## C 的解鎖條件:不是「機制不存在」,是「凍結來源不存在」

C 需要「每個 repo 宣告啟用哪幾條規則」。查證過(2026-08-10):
**這個機制沒有實作**,`gate.py` 的 R 系列全部無條件生效;
`rule_codes()` 與 `verify_gates.SCENARIOS` 都是**列舉**,不是**啟用控制**。

但真正的障礙不是「寫一個設定檔」——那是小事。障礙是:

**啟用宣告必須是不可自我服務的,否則 agent 可以自己把 R3 關掉。**

現有唯一的凍結模式是 `legacy-no-redlight.txt`:它以
「存在於 go-live commit 的樹裡」為入場券,而 **agent 改不了 git 歷史**。
那套綁的是**路徑**。規則代號**沒有等價物** ——
「R3 是否啟用」不是一個能被 git 樹背書的事實。

所以 C 的解鎖條件是:
**先有一個不可自我服務的規則啟用來源。**
不是「以後再說」,是一個具體的、可以被做出來的前置條件。

在那之前選 C 等於開一個 agent 自己關得掉的開關 —— 比不裝更糟,
因為它會讓人以為有在守(ADR 0007 的同一個判準)。

## 暫定 B 的代價,以及為什麼可以接受

代價是「框架自己不是驗收案例」。但這個代價**不是新增的**:

現有所有「六條規則各擋一次」的證據本來就來自**別的 repo**
(空 repo 的淨室安裝測試)。B 不會失去現有的驗收,只是不會多一個。
而淨室測試是**更強**的證據形式 —— 它驗的是「裝到別處會不會動」,
那正是這個 repo 存在的目的(F-031:換環境跑一次是獨立的涵蓋維度)。

## 什麼時候回頭

出現以下任一情況就重新評估:

1. 有了不可自我服務的規則啟用來源 → 改 C
2. agent-gates 自己出現「改壞了規則而沒有被發現」的事件 → 代表少的那個驗收案例是真的需要
