# ADR 0004:閘門自身 —— R2 豁免,R3 不豁免

- 狀態:已採納
- 日期:2026-08-09
- 發現於:fail-open 稽核票,維度 1(不涵蓋的集合)

## 背景

`.claude/` 整個在非原始碼清單裡,理由是「設定檔目錄」。但它同時裝著兩支會被執行的程式:
`hooks/gate.py`(閘門本身)與 `patches/apply_patches.py`。

實測:寫 `.claude/hooks/gate.py` 回 exit=0 —— 完全不受 R2/R3 管。
上一輪我改 gate.py 十幾次,沒有一次需要先有測試、沒有一次受站別限制。
**修改閘門的行為是整個系統裡防護最弱的動作,而它的爆炸半徑最大**:
F-017 的自造 fail-open 就發生在這裡,零阻力。

## 決定

`.claude` 移出非原始碼清單,`.claude/**/*.py` 納入 R2/R3 管轄。其上:

- **`.claude/hooks/gate.py`:R2 豁免、R3 照常適用。**
- **豁免不靜默**:放行時 stderr 明說「自我修改豁免,已記錄」,並寫一筆
  `gate-exemptions.jsonl`,理由欄 `gate-self-modification`。
- **豁免對象是具體檔案清單**(`GATE_SELF`),不是「`.claude` 底下的 `.py`」這個籠統類別
  —— 後者又是白名單思維的變形。`apply_patches.py` 不在清單內,R2 與 R3 全部受管。

## 為什麼 R2 有例外

死鎖。R2 擋的是「還沒談清楚就寫」,但**搶修的前提就是流程已經不通**——
閘門把站別卡住時,修法需要改 gate.py;R2 若管到它,人會被鎖在外面,
唯一出路是 `--no-verify` 或手改狀態檔,兩者都比開一個看得見的豁免更糟。
該判準在此不適用,不是規則太嚴。

## 為什麼 R3 沒有例外 —— 這條比上一條重要

**未來被閘門擋住的人,第一個念頭會是「全部豁免比較乾脆」。理由不寫下來,
下次搶修到一半就會順手把 R3 也豁免掉。** 這與 F-017 修誤擋時自造 fail-open 是同一個心理:
修規則的阻力當下,最容易做的事就是把規則關掉。

R3 沒有死鎖問題:**寫測試不需要先解鎖任何東西**。閘門壞掉時你照樣能寫 `tests/test_gate.py`,
它不受任何站別或規則限制。R2 的例外源於「修它需要它自己讓路」,R3 沒有這個循環。

而且爆炸半徑的方向是反的:改閘門而沒有測試,壞掉的是**所有其他規則的守備能力**,
不是單一模組的行為。防護最弱處遇上爆炸半徑最大處,正是最不該再放寬的地方。

## 後果

- 改 gate.py 一律需要 `tests/test_gate.py` 存在(本票已建立)
- 改 `apply_patches.py` 需要 `tests/test_apply_patches.py`,且必須在可寫站 —— 尚未建立,下次修它會被擋,那是預期行為
- 每次自我修改都留下一筆帳,code review 的 Standards 軸逐筆看:
  搶修是罕見事件,某一輪出現十筆就不是搶修,是把後門當日常通道
