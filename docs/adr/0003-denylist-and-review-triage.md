# ADR 0003:閘門用黑名單,以及 code review 的分流判準

- 狀態:已採納
- 日期:2026-08-09
- 觸發:Step 5 試跑,一輪之內連續踩到三個同源缺陷(F-001、F-009、F-011)

## 背景

`gate.py` 的三條規則在一輪試跑內各被發現一次 fail-open:

| 編號 | 缺陷 | 共同形狀 |
|---|---|---|
| F-001 | 站別定義讀不到時退回「implement 可寫」的預設 | 出事時放行 |
| F-009 | R1 只守 `docs/specs/`,官方 spec 落在 `.scratch/` | 名單沒列到就放行 |
| F-011 | `SRC_DIRS` 白名單不含新模組,而 spec 正要求新增獨立模組 | 名單沒列到就放行 |

三者都是**白名單思維**:先列出「要管的東西」,沒列到的一律放行。
問題在於「沒列到」有兩種來源——真的不需要管,以及**還沒想到**。白名單把兩者一視同仁地放行。

F-011 另有一層:Standards 軸在框架自身的 diff 上**就標過** `SRC_DIRS` 是硬編碼元組
(Shotgun Surgery),當時被當成風格建議打發掉。**偵測沒有失效,分流失效了。**

## 決定

### 一、閘門一律用黑名單,fail-closed

列出「不管的東西」,其餘全管。新東西預設被守。

**誤擋時的正確處置是把該目錄加進黑名單例外,不得因為覺得規則煩而退回白名單。**
R2/R3 的擋下訊息會直接指出例外清單的檔名與行號,讓誤擋當下的處置是三十秒的事,
並在訊息裡明寫禁止退回白名單。

黑名單會誤擋,這是它的設計代價,不是缺陷:誤擋會被立刻發現並修好,
放行不會——你會以為它在守。

### 二、code review 的處置判準

發現一個問題時,要問的不是「**要不要改**」,而是「**不改會不會讓別的規則失效**」。

前者是品味問題,可以擱置;後者是安全問題,擱置就是把一個已經被偵測到的洞留在原地。
`SRC_DIRS` 是硬編碼元組——以品味論,擱置合理;以「不改會讓 R2/R3 對新模組完全失效」論,
它是當下就該處理的。同一個發現,分流結果完全不同。

## 後果

- 黑名單會持續誤擋新的非原始碼目錄,處置固定:加例外,不退回白名單
- code review 的發現必須逐條問「不改會不會讓別的規則失效」,不能只按嚴重度排序後擱置低分項
- 尚未做:對每條規則逐一問「它不涵蓋的集合是什麼」的系統性 fail-open 稽核。
