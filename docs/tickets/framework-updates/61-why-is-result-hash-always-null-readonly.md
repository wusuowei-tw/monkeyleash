# 61 — 唯讀:量化 pre-commit 路徑的 `result_hash` 為何恆為 null,以及 `ledger_verify` 該不該分型

**狀態**:**candidate(唯讀盤點,不動工)**
**立案**:量化同步輪(2026-08-19)
**來源票根**:量化 `add89e7` 的 commit 訊息(順帶觀察,當時**刻意未發號**)

> **這一張刻意沒有 friction 號。**
> 發號前要先判定它是框架層還是量化本地的事,而那正是本張要查的東西之一。
> **先發號再判層級,會讓一個還沒被理解的東西看起來已經被歸類了。**

## 觸發的觀察

2026-08-19 用剛落地的 `.claude/portable/ledger_verify.py` 掃量化的豁免帳:

```
$ cd 台股資訊收集 && python .claude/portable/ledger_verify.py .dev/gate-exemptions.jsonl
    ...
    斷點:第 34 筆結束於 ,第 35 筆卻從 3a399ab2621e 開始

**斷點不等於缺陷。** 它的意思是「有一次改動發生在前哨看不見的地方」
(`git checkout`、外部編輯器、或真的有人繞過)—— 要讀上下文才分得出來。

**首尾相等不蘊含逐段接續** —— 兩者是分開的兩個問題。
EXIT=0
```

**35 筆裡 34 處斷點。**
訊息裡「第 N 筆結束於 」後面是空的 —— 因為那些紀錄的 `result_hash` 是 `null`。

**上游 agent-gates 的同一份帳只有 1 處斷點**(commit `d179963` 的訊息記載)。
**同一支工具、同一種檔案,兩邊形狀差 33 處。**

## 待查猜想(裁決當場提出,**尚未查證**)

> 帳本有**兩種紀錄形態**:
> **Edit 轉移**(前哨在 agent 寫檔時記,知道寫之前與寫之後,所以填得出 `result_hash`)
> 對上 **pre-commit 偵測**(權威層在提交時記,它看到的是一個既成狀態,沒有「之後」可填)。
>
> 若成立,則 `ledger_verify` 需要**分型**,而
> **這 34 處斷點是「語意不匹配」,不是「有人繞過」。**

猜想若成立,它推翻的不是工具的正確性,是工具的**適用範圍宣告** ——
`ledger_verify` 目前把一份混著兩種形態的帳當成一條鏈在驗,
而**一條鏈的前提是每一筆都有「之後」**。

## 要查的(全部唯讀,不改任何東西)

1. **量化那 35 筆的 `tool` 欄位分佈** —— 是不是全部 `pre-commit`?
   (已知樣本:2026-08-19 新增的 6 筆全部 `"tool": "pre-commit"`、`"result_hash": null`)
2. **上游那份帳的 `tool` 欄位分佈** —— 那 1 處斷點落在哪一種形態的交界?
3. **`result_hash` 是誰寫的** —— 找出寫它的程式碼路徑,確認 pre-commit 路徑是
   **不填**(設計)還是**忘了填**(缺陷)。**這一題決定層級**:
   - 不填 ⇒ 框架層(任何裝了框架的 repo 都成立)⇒ 回 `F-` 號
   - 忘了填 ⇒ 仍是框架層,但變成一張修復票而不是一則 friction
   - 只有量化這樣 ⇒ 才輪得到 `TSI-` 號
4. **`ledger_verify` 的既有測試涵蓋哪一種形態** —— 9 條測試全部用手造紀錄串列,
   **手造的紀錄是哪一型?** 若全是有 `result_hash` 的那一型,
   則「混型帳本」這個情況**從來沒有被測過**,而它正是真實資料的樣子。
5. **`EXIT=0`** —— 工具對 34 處斷點回退出碼 0。

   > **⚠ 動工時必須把原始設計理由逐字引進票面,不得只寫我這一側。**
   > 這一題是一個**張力**,不是一個缺陷。只寫一側會讓下一個人以為它已經有答案了。

   **它是刻意的,而且理由已經寫下來了。** `ledger_verify.py:44-48` 逐字:

   > 因此本檔**永遠回 0**,不用退出碼表達「有沒有斷點」——
   > 把「需要人看一眼」講成「失敗」,會讓它被當成紅燈去消除,
   > 而消除的方法多半是不再跑它(F-031)。

   同檔 `:36-43` 是它的前提:`chain_breaks()` **只回報,不判對錯**,
   斷點可能是 `git checkout`、外部編輯器、也可能是真的有人繞過,
   **分辨它們要讀上下文,那是人的判斷**(明寫與 `sync.refuse_if_duplicate_headings`
   同一個理由:護欄讓它現形,不替人決定)。

   **所以兩側都成立,而它們互相牴觸:**

   | | 主張 | 靠山 |
   |---|---|---|
   | 保持 `return 0` | 把「需要人看一眼」講成「失敗」會訓練人忽略訊號,而消除的方法多半是不再跑它 | **F-031**,且已寫進 `ledger_verify.py` 檔頭 |
   | 讓它能回非 0 | 一個永遠回 0 的驗證工具,接進 CI 時等於沒接 —— **CI 只讀退出碼** | 票 54 落差表第 8 列(「全綠證明的是接上了,不是擋得住東西」) |

   **要查的因此不是「該回幾」,是「這兩側能不能同時滿足」。**
   可能的第三條路(先寫下來,免得動工時只在兩極之間選):
   - `--strict` 旗標:預設回 0,CI 那條路徑明確要求嚴格
   - 分型之後只對**不該有斷點的那一型**回非 0(依賴第 1-3 題的答案)
   - 退出碼永遠 0,但**輸出一個機器可讀的計數**,由 CI 那側決定門檻

   **這三條都還沒有被評估過**,列在這裡是為了讓動工的人不必重新想一次。

## 為什麼值得一張票(而不是順手查掉)

- 第 4 題是 **F-103 那一族**(「一個斷言可以因為錯的理由而通過」)的直接候選:
  若測試只餵單型資料,那 9 條綠燈**證明不了工具能處理真實帳本**
- 第 5 題**不是缺陷,是張力** —— 兩側各有靠山(F-031 對票 54 落差表第 8 列),
  而**張力要兩側都在票面上才裁得動**。只寫一側的票會被下一個人當成已有結論的題目,
  然後他照著那一側去改,把另一側的理由一起刪掉 —— 而那個理由**當時是對的**。
  它同時是 **F-105 那一族**(訊息類斷言只有一種抓得到判定壞掉)的鄰居
- 而 CLAUDE.md 的常駐檢查項要求:**修好一個偵測器之後,回頭重掃既有資料。**
  `ledger_verify` 是 2026-08-18 才進版控的**新偵測器**,
  這是它的**第一次跨 repo 全量掃描** —— 而第一次全量掃描問的是
  「**以前犯過幾次**」,不是「以後會不會再犯」。
  **34/35 就是那個答案,而它現在還沒有被解讀。**
