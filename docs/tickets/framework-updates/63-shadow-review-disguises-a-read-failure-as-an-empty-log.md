## 現象(實測,不是推論)

量化的影子日誌有 **222 行**,而工具說「還沒有任何」:

```
$ cd 台股資訊收集 && python .claude/portable/shadow_review.py --status
還沒有任何已分類的影子日誌。先跑一輪互動分類。

$ wc -l < 台股資訊收集/.dev/shadow-log.jsonl
222

$ head -c 8 台股資訊收集/.dev/shadow-log.jsonl | od -c
0000000 357 273 277   {   "   t   s   "
        ^^^^^^^^^^^  EF BB BF = UTF-8 BOM
```

成因(`shadow_review.py:41-49`):

```python
def load_log(path):
    rows = []
    try:
        for line in io.open(path, encoding="utf-8"):
            line = line.strip()
            if line:
                rows.append(json.loads(line))
    except Exception:
        pass
    return rows
```

BOM 讓第一行變成 `﻿{"ts": …}` → `json.loads` 丟例外 → `except: pass` → 回 `[]`。
`print_status` 收到空的就播報「還沒有任何已分類的影子日誌」——
**那是一句關於資料的斷言,而它是假的。**

> **「沒東西可報」與「壞了」被壓成同一個輸出。**(`TSI-012` 的形狀。)

## 第二個缺陷:同一個 `except` 在另一條路徑上是**靜默資料破壞**

`review()` 拿 `load_log` 的結果**整份重寫檔案**:

```python
rows = load_log(path)
unclassified = [i for i, r in enumerate(rows) if not r.get("classification")]
if not unclassified:
    print("沒有未分類的項目。")
    print_status(path)
    return                      # ← 全失敗時在這裡就走了,檔案沒事
...
with io.open(path, "w", encoding="utf-8", newline="\n") as f:
    for r in rows:              # ← rows 是 load_log 給的那一份
        f.write(json.dumps(r, ensure_ascii=False) + "\n")
```

| 情況 | `rows` | 後果 |
|---|---|---|
| BOM(第 1 行就炸) | `[]` | `unclassified` 空 → **提早 return,檔案沒事**(僥倖,不是設計) |
| **壞行在第 50 筆(共 222)** | **49 筆** | 分類完 → **重寫成 49 筆,173 筆永久消失** |

**沒有任何東西在檢查「讀進來的筆數 == 檔案裡的筆數」。**

> 這讓「出聲失敗」從**回報正確性**升級成**資料安全**:
> `except: pass` 在這條路徑上不是靜默沉默,是靜默破壞。

### 裁決問的「筆數守恆斷言便不便宜」:**便宜,做**

理由不是省事,是**兩道守的東西不同**:

- 出聲失敗守的是**這一次的讀**(壞行 → 不回部分)
- 筆數守恆守的是**寫的那一刻**(不管 `rows` 怎麼來的,少了就不准寫)

修好之後 `load_log` 要嘛回全部、要嘛丟例外,所以兩者在**當下**等價 ——
**而那正是為什麼要留第二道**:等價是**目前實作**的性質,不是這條路徑的性質。
下一個人若為了別的理由讓 `load_log` 再度容忍部分失敗,
**第一道會消失,而重寫那一行不會知道**。

> **能用構造消掉的不要用紀律管;消不掉的,留一根釘子在會出事的那一行旁邊。**
> 這一根釘在 `with open(path, "w")` 前面,不在 `load_log` 裡 —— 位置就是它的理由。

成本:一個 helper + 三行檢查 + 一條負控測試(把 `load_log` monkeypatch 成回截斷清單,
斷言 `review()` **拒絕寫入**)。負控是必要的:少了它,這道檢查在
「第一道正常運作」的世界裡**永遠不會被走到**,而一個從未被走到的
fail-closed 分支,會在它前面那個分支被拿掉的當天才現形(票 42 的判準句)。

## 動工中追加:同一個病在上一層又出現一次

**這一段不在立案時的範圍內,是修完之後拿真檔驗收才撞到的。**

`load_log` 修好之後,量化那 222 筆讀得到了 —— 但它們**全部尚未分類**
(`classification` 欄:0 / 222)。於是 `promotion_status` 回空 dict,
而 `print_status` 對空 dict 印的是:

```
還沒有任何已分類的影子日誌。先跑一輪互動分類。
```

**與壞掉時逐字相同。**

> `load_log` 那一層分開了「讀不到」與「日誌是空的」;
> **這一層還壓著「讀到了但沒分類」與「什麼都沒讀到」。**

後果不只是訊息不精確 —— **本票自己的驗收條件驗不了**:
裁決寫的是「量化側驗 `--status` 讀得到 222 筆」,而修好前後那一行字一模一樣。

**判為在範圍內,補完**(理由:本票的主張就是「『沒東西可報』與『壞了』要分開」,
而這是同一句話在上一層的實例;留著它等於修了一半並且拿不到驗收證據)。

處置:狀態一律**先報讀到幾筆**,再報分類情形 ——
讀到的筆數是這支工具唯一能證明「我真的看到資料了」的東西。

修好後對量化真檔的實際輸出:

```
影子日誌:讀到 222 筆,其中 0 筆已分類。
尚無任何分類 —— 跑一輪互動分類(不加 --status)即可開始。
```

四條測試釘住(含兩條負控:真空日誌要說得出自己是空的;加了筆數不得把晉升表擠掉)。

**這一層仍用 `print()`**,沒有改成 `sys.stdout.buffer.write` —— 那是票 62 的範圍。
