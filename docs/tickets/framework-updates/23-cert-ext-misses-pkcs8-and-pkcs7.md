# 23 — `CERT_EXT` 漏掉 PKCS#8 私鑰與 PKCS#7 簽章包

**排程**:**立刻辦**。這是票 22 R1b(全樹掃描)的前置 —— 用有洞的規則掃出來的「乾淨」不算乾淨。
守衛變更,走完整流程,自己的紅燈。

## 現象

`leak_scan.py` 的 `CERT_EXT` 是**副檔名即判定、不讀內容**的那條路徑,
註解裡寫得很清楚它的地位:

> 二進位憑證任何編碼都解不開,掃內容永遠漏,而檔名是確定的。
> F-062 紅燈:260-byte 二進位憑證進 staged,舊版回 0(沒擋)。

清單目前涵蓋六種副檔名,**不含 PKCS#8 私鑰(`.p8`)與 PKCS#7 簽章包(`.p7b`)**。
票 22 Phase 1 在本機盤點到這兩種檔案**實際存在**:PKCS#8 私鑰兩份(各 1,704 B)、
PKCS#7 簽章包兩份,分屬兩個憑證存放目錄。

## 為什麼是洞,而不是「反正內容比對會抓到」

盤點時實測過那兩份 PKCS#8:**前 5 個 bytes 是 `-----`,是 PEM 文字**。
通用 pattern 有一條私鑰標頭式 `-----BEGIN [A-Z ]*PRIVATE KEY-----`,
所以**這兩份**大概打得到。

但那是「這一份剛好是 PEM」,不是「這條規則守得住」:

1. **同一種副檔名可以是 PEM 也可以是 DER。** DER 是純二進位,沒有任何文字標頭,
   內容比對完全打不到 —— 這正是 F-062 那次紅燈的形狀。
   判定不能取決於手上這份剛好是哪一種編碼。
2. **本次沒有驗證第一行標頭實際是什麼**(只讀了前 5 bytes,沒有再讀進金鑰內容)。
   所以連「這兩份會被打到」都只是推論,不是實測結果。**不引用未驗證前提。**
3. PKCS#7 簽章包(`.p7b`)通常是 DER。它連 PEM 那條僥倖都沒有。

副檔名判定的價值就在於**不必知道內容長什麼樣**。
把兩個副檔名補進去,上面三點全部消失;不補的話,守得住與否取決於運氣。

## 範圍:只動副檔名判定,**不加對應的內容 regex**

通用 pattern 檔裡有一族是**內容比對**的副檔名字面(`\.<副檔名>\b` 形狀)。
`SELF_PATHS` 只豁免兩個檔(`leak_scan.py` 與通用 pattern 檔本身),
`SKIP_BASENAMES` 只豁免 `.gitignore` —— **其餘一切散文都掃**,而且「散文不豁免」是刻意的。

實測後果:票 22 的完整盤點表因此**無法進這個 repo**(對它跑 `leak_scan` → exit 1,
命中三條通用 pattern + 兩條個人 pattern),票 22 只能寫佔位符版。
那個代價是對的 —— 但**不要再擴大它**。

再加同型的內容 pattern,repo 會連自己的守衛都寫不出來:
往後任何討論這兩種副檔名的票、ADR、machine-init 章節都會被自己擋下。
**副檔名判定沒有這個副作用**(它比對的是 staged 檔案路徑,不是檔案內容),
所以本票只動 `CERT_EXT`。

> 這一段是決定,不是待議項:**不加 `\.p8\b` / `\.p7b\b` 之類的內容 pattern。**
> 要推翻它請開新票,理由要能回答「repo 之後怎麼記載這條規則」。

## 紅燈先行(真紅燈,不是補測試)

現行實作對下列每一條都回 0(沒擋)—— 這是本票要看到的紅:

| 案例 | 期望 |
|---|---|
| **DER(二進位、無文字標頭)的 `.p8` 進 staged** | 擋。命中理由是「憑證副檔名」,不是內容 pattern。**這條是核心紅燈**:它證明修的是副檔名路徑,不是靠內容僥倖。 |
| **DER 的 `.p7b` 進 staged** | 擋,同上。 |
| PEM 文字的 `.p8` 進 staged | 擋,且理由仍是副檔名(不是私鑰標頭)—— 否則測到的是內容 pattern,不是這次的修改。 |
| 大寫副檔名 `.P8` | 擋(現行用 `.lower()` 後 `endswith`,這條應該一開始就綠;綠也要留著,它守的是往後別把 `lower()` 拿掉)。 |
| 檔名**含**但不以該副檔名**結尾**(如 `x.p8x`、`notes-about-p8.md`) | **不擋**。誤擋的代價在這裡不是不方便 —— 是這條規則會被關掉。 |

現行六種副檔名的既有案例必須**全部維持綠**;沒有既有案例的就補一條,
否則這次改動的回歸網只蓋新的兩種。

### 紅燈已取得(2026-08-14)

`tests/test_leak_scan.py::TestCertExtCoversPkcs8AndPkcs7` —— **5 紅 1 綠**,
紀錄在 `.dev/test-runs.jsonl`,`ticket_id: "23"`、`impl_exists: true`、
`impl_hash` 為改動前的 `leak_scan.py`(R3 的「紅燈對著改動前的碼發生」成立)。

綠的那一條是**反控**(相鄰副檔名不得誤擋)—— 它一開始就該綠,
紅的話代表新規則太寬,而那個方向的錯誤會讓整條規則被關掉。

**上表「現行實作對每一條都回 0」經實測成立,包括二進位的兩條。**
中途曾懷疑二進位那兩條會走到「讀不到內容」而被計為違規(退出碼 1、理由卻是別的),
實測不是:掃描器對那些位元組解得出東西,於是走完內容比對、沒命中、放行。
**所以這兩種副檔名今天是完全的 fail-open,不是「擋對了但理由不對」。**

即便如此,每一條測試仍斷言「命中理由是**憑證副檔名**」而不只斷言退出碼 ——
因為 `.p8` / `.p7b` 不在 `SKIP_SUFFIX` 裡,未來任何一次把它們加進去的「整理」
都會改變它們走哪條路;只斷言退出碼的話,那種改動不會有任何訊號。
