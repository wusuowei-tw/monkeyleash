## 票 114 為什麼判它「不屬 B-4」—— 以及那個判定為什麼要被核

B-4 的停手判準是「**內容比對前的行尾正規化**」。
票 114 把 `splitlines()` 判為**不屬於**,理由逐字:

> `splitlines()` 確實會吃掉 `\r`,但用途是**切行**不是**等價比對**。

**而那份報告同時標明了這一格是灰的**,逐字:

> 「`splitlines()` 會把 `\r` 吃掉」,代表這個副作用在本 repo 被意識到過。

**本票就是去核那個判定。**

## 為什麼值得核(不是「有用到就要改」)

**危險的不是 `splitlines()` 本身,是它與「之後要拿那些行去比對」的組合。**

具體要問的三類:

| 類 | 形狀 | 危險嗎 |
|---|---|---|
| **A** | 切完只是**印出來**或取第一行給人看 | 幾乎不危險。例:`msg.splitlines()[0]` |
| **B** | 切完拿去**比對 / 判定**(`in`、`==`、集合運算) | **危險** —— 一行結尾帶 `\r` 與不帶,切完之後**長得一樣**,於是兩份不同的資料被判成相同 |
| **C** | 切完拿去**當路徑** | **已知有坑**,而且本 repo 修過:`git` 輸出要用 `-z`(NUL 分隔)不是 `splitlines`(`gate.py:3225` / `install.py:63` 都逐字寫著) |

**⇒ 本票的第一件事是把那 30+ 處分成 A/B/C 三類,不是全部改掉。**
全部改掉是**沒有判準的動作**,而它會製造一堆無意義的 diff。

**已知的 C 類已經修過**(`-z` 那一族),所以本票的實際範圍大概是 B 類 ——
**而 B 類有幾處,現在沒有人知道。那個數字是本票要產出的第一個東西。**

## 待裁

1. **要不要做?** 若 A 類佔絕大多數而 B 類為 0,那本票的結論就是
   「登記為已知,不動工」—— **而那也要量過才說得出來**。
2. **B 類的修法是什麼?** `split("\n")` 不等價(它不處理 `\r\n`);
   正解可能是「比對前先做行尾正規化」——**而那正好是 B-4 的判準**,
   於是這張票可能會**回頭併進 B-4 的家族**。
3. **要不要一條測試守著?**(例如:某些模組不得使用 `splitlines()`,
   或使用時必須先正規化)—— 依 `F-087`,「哪些呼叫點」是封閉可枚舉的。
