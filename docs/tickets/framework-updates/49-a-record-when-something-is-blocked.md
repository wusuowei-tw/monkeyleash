## 現況證據

### 頭條一:沒有通用的攔截帳本

全 repo **唯一**一筆有紀錄的實際攔截是 **R3**
(`.dev/gate-exemptions.jsonl`,`outcome=blocked`,`blocked_by=R3`)。

所以清冊的第 4 欄(「擋過沒有」)對多數規則**不可回答** ——
而原因是「**沒有東西在記**」,不是「查過沒有」。這兩者在表上長得一樣。

### 頭條一之二:**被批准的豁免也有一半沒有紀錄**(2026-08-18 加入,票 57 實測)

前一段講「攔截沒帳本」。這一段講**同一本帳裡,兩條豁免待遇不同** ——
而少的那一條是**放行**的那一條。

**實測**(票 57 ⑦ 那一輪,對 `gate.py` 與 `manifest.py` 各做了編輯):

| 豁免 | 觸發的檔案 | 進帳本? | 程式位置 |
|---|---|---|---|
| **R2 自我修改**(`GATE_SELF`) | `.claude/hooks/gate.py` | **是** —— 4 筆,`reason: gate-self-modification`、`outcome: granted` | 記帳走 `log_exemptions` |
| **R3 legacy 清單** | `.claude/portable/manifest.py` | **否 —— 一筆都沒有** | `gate.py` 的 R3 legacy 分支:`if r in legacy_no_redlight(): return None` |

那兩行直接 `return None`,**不進 `bucket`**,所以 `log_exemptions()` 收不到它。

> **擋下來的事你會看到(commit 失敗),放行的事你不會。**

`.agents/legacy-no-redlight.txt` 現在有 **9 個檔案**靠它繞過 R3 **整條**
(紅燈紀錄 + 測試檔存在,兩半都免)。**每一次繞過都沒有留下任何紀錄。**
問「這半年 legacy 豁免被用了幾次、用在哪些檔案上」——**無法回答**,
而原因與頭條一完全相同:**沒有東西在記**,不是查過沒有。

#### 附帶問題(本張要回答,不是順帶提一句)

**為什麼 `GATE_SELF` 記帳而 legacy 不記?**

兩條都是「這個檔案免受某條規則管」,性質同類,待遇不同。
**最可能的解釋是設計時只想到前者** —— `GATE_SELF` 是寫 ADR 0004 時
連同帳本一起設計的,legacy 清單是票 26 後來補的,而補的時候
**沒有人問「這條豁免也要記嗎」**。

若屬實,那不是「legacy 漏了記帳」這一個缺口,而是
**「新增一條豁免時,沒有任何東西提醒它要接上帳本」** ——
下一條豁免會用同樣的方式漏掉。**本張要處理的是後者。**

### 頭條二:當時的設定也沒有紀錄

F-083 掃出 **9 處**「決定規則行為卻不進版控」的檔案。

> **每一次判定,都是「一份不進版控的設定」對「一份不進版控的輸入」做出的,
> 而結果也不進版控。三樣缺一就無法複現,而現在三樣都缺。**

唯一例外是 `.dev/gate-exemptions.jsonl` —— **它進版控,而它剛好就是唯一留得下證據的那一個。**
兩件事是同一件事的兩面。

### 為什麼範圍是「被擋」而不是「每一次判定」

輸入**不是均勻缺失的**:

| 判定結果 | 輸入後來去了哪 |
|---|---|
| 通過 | 變成 commit —— **留得下來** |
| 被擋(pre-commit) | **從未落地** |
| 被擋(前哨) | **那筆寫入根本沒發生過** |

> **輸入唯一留不下來的情況,正是最想事後複驗的那一種。**

通過的已經有紀錄(commit 本身),被擋的一筆都沒有 —— **而它們是全部的爭議來源。**

### 那筆紀錄要帶三樣

**設定指紋 + 被拒的輸入 + 擋下的理由。**

### 先例

量化 `dc-01`:「**內容不進版控、指紋進版控**」。
理由是**可複現性**,不是完整性 —— 少了它結論無從證偽。

指紋綁的是**那一次判定**,不是某個時間點;於是設定 / 輸入 / 結果同處一筆,
而那九個檔**不需要**進版控。

### 寫進哪個檔:**新檔 `.dev/intercepts.jsonl`,不併進 `gate-exemptions.jsonl`**

**兩個理由,都是硬的:**

1. **schema 不相容。** `exemption_record()` 的鍵是**豁免形狀**的:
   `file` / `module` / `declared_in` / `reason` —— 全部來自 `ex` 這個豁免物件。
   一次 R7 攔截**沒有 `file`**(它的觸發物是指令),四個鍵全部填不出來。
2. **會弄壞 `ledger_verify` 的鏈驗證。** 那支工具逐筆讀
   `content_hash` → `result_hash` 串成鏈,**逐段驗接續**(v2 的存在理由)。
   插進一筆沒有這兩個欄位的紀錄,鏈就斷在那裡 ——
   而那條鏈是票 58 / 票 47 三次有界突變的收尾依據。

> **把兩種語意塞進同一個檔,省下的是一個檔名,付出的是一支已經在用的驗證工具。**

### 欄位

```json
{"ts": "<ISO8601 UTC>",
 "rule": "R7",
 "at_commit": false,
 "cmd_sha256": "<sha256(指令位元組)>",
 "cmd_verb": "<command_verb(指令)>",
 "cmd_len": 123,

```

- 前四個**沿用票 68 已經定案的指紋三欄**(`cmd_sha256` / `cmd_verb` / `cmd_len`),
  **不發明新的** —— 這樣影子側與 enforce 側的紀錄可以**用同一組欄位對帳**,

### 要不要進版控 —— **裁決:不進版控,改納入控制檔備份清單(第十處)**

### 為什麼它們也是空白 —— **`gate-exemptions.jsonl` 是豁免帳本,不是攔截帳本**

`log_exemptions` 第一行:

```python
def log_exemptions(bucket, verdict, at_commit, content=None, tool=None):
    if not bucket:
        return
```

`bucket` 是 `check()` 填的「這次判定**用到的豁免**」。**空的就直接返回。**

> **而「沒用到豁免的單純攔截」是最常見的那一種。**
>
> 豁免是例外路徑 —— 大多數攔截根本不會碰到任何豁免:
> 一個站別不對的寫入、一個缺測試檔的 `.py`、一條寫到專案外的指令,
> 都是直接判違規,`bucket` 從頭到尾是空的。
>
> 所以這個帳本記到的是**判定過程中順道用掉的豁免**,
> 而不是**「擋了什麼」**。它回答的是「哪些後門被走過」,
> 不是「閘門今天攔了幾次、攔了什麼」。

**兩者名字很像而問題完全不同**,這一格寫進票面是因為
上一輪我自己就把它們搞混過一次(說「其餘兩個呼叫點仍會寫帳本」,
漏掉了 `if not bucket` 那個條件)。
