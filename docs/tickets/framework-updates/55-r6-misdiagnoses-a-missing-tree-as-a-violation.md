## 為什麼不該躺在 backlog(三個條件同時滿足)

| 條件 | 內容 |
|---|---|
| **便宜** | 修法只有**一行的形狀**:進迴圈前先驗 `git cat-file -e <go-live>^{commit}`,不成立時給另一句訊息 |
| **有明確受害者** | **任何淺層 clone 上的每一次 commit** —— CI、`--depth` 取得的工作副本、下游的自動化 |
| **會主動誤導** | 見下 |

### 與其他 (c) 項的分別

> **其他 (c) 是「沒人在看」;這一則是「看了,而且指錯方向」。**

它會**主動把人推向刪清單條目** —— 那是讀到「新檔案要走紅燈,不是往豁免名單裡加」
之後最合理的下一步。而:

1. 刪掉之後,**一份本來正確的清單被改壞**
2. 而 **R6 仍然紅**(樹還是不在)
3. 於是人會繼續刪,直到清單空掉,**而它從頭到尾都是對的**

> **一個方向正確而理由錯誤的擋下,比不擋更耗人。**
> 不擋的話人自己查;擋了並給錯理由,人會先照著錯理由做,
> **而且做完之後現象沒變,他會以為自己做得還不夠**。

`fail-closed` 保證的是「**擋不擋**」,不是「**為什麼擋**」——
而**人是照理由行動的**,不是照擋不擋行動的。

## 為什麼不在原票修

票 54 是**裝 CI**。修 R6 要動**權威層規則的判定路徑** ——
那是每一次 commit 都會跑的程式碼,規模與「裝 CI」不相稱,
而且它需要自己的紅燈(至少兩條:淺層下給新訊息、正常違規下仍給原訊息)。

票 54 當下的正確處置是 `fetch-depth: 0`:**讓 CI 不要踩到它**,
而不是**在裝 CI 的過程中改權威層規則**。

## 已知代價(不修的話)

- 任何淺層 clone 上 **R6 擋下每一次 commit**,而且**九條理由全是錯的**
- 而錯的理由**看起來完全合理** —— 它是一句通順、具體、帶規則代號的判定
- 這個缺陷**本機結構上碰不到**(本機的 clone 一直是完整的),
  所以它只會在**別人的環境**裡出現 —— 而那個人手上沒有這份紀錄

### 四、測試(紅燈先行,4 條)

`tests/test_gate.py::TestR6SeparatesAMissingCommitFromAMissingPath`:

| # | 驗什麼 | 開工當下 |
|---|---|---|
| ① | commit 不在 → 新訊息、帶 sha、帶 `--unshallow`、**不含「清單只減不增」** | 🔴 **紅** |
| ② | commit 在、路徑不在 → **原訊息一字不改**,且不含新訊息的關鍵字 | ✅ 綠(**必須維持**) |
| ③ | 兩者皆正常 → **不擋** | ✅ 綠(**必須維持**) |
| ④ | **非空性**:兩條路徑的訊息不得只差幾個字,各自**只**含自己那一半的關鍵字 | 🔴 **紅** |

**④ 為什麼要有**:少了它,「兩種原因都說得出來」可以靠**一句話裡塞兩種可能**
滿足 ——「不在樹裡,或者 commit 不在這個 repo」。
**那種訊息每一次都對,而它每一次都沒有指出是哪一個。**

### 五、🔴 一個測試構造的陷阱 —— 被本類自己的前提斷言抓到

①④ 要「另一個 repo 的 sha」。第一版兩個 repo 用**同一份內容、同一個 commit
訊息、同一個身分**建 —— 而 **git 是內容定址的**:樹一樣、訊息一樣、
時間戳落在同一秒,**兩個「互不相干的 repo」算出來的 commit sha 完全相同**。

```
E  AssertionError: 測試的前提垮了:另一個 repo 的 commit 竟然在這裡找得到
E  assert 0 != 0
E    where 0 = ...(['git','cat-file','-e','077dcba8…^{commit}'], returncode=0)
```

> ### **「另一個 repo」不等於「另一個 sha」。**
>
> 而它失效的樣子是 **測試綠**(那個 sha 在這裡真的找得到)——
> 若沒有那句前提斷言,①④ 會變成兩條**驗錯東西而且看起來通過**的測試。

**處置**:`_repo()` 加 `body` 參數,兩個 repo 內容不同;理由寫進它的 docstring。
**不用 `"0" * 40`**:git 對全零 sha 有特殊語意(null sha),
拿它當樣本測到的可能是那個特例,不是本票的情境。
