## 二、定性 —— 這一條為什麼比「文件過期」重

> ### **這個 repo 的整個論點是「證據要能被查證」,而它自己的 129 個證據指標全部斷了。**

`CLAUDE.md:312` 逐字:「不用『已修正』『已確認』這類宣稱句 ——

票面上那些 `` `52557eb` `` 就是那個「讓人自己看得出來」的裝置。
它們現在**指向不存在的東西**,而畫面上與有效的引用一模一樣。

**同族但更重**:`F-122`(票面裡的內容快照是沒有人在守的副本)。
那則講**內容**會過期;本則講**指標**會斷,而
**指標斷掉比內容過期更難發現** —— 過期的內容還讀得下去、還會被質疑;
一個 7 位十六進位字串**看起來永遠是對的**,直到有人真的去 `git show` 它。

**與盤點表第 13 條(R9 只查重複、「改指所有引用」那半無機器)是同一個形狀:

## 四、🔴 修理:**不得無腦批次替換**(寫死,不得在實作時被磨掉)

看起來這是一支 30 行的 `sed`:拿 commit-map 的 old → new 逐筆替換。**不是。**

### 四之一、至少有一類引用是**刻意保留舊 sha 的**

```
$ git log -1 --format=%B b91f1f6 | grep -n e7702c8
27:交接說「輪替 e7702c8 已落地,不用重做」。實查不成立:
29:    $ git show --stat e7702c8
30:    fatal: ambiguous argument 'e7702c8': unknown revision or path not in the working tree.
33:    216:e7702c8e46bd5e9de11c141154a1f4f8000a4ab6 1337aea5a3efc00275ba51bd16ee588140fa94cc
41:e7702c8 是票 84 身分改寫前的舊雜湊,對到 1337aea
```

**那 2 筆是刻意引用舊 sha 來記錄「舊 sha 解不開」這件事的原文。**
批次替換會把它們改成新 sha,於是那段紀錄**在講一件它不再示範的事** ——
一段說明文字被改成與它要說明的現象相反。**照 `F-036`:舊文不改。**

### 四之二、還沒查的三件(動工時要先查,不得憑印象)

1. **哪些引用在 `code fence` 裡**(逐字原文,通常不該動)vs **在散文裡**(指標,該回填)
2. **票 39 那一期的 sha** —— commit-map 有兩份
   (`2026-08-15-ticket39-…` 與 `2026-08-27-identity-rewrite-…`),
   **一個舊 sha 可能要走兩跳才對得到現在的**。只套第二份會得到一個仍然解不開的 sha,
   **而它看起來像修好了**
3. **7 位縮寫的碰撞**:`git cat-file` 對縮寫 sha 可能回 `ambiguous`,
   替換前要確認 old 欄前綴在現庫裡唯一

### 四之三、回填的形式待裁(兩個方向,現在不選)

| | 做法 | 代價 |
|---|---|---|
| **就地替換** | 舊 sha → 新 sha | 讀的人看不出這裡改寫過;而**改寫這件事本身是 `F-0015` 的已知項** |
| **加註不替換** | 舊 sha 旁註「(票 84 改寫前;現為 `<新>`)」 | 散文變長;但**保留了「當時寫的是這個」這個事實**,與 `F-036` 同向 |
