### Phase 1 的四個實質發現

**發現 1 —— 兩個 repo 沒有任何 remote,合計 78 個 commit 只存在這台機器上。**
其中一個還帶著兩個**整包未追蹤的目錄**。

這是本次盤點裡最大的單點風險,也是**最便宜的一步**——開私有 remote 推上去,不必等 Phase 2。

**發現 2 —— G1 保護清單只列目錄,`<資料目錄>` 根目錄的憑證檔沒被涵蓋。**
G1 第一級是**前綴比對**;清單裡沒有涵蓋根目錄那一層,於是散在那裡的多份憑證檔

家目錄底下幾個憑證存放目錄同樣不在清單裡。
→ 這不是本票要修的東西,但**要開票**。修法是加進保護清單,而那一步只有人能做(ADR 0009)。

**發現 3 —— `leak_scan` 的 `CERT_EXT` 漏掉兩種憑證副檔名(PKCS#8 私鑰與 PKCS#7 簽章包)。**
`CERT_EXT` 是「副檔名即判定、不掃內容」,那條路徑是 F-062 紅燈換來的
**二進位憑證唯一可靠攔截點**。這兩種副檔名不在裡面 → 退回**內容比對**那條較弱的路徑。
本機實際存在這兩種檔案,實測是 PEM 文字,通用 pattern 的私鑰標頭式**應該**打得到——
但「應該打得到」不是「保證擋得住」,而 F-062 的教訓正是別依賴內容比對。
→ **要開票**。

**發現 4 —— 兩邊的影子/豁免證據都沒有 off-machine 副本。**
本 repo 的 `.gitignore` 擋掉整個 `/.dev/`;quant 那邊 `shadow-log.jsonl` 與 `shadow.json`
也各自被 gitignore。另有三份影子基線 `.jsonl` 散在工作台根目錄,**不在任何 repo 內、沒有任何規則管它們**。
→ **9/15 的影子晉升評估要靠這些數字。磁碟壞在 9/15 之前,晉升評估就沒有樣本。**
與票 21 是同一個晉升前提的兩面:票 21 管樣本**乾不乾淨**,這一條管樣本**還在不在**。

### 三、雙機引入的新問題(**本票不解,記錄待議**)

`machine-init.md` 目前假設「一台機器」。雙機常態化之後至少有兩件事沒有答案:

1. **保護清單在兩台機器上會分歧** —— 清單是照**該機器實際存在的路徑**寫的
   (machine-init 第二節末的關鍵警告),筆電的磁碟結構與桌機不同,
   所以兩份清單**本來就不該相同**。那 sha 核對要核什麼?

### 具名原則:「依構造唯讀」與「已驗證未動」是不同強度的兩句話

> 判準:報告的強度要對得起實際做過的觀測。

zip 內以 repo 名分頂層目錄,因為**證據脫離它的 repo 就失去意義**:
`test-runs.jsonl` 只有配上「哪個 repo 的哪張票」才解釋得動。
