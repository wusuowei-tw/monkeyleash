## 為什麼不記原文(裁決給定的理由,展開)

> 原文含路徑與個資,會讓 `shadow-log` 變成新的洩漏面,
> 而它已經是備份與 G1 的保護對象。

三件各自獨立的事實,合起來讓「記原文」變成不划算:

1. **指令原文含路徑**,而路徑含使用者名、專案名、有時是真實資料夾名 ——
   F-082 / F-085 那一族(**已經推上遠端的真實資料夾名**)正是這個形狀。
2. **`shadow-log.jsonl` 不進版控**(實測:`git ls-files .dev` 只有 5 個檔,
   不含它),所以它的存續靠週級人工備份 —— **備份會被複製到別的地方**,
   而複製會讓洩漏面跟著擴散。
3. **它是 G1 的保護對象**,也就是一個「不該被輕易改動」的檔案 ——
   往這種檔案裡塞更多敏感內容,等於提高它自己的處置成本。

> **判準:一個檔案越難刪改,往裡面寫東西就越要保守。**

## 要記什麼

| 欄位 | 內容 | 為什麼 |
|---|---|---|
| `cmd_sha256` | 指令原文的 sha256 | **同一條指令再出現時對得起來**,而雜湊本身不洩漏內容 |
| `cmd_head` | 前 N 字(**N 待定**) | 讓人看得出「這是哪一類指令」(`python -c`、`git commit`、`printf`) |
| `cmd_len` | 原文長度 | 前 N 字被截斷時,知道截掉了多少 |

### 設計時要先答的

1. **N 是多少?** 太短分不出類別,太長就是變相記原文。
   **判準不是「多少字夠用」,是「多少字之內不會出現路徑」** ——
   而 `cd "c:/Users/…"` 這種指令**第一個字就是路徑**。
   ⇒ **可能需要的是「前 N 字**再過一次 `leak_scan` 的遮罩**」,而不是純截斷。**
2. **`cmd_head` 要不要過現有的遮罩管線?** `leak_scan.py` 已有 pattern 清單。
   複用它是對的 —— **不要寫第二份遮罩**(兩份會漂移,而漂移的那天沒有人發現)。
3. **雜湊要不要加鹽?** 不加:同一條指令在不同 repo 要對得起來。
   加了就只能在同一個 repo 內比對。**傾向不加**,因為它不是密碼、是指紋。
4. **舊紀錄怎麼辦?** 新欄位缺席時,`shadow_review` 不得當成錯誤 ——
   否則本票一落地,現有 222 筆全部讀不動。**向後相容是硬需求**,
   而它需要一條測試(舊格式紀錄仍可讀)。
5. **`gate.py` 的哪一層有指令?** R7 是 Bash hook,拿得到 `tool_input.command`;
   而 R1–R6 的觸發物是**檔案寫入**不是指令 —— 那些紀錄要記什麼?
   **不要為了欄位齊整而編造一個「指令」** ——
   沒有的就是沒有,欄位缺席比欄位填「N/A」誠實。

## 已知的連帶

- **`shadow_review` 的 `record_id` 會改變。** 它是「除 `classification` 外全欄位」
  的雜湊(票 64),所以加欄位 = 舊紀錄與新紀錄的身分算法涵蓋不同欄位。
  **舊紀錄的身分不會變**(它們沒有新欄位),但這件事要有測試釘住,
  否則已發出去的套用卡會在某天指不到東西。
- 觀測動作會推高日誌筆數(F-070),而本票會讓每一筆變長 ——
  檔案成長速度變快,**而它靠週級人工備份**。
