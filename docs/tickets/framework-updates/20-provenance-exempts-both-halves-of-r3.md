# 20 — provenance 豁免 R3 兩半,不只紅燈半

## 缺口

`upstream_backed()` 目前只豁免 R3 的**紅燈半**,前半(對應測試檔要存在)照常適用。
那段程式碼的註解寫著它的正當性:

> 前半(測試檔要存在)照常適用 —— **同步本來就會把測試一起帶過來**,
> 所以那一半不需要放寬。

**那個前提對「上游自己不出貨測試的檔案」為假。** 實測(2026-08-13,4a8ca4d):

```
.claude/portable/g1_verify.py      tests/test_g1_verify.py       無
.claude/portable/shadow_review.py  tests/test_shadow_review.py   無
.claude/portable/verify_gates.py   tests/test_verify_gates.py    無
```

三支都在 `copy` 桶,下游一納管 R3 前半即紅,而**下游沒有合法解**:

- legacy 清單只減不增,而且入場券是「在**該 repo** 上線 commit 的樹裡」
- 下游自己補測試 —— 那份測試不是上游的成品,與 F-0014 的前提(責任在上游)相衝
- 手寫豁免 = 自助,正是整套設計要防的

**同步救不了**:上游沒有那個檔案可帶,再同步幾次都一樣。

順帶查證:**上游自己也編輯不了這三支**(同樣卡在 R3 前半)。
它目前的「安全」只是因為沒有人去改它們 —— 與 gate.py 那次的死結同型。

## 裁決

**provenance 成立(與上游那個 commit 的物件逐位元組相同)⇒ 豁免 R3 兩半。**

理由是責任歸屬,不是方便:整個 R3 問題(有沒有測試、紅過沒有)的責任在上游。
**下游不得對進口成品要求比上游對自己更多的紀律。**

### 這條性質最好的地方:它會自己收緊

上游日後替 `g1_verify.py` 補上測試,`sync` 就把測試一起帶下去,
下游的 R3 前半自然成立 —— **零下游動作**。
豁免不是永久的洞,是一個隨上游品質自動關閉的窗。

## 邊界(不變)

- **漂移的檔案兩半照常**:本地改過一個位元組就不再是「上游的成品」
- **沒有證的新檔案照常紅**:R3 對本地寫的碼完全不變
- **不碰 R2**(票 10)、**不碰 R8**:R8 在 R3 之前,進口成品若 import research 照樣擋
- 驗證仍然對到上游的 git 物件,不採信 provenance 宣稱的 hash(F-0014)

## 怎樣算做完

- 有證、上游無測試檔的檔案 → R3 完全不擋
- 同一個檔案本地改一個位元組 → R3 兩半都回來
- 沒有證的本地新檔 → 照常紅(前半後半都在)
