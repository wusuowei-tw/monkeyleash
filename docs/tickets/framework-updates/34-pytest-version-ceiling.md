# 34 — `pytest>=8.0` 沒有上限:設,或把「不設」寫成決定

**排程**:穿插,低。**無紅燈**(相依設定 + 決定紀錄)。

**來源**:換機器演練卡點 #9(**風險已解除,保留為事實**)。

## 事實

`pyproject.toml` 寫 `pytest>=8.0`,**沒有上限**。
新機器安裝時拿到當下最新版 —— 演練那台拿到 **9.1.1**,桌機是 **9.0.3**。
**兩台機器跑的不是同一個測試執行器,而且跨了一個大版本。**

## 風險已解除,但事實留著

解凍後的交叉驗證:同一份 **611 條在 9.0.3 與 9.1.1 兩個大版本上全綠**。
所以這不是一個待修的缺陷,是一個**待決定的取捨**。

## 兩個方向,選一個並寫下理由

**A. 設上限**(例如 `pytest>=8.0,<10`)

- 好處:兩台機器、CI、將來的第三台拿到同一個大版本區間,**紅燈的成因少一個維度**
- 代價:上限會過期。而過期的上限**不會出聲** —— 它只是安靜地擋住升級,
  直到有人去查為什麼裝不上新版。這與本 repo 一路在打的「靜默」是同一族

**B. 不設,但把「為什麼不設」寫成決定**

- 好處:永遠拿得到最新的執行器;而**跨版本全綠本身就是一種涵蓋**
  (框架測試若依賴某個 pytest 版本的行為,那是測試寫壞了)
- 代價:出現非預期紅時,**版本是一個要先排除的嫌疑**,而人未必想得到

## 建議(不預設,供裁決)

傾向 **B**,理由是本 repo 的測試**刻意不依賴執行器行為**
(斷言的是訊息內容與檔案狀態,不是 pytest 的輸出格式)。
跨大版本全綠是那個設計的證據,設上限反而會讓那個證據停止產生。

但 B 只有在「**撞到非預期紅時真的會先排除版本**」時才成立,
而那要靠人記得 —— 所以 B 的落地不是「什麼都不做」,是:

1. `pyproject.toml` 註解寫明**為什麼沒有上限**
2. 那句話裡要包含**該怎麼排除嫌疑**(`python -m pytest --version`,兩台比對)
3. `machine-init.md` 已經有一句(演練當天補的),與註解互相指

## 怎樣算做完

- 選 A 或 B,**決定寫在 `pyproject.toml` 的註解裡**,不是只寫在票裡
  (票會被讀一次,註解在每次改相依時都被讀到)
- 若選 B:排除嫌疑的方法可執行,不是「注意一下」
- 若選 A:上限過期時**會出聲**的機制要一併想 —— 否則只是把靜默換個地方

## 落地紀錄(2026-08-15)—— 裁決選 **A**

建議欄寫的是 B,裁決選 A。照票面實作,**無紅燈**(相依設定 + 決定紀錄)。

### 上限值:`pytest>=8.0,<10`

**線畫在實測證據的邊界上,不是猜 pytest 的路線圖。**

| 版本 | 證據 |
|---|---|
| 9.0.3(桌機)、9.1.1(演練那台) | 同一份測試**兩台全綠**,跨了一個小版本 |
| 10.x | **一條也沒有** |

所以 `<10`。這個理由的好處是它**可被推翻也可被推進**:哪天有人在 10.x 上跑
全綠,證據邊界就往前移一格,上限跟著移 —— 而不是去爭論「pytest 會不會破壞相容」。

**下限 `>=8.0` 沒有動,而它同樣沒有實測證據**(沒有人在 8.x 上跑過這套)。
這個不對稱是知道的,寫進 `pyproject.toml` 註解裡而不是留在腦子裡。
本票只處理上限,不順手改下限。

### A 的代價:照票面一併處理

票面說得很準:「上限會過期。而過期的上限**不會出聲**。」
**光設上限只是把靜默換個地方** —— 從「兩台機器版本不同」換成
「新版裝不上而沒人知道為什麼」。所以上限不是單獨存在的:

- `pyproject.toml` 的 `[tool.agent-gates] pytest-ceiling-review = "2027-02-15"`(半年)
- `tests/test_dependency_ceiling.py` 三條:

| 守什麼 | 破壞時 |
|---|---|
| 上限**還在** | 有人刪掉上限 → 紅 |
| **實際裝的**那版在區間內 | 手動 `pip install -U pytest` 繞過宣告 → 紅 |
| 複審日**還沒過** | 到期 → 紅,並印出複審程序 |

**一條會在某天自己轉紅的測試是刻意的。** 上限的危害正是它不會自己出聲,
而不依賴網路、不依賴有人想起來的觸發器只有時間。訊息第一句就寫
「這條紅燈不是壞掉,是它在做它被寫出來要做的事」。

複審程序寫在測試訊息裡(裝新大版本 → 跑全套 → 全綠才把上限與日期**一起**往上推),
最後一句是「不要只改日期不做前兩步 —— 那會把這條測試變成一個沒有內容的儀式」。
這是這個機制唯一真正的失效方式,所以它被寫在人唯一會讀到的地方。

### 刻意不用 `tomllib`

`requires-python` 是 `>=3.10`,而 `tomllib` 是 **3.11** 才進標準庫。
在 3.10 上 `skip` 掉等於這一檔**在最舊的支援版本上靜靜消失** —— 那正是本檔在防的東西。
兩個值都是單行、格式由本 repo 自己定,直接讀原文比引入版本分歧安全。
(附帶:複審日若寫在註解裡,toml 解析器**看不到** —— 它是真的 key,不是註解。)

### 負控(四條,各自確認會紅)

不動 repo 內的 `pyproject.toml`,把測試模組的 `PYPROJECT` 指到 scratch 假檔:

```
== 1 上限被刪掉      -> 紅  讀不到 `pytest>=X,<Y` 形狀的宣告
== 2 裝的版本超出上限 -> 紅  實際安裝的 pytest 9.0.3 落在宣告區間 [>=8.0, <9) 之外
== 3 複審日已過      -> 紅  複審日 2020-01-01 已經過了(今天 2026-08-15)
== 4 複審日整行不見   -> 紅  讀不到 `pytest-ceiling-review = "YYYY-MM-DD"`
```

第 4 條是分開驗的:**「值過期」與「值不見」是兩件事**,而後者才是重構時
容易悄悄產生的形狀(與票 13 那個空括號同族)。
