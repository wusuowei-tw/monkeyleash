# 34 — `pytest>=8.0` 沒有上限:設,或把「不設」寫成決定

**排程**:穿插,低。**無紅燈**(相依設定 + 決定紀錄)。

**來源**:換機器演練卡點 #9(**風險已解除,保留為事實**)。

## 事實

`pyproject.toml` 寫 `pytest>=8.0`,**沒有上限**。
新機器安裝時拿到當下最新版 —— 演練那台拿到 **9.1.1**,桌機是 **9.0.3**。
**兩台機器跑的不是同一個測試執行器,而且跨了一個大版本。**

## 風險已解除,但事實留著

解凍後的交叉驗證:同一份 **611 條在 9.0.3 與 9.1.1 兩個大版本上全綠**。
所以這不是一個待修的缺陷,是一個**待決定的取捨**。

## 兩個方向,選一個並寫下理由

**A. 設上限**(例如 `pytest>=8.0,<10`)

- 好處:兩台機器、CI、將來的第三台拿到同一個大版本區間,**紅燈的成因少一個維度**
- 代價:上限會過期。而過期的上限**不會出聲** —— 它只是安靜地擋住升級,
  直到有人去查為什麼裝不上新版。這與本 repo 一路在打的「靜默」是同一族

**B. 不設,但把「為什麼不設」寫成決定**

- 好處:永遠拿得到最新的執行器;而**跨版本全綠本身就是一種涵蓋**
  (框架測試若依賴某個 pytest 版本的行為,那是測試寫壞了)
- 代價:出現非預期紅時,**版本是一個要先排除的嫌疑**,而人未必想得到

## 建議(不預設,供裁決)

傾向 **B**,理由是本 repo 的測試**刻意不依賴執行器行為**
(斷言的是訊息內容與檔案狀態,不是 pytest 的輸出格式)。
跨大版本全綠是那個設計的證據,設上限反而會讓那個證據停止產生。

但 B 只有在「**撞到非預期紅時真的會先排除版本**」時才成立,
而那要靠人記得 —— 所以 B 的落地不是「什麼都不做」,是:

1. `pyproject.toml` 註解寫明**為什麼沒有上限**
2. 那句話裡要包含**該怎麼排除嫌疑**(`python -m pytest --version`,兩台比對)
3. `machine-init.md` 已經有一句(演練當天補的),與註解互相指

## 怎樣算做完

- 選 A 或 B,**決定寫在 `pyproject.toml` 的註解裡**,不是只寫在票裡
  (票會被讀一次,註解在每次改相依時都被讀到)
- 若選 B:排除嫌疑的方法可執行,不是「注意一下」
- 若選 A:上限過期時**會出聲**的機制要一併想 —— 否則只是把靜默換個地方
