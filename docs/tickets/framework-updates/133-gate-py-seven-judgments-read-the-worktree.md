## 命題

**與票 132 完全同一句話,只是換了一支檔案**:判定吃檔案內容,而內容來自**工作樹**;
`git commit` 寫進歷史的是 **index**。於是三步繞過:

```
① git add <違規版>   ② 工作樹改回合規版(不重新 add)   ③ git commit
```

③ 的 pre-commit 讀工作樹、看到合規版、放行;而進歷史的是 index 那份違規版。

## 修法方向(立案不定死,但這是起點)

**本票不是「發明一個新東西」,是「把已經寫對的那一支接到它其餘的消費者身上」。**

`gate.py:1957` 已經有 `staged_blob()`,而它的 docstring **逐字寫著這個攻擊形狀**:

```
    **為什麼不是工作樹**:commit 要判的是**要進 commit 的那一份**。
    工作樹與 index 可以不同(`git add` 之後又改了一次),而讀錯對象的失敗方式是
    **靜默的** —— 兩者多數時候一樣,所以日常與測試都不會發現,只有在
    「先 add 一份乾淨的、再把工作樹改壞」時才漏,而那正是要防的形狀
    (票 07 / F-046 那條「判定對象」的判準換到提交時點)。

    **取不到一律 `None`,呼叫端不得退回工作樹** —— 退回去就是判錯對象,
    而且是往 fail-open 的方向錯。
```

而它目前**只有一個消費者**(票 132 量):

```
$ grep -n "staged_blob" .claude/hooks/gate.py
1957:def staged_blob(rel_path):
2002:    raw = staged_blob(rel_path)      <- upstream_identical_staged,R2 內容豁免,票 10
```

⇒ **判準寫對了、實作寫對了、接了一個消費者,然後停在那裡。**
這正是 CLAUDE.md 那條的形狀:**註解不是機制**;而本則比 `F-086` 更難察覺一階 ——
判準不在隔壁模組,**在同一支檔案裡,而且已經被正確實作過一次**,
所以「有沒有人想過這件事」搜得到,**搜到的那一個正是唯一被守住的那一格**。

### 起點清單(不是裁決)

- **只換位元組的來源,不換判定** —— 票 132 的形狀:`read_text` 那一半原封不動。
  `gate.py` 這邊對應的是 `read_text_or_none`(`gate.py:1095`,工作樹)
  與一條新的 index 版本,共用同一套解碼階梯(`TEXT_ENCODINGS`)。
- **`at_commit` 已經是現成的分岔點。** `check(path, content, at_commit=True, …)`
  在提交時走的那一條就是要換來源的那一條;前哨那一條(工作樹 + `content_after_edit`)
  **不動** —— 前哨判的是「這次寫入之後檔案會有的內容」,那本來就不是 index。
  ⚠ 這件事要先查證再下手,形狀同票 132 對 `--review` 的查證:
  **共用一個讀取函式不等於共用一個正確對象。**
- **R4 的修法是不對稱的**(見上),不能套用同一個機械式替換。
- **R6 有兩個讀取點**(清單 + go-live sha),而 go-live sha 是**清單檔第一行**——
  兩者來自同一個檔案,所以換來源要一起換,否則會出現「用新清單的 sha 驗舊清單的條目」。

## ⚠ 爆炸半徑 —— 動工時的**硬條件**,現在就寫進票面

`gate.py` 是權威層本體。任何一格改壞、往 fail-closed 的方向斷掉,結果是
**【沒有人能 commit,包含修它的那一次】**。

所以動工時:

1. **一次只改一格。** 每格改完**立刻實跑** `python .claude/hooks/gate.py --pre-commit`
   並看 `rc` —— 確認 commit 路徑還活著。
2. **不接受「七格一起改完才第一次驗證」。**
3. **動工前先想好退路,寫在下面。**

### 退路(現在就寫,不等動工)

**第一條,而且是唯一不依賴「能 commit」的那一條:**

```
git checkout -- .claude/hooks/gate.py        （或 git restore .claude/hooks/gate.py）
```

**`checkout` / `restore` 不跑 pre-commit hook** ⇒ 這條復原路徑
**不需要先讓閘門變好才能用**。這是選它當第一條的唯一理由 ——
**復原路徑不得依賴那個壞掉的東西**。
動工前要先確認 HEAD 那一份是好的(也就是:**動工的第一步是先 commit 一個乾淨基準**)。

**第二條(break-glass,只在第一條也不可用時)**:

```
git config --unset core.hooksPath            # 暫時卸下權威層
…修好…
git config core.hooksPath .githooks          # 裝回去（bootstrap.sh 設的就是這一行）
```

掛載點是 **per-clone 的 local config**(`docs/adr/0007`),所以卸下與裝回都是一行,
**而且卸下的狀態是看得見的**(`.claude/portable/status.py` 的 `authority config` 會印設定值,
票 27)。**選它而不選 `--no-verify` 的理由**:`--no-verify` 在 git 裡
**不留任何痕跡**(commit 上沒有標記、reflog 也不記 —— `gate.py:3348-3357` 逐字記過
「宣稱一個不存在的機制比不寫更糟」),而卸下 config 這件事查得出來。
**⇒ `--no-verify` 是最後手段,不是退路。**

**第三條(結構性,不是應急)**:動工放在**自己的分支**上,
`master` 隨時有一個閘門是好的 commit 可以回去。

## 紅燈先行(**本輪只寫規格,不寫測試**)

**每一格兩條**,合計七格 × 2:

| 條 | 主張 | 為什麼少了它會壞 |
|---|---|---|

**假樣本一律取現有測試語料庫已在用的組裝樣本,不憑空發明新字串。**
