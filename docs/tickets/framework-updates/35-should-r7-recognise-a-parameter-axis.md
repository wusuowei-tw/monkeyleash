# 35 — R7 要不要認「參數決定的寫入」這第二個判定軸?

**排程**:**低優先,本季後。** 這是設計問題,不是活洞。

**來源**:票 29 第三類調查的異構項(唯一一個有受管替代路徑的)。

## 事實

`Invoke-WebRequest -OutFile pkg/thing.py` 與 `Invoke-RestMethod -OutFile …`
**會把任意 URL 的內容寫進工作樹**,而 R7 現在整條放行。

R7 現行的判定軸是**動詞**:指令位置的 token 在不在寫入者名單裡。
而 `Invoke-*` 的動詞是 `Invoke` —— **語意上完全看不出在寫檔**,
寫不寫取決於**有沒有給 `-OutFile`**。

**那是第二個判定軸(參數),而 R7 目前只有一個。**

## 為什麼它與票 29 的「已知邊界」不同類

票 29 把 `*-ItemProperty` / `Set-Acl` / `New-TemporaryFile` 列為邊界,
理由是**沒有受管替代路徑** —— 收它們就是票 13 的罪(建議一個不存在的出口)。

**`-OutFile` 有替代路徑**:抓取工具取內容 + `Write` 落檔。
所以「擋它」是**可辯的**,不會把人逼進死路。代價落在別處,見下。

## 代價(這才是本票要權衡的東西)

### 1. 軸擴張

加一個判定軸,不是加一個名字。往後每一條規則都要問「這一軸涵蓋了嗎」,
而**兩軸的交互作用是新的錯誤面**:
`Invoke-WebRequest` 在動詞軸放行、在參數軸擋下 —— 誰贏?
交互規則寫錯的方向通常是 fail-open,而那正是 R7 收口要避免的。

### 2. `Invoke-*` 家族的誤擋面

`Invoke-*` 家族極大,**絕大多數不寫檔**。
- 用**動詞**收 → 過度:`Invoke-Expression`、`Invoke-Command`、
  `Invoke-Pester` 全被擋,而它們多半只是執行
- 用**參數**收 → 回到 `-FilePath` 那個歧義:同一個參數名在不同 cmdlet
  可能是輸入也可能是輸出(票 29 實測:`Tee-Object -FilePath` 是輸出、
  `Start-Job -FilePath` 是輸入腳本)

票 29 之所以能安全使用路徑參數清單,**是因為有動詞閘先過濾** ——
參數軸一旦獨立運作,那個中和就沒了。**這是本票最關鍵的一句。**

### 3. 涵蓋不完的老問題

`curl -o`、`wget -O`、`Start-BitsTransfer -Destination`、
以及任何「自己算路徑再寫」的腳本,同樣是參數決定的寫入。
收一個不收其餘,又回到 R4 那個形狀:**讀起來在守,實際只守一部分。**

## 候選方向(未裁決)

1. **不收,寫成邊界** —— 與票 29 那三項同列,理由改成「軸擴張的代價大於收益」
2. **只收 `-OutFile` 這個具體參數,且限定在已知的少數 cmdlet 上** ——
   可列舉、不擴張軸(等於把它們當成動詞收)。最小,但涵蓋面窄且要維護名單
3. **正式引入參數軸**,連同交互規則與誤擋面一起設計

**判準建議**:先問**這條路徑實際被用過幾次**。
R7 的收口是為了把日常寫入逼回檔案工具;
如果 `-OutFile` 在這個 repo 的工作流裡從來沒出現過,
那它是**理論缺口**而不是活洞 —— 而理論缺口的修法優先序低於任何一條實際發生過的。

## 怎樣算做完

- 三個方向擇一,**理由寫下來**(尤其若選 1,要寫清楚為什麼「有替代路徑」仍不收)
- 若選 2 或 3:`curl -o` / `wget -O` 一併處理,否則就是新的「只守一部分」
- 不論選哪個,**票 29 的動詞閘中和機制不得被破壞** ——
  參數清單獨立運作的那一刻,`Start-Job -FilePath` 就會被誤擋
