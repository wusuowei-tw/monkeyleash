## 判準(存為原句)

> **達不到這些條件,批次核准即等於裸奔。**

這句話的作用不是修辭 —— 它把「要不要用批次」從**偏好問題**改成**條件問題**。
偏好可以妥協,條件不行:**四件套缺一件,批次就不是「風險稍高的批次」,
是另一種東西。**

---

## 為什麼暫不採用(回件第一部分的四點,不摘要,見原檔)

四點裡對本 repo 打得最準的是第 2 點 —— 它**逐一檢查了我們既有的防護網**,
結論是**四類裡有兩類會在批次模式下失守**:

| 回件檢查的實例 | 判定 |
|---|---|
| 複本演練那 30 檔誤傷 | **失守** —— 那一頁靠「執行者自行叫停」擋住,不是靠機制 |
| 身分洩漏在 force-push 前被擋 | 存活(機制層:hook / 閘門) |
| `sync` 兩次正確拒絕 | 存活(機制層) |
| 驗證在自身的假綠燈被抓到 | **嚴重失守** —— 綠燈對 agent 就是綠燈 |

**第 4 類是這次開刀期間真實發生過三次的形狀**(F-090 表示法不一致、
F-091 判準與實作不一致、以及 25 的過度嚴格)。三次都是**人**在讀報告時
察覺數字不對才回頭查 —— 在批次模式下,那三次都會被寫進「已完成」。

## 門檻四件套(要重啟就要全部到位)

### 一、機制化的煞車條件

**煞車條件不能寫在提示裡,必須由外部資源或 hook 物理阻斷。**

- 檔案存取白名單:碰到白名單以外的檔案即強制終止
- 測試框架鎖定:禁止建立 / 修改 / 刪除驗證器或測試碼本身
- 指令執行黑名單:除指定的編譯 / 測試 / git 基礎指令外,拒絕未經授權的 shell

> 回件的判準句:**說明會隨 context 變長而漂移,機制不會 —— 機制只變數據閘門。**

**本 repo 現況**:R7 已是「入口收成一個」的形狀、G1 是使用者層物理阻斷 ——
**兩者都已經是機制而不是說明**,這一件的基礎比回件假設的好。
缺的是「測試框架鎖定」:目前**沒有任何規則禁止 agent 改測試碼**。

### 二、票面的機器可讀欄位

票面不能只有文字敘述,要有:

| 欄位 | 內容 |
|---|---|
| `Scope_Whitelist` | 精確到具體檔案路徑 |
| `Exit_Condition` | 明確的測試指令與預期 stdout 特徵字串 |
| `Pre_Batch_Snapshot` | 批次前強制建立的 commit hash 或 stash id |

**本 repo 現況**:票面全是散文。`Pre_Batch_Snapshot` 最接近 ——
票 39 的備份與 `APPROVED-*` 雜湊就是手工版的它。

### 三、最小證據集(**這一件是重啟前提**)

批次執行完必須**自動生成**,缺一不可:

- 檔案異動清單(路徑 + 增刪行數總量)
- 終端機指令全紀錄(所有 shell 指令與**完整** stdout / stderr)
- 最終紅綠燈:**由 test runner 直接輸出的原始報告**,不可由 agent 自行轉述

> **為什麼這一件是重啟前提**:另外三件是「防止越界」,
> 這一件是「越界之後看得見」。而回件第 4 類的失效(agent 誤判綠燈)
> **只有這一件擋得住** —— 前三件都假設 agent 的自我回報可信。

### 四、降級條件(自動退回逐步模式)

- 觸發任何一次機制層 fail-closed
- 同一任務節點連續兩次紅燈(代表方案無效、正在無意義試錯)
- 事後審計發現最終報告與 runner 實際輸出不符
