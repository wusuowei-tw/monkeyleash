# 08 — 豁免帳本記的是「評估事件」,不是「寫入」

## 事實(實測於 2026-08-12)

`.dev/gate-exemptions.jsonl` 有 19 筆 `gate-self-modification`,
而 `gate.py` 對 HEAD **位元組不變**。

`log_exemption()` 在 `check()` 裡被呼叫,位置在**判決之前**:
只要路徑落在 `GATE_SELF`,不管後面放行還是擋下,都記一筆。實測到的來源:

| 來源 | 實測 |
|---|---|
| 被 R3 擋掉的寫入嘗試 | 照樣記一筆 |
| 跑一次 `pytest tests/test_gate.py` | +1 筆(測試自己會 `check(".claude/hooks/gate.py", …)`) |
| 診斷用的 `python -c` 探針 | 記 |
| pre-commit 重掃 staged 檔案 | 記 |
| Read 工具讀取 gate.py | **不記**(matcher 沒有 Read) |

所以 19 筆與「19 次修改」沒有關係。**帳本從頭到尾沒有觀測過任何一個位元組。**

## 為什麼要修

ADR 0004 寫著:

> 搶修是罕見事件,某一輪出現十筆就不是搶修,是把後門當日常通道

這句話假設**一筆 = 一次修改**。實際上一筆 = 一次評估,而評估的來源包含測試執行。
於是這個門檻**刻度是錯的**:19 筆換到零提交變更是這個記錄單位的必然結果,
不是異常。照現況去對帳,會對著一個沒有意義的數字做判斷。

先補時間戳/站別/ticket 而不動記錄單位的話,只會讓一個刻度錯誤的訊號
**看起來更嚴謹** —— 那是 F-031 的形狀(壞掉的訊號訓練人忽略訊號),
而且對帳的人會更信任它。

## 決定的順序

1. **記錄點移到判決之後**,並且移出 `check()`。
   `check()` 是純判定函式,不該有副作用 —— 那個副作用正是「測試執行也記一筆」
   的來源。記錄屬於**強制點**(`mode_hook` / `mode_pre_commit`),
   那裡才有「真的有人要寫」這個事件。
2. 加 `outcome`(granted / blocked)與 `blocked_by`,讓「豁免真的被用掉」
   與「嘗試被後面的規則擋下」分得開。ADR 0004 的門檻只算 granted。
3. 加 `content_hash` / `result_hash` / `changes_bytes`,讓「位元組沒變」
   在帳本裡看得見 —— 這是本票的原始問題,不能只靠事後推論。
4. 最後才補 `ts` / `stage` / `ticket`。

## 怎樣算做完

- `check()` 不再寫帳本(有測試釘住:呼叫它前後帳本行數不變)
- 被擋下的嘗試記成 `blocked`,放行的記成 `granted`
- 一次無變更的寫入(結果與磁碟現況相同)記成 `changes_bytes=false`
- 跑一次完整測試套件,帳本**不增加任何一筆**
- 回答:改完之後,同樣的一輪操作會產生幾筆、分別是什麼
