# 13 — fail-closed 的訊息必須說出是哪一個前提沒滿足

**排程**:sync session 六步全部完成之後。不插隊。

**原標題**:「R7 沒有刪除出口」——(已作廢,前提是錯的,見下)

## 結論先講:R7 有刪除與改名的出口,是我把指令寫壞了

原本這張票斷言「R7 把寫入收口了,卻沒給刪除一條出口」,並據此把
`tests/test_install_defaults.py` 的改名、ADR 的 `F-` 改名都判為做不到。

**那個斷言是錯的。** 實測(2026-08-13,裁決者指出後):

```
git mv docs/adr/0013-... docs/adr/F-0013-...      -> 通過,無輸出
```

`git` 本來就在 `BASH_ALLOWED_CMDS` 裡。我先前寫的是:

```
cd "c:/Users/.../agent-gates" && git mv A B        -> 被 R7 擋
```

`bash_write_violation()` 的比對是**逐段**的:

```python
segments = [s.strip() for s in re.split(r"&&|\|\||;", cmd) if s.strip()]
if segments and all(any(seg.startswith(p) for p in BASH_ALLOWED_CMDS) ...):
    return None
```

第一段 `cd "..."` 不以任何許可前綴開頭 → 整條落出許可清單 →
掉進 `WRITE_CONSTRUCT` 檢查 → `mv` 命中 → 擋。

逐段比對本身是**對的**:少了它,`git status && rm -rf x` 會整條被許可。
錯的是我的指令形狀,以及我從一次失敗直接推論出「規則缺一條出口」。

## 真正的缺陷(移到本票範圍)

擋下訊息說的是:

> 這個 Bash 指令會寫入檔案,請改用 Write / Edit。

**那句話把人指向錯的修法。** 現場是「你的 `cd` 前綴讓許可清單失效」,
而訊息叫人去改用檔案工具 —— 而檔案工具**沒有**刪除/改名,
於是照著訊息做的人會得出「這件事做不到」的結論,然後發明一條繞路
(本票原本的結論:留著不刪,兩個檔案並存)。

這與 F-046 是同一個形狀:**擋得對,但訊息讓人去檢查一個沒問題的地方。**
代價在這裡具體化成一張寫錯前提的票、一個沒必要的重複檔案,
以及一條差點被改掉的守衛。

## 判準(裁決 2026-08-13,由 R7 那一例擴大)

> **fail-closed 的訊息必須說出是哪一個前提沒滿足。**

fail-closed 系統的故障是隱形的:它擋得對、方向對、什麼都沒壞,
所以**唯一的線索就是那句訊息**。訊息指錯方向的代價因此比一般錯誤訊息高一級 ——
它不只浪費時間,它讓人去修一個沒問題的地方,然後得出「這件事做不到」,
最後發明一條繞路(本票原本的結論就是這樣長出來的)。

## 範圍(兩例,同一個判準)

### 例一:R7 的逐段許可

- 若**某一段**落出許可清單而其他段命中,訊息要指出是哪一段,
  並說明「許可是逐段比對的」。現在的訊息完全不提這件事,
  只說「請改用 Write / Edit」—— 而檔案工具沒有刪除/改名,
  照著做的人會得出「做不到」。
- 不改判定邏輯,只改訊息。逐段比對維持原樣(它是對的)。

### 例二:provenance 的上游指標缺失

實測(2026-08-13)。provenance 有、`~/.claude/upstream-roots.txt` 沒有時:

```
[R3/紅燈] pkg/thing.py:測試檔存在,但沒有合格的紅燈紀錄。
     找不到紅燈紀錄檔 .dev/test-runs.jsonl —— 無法證明測試曾經紅過。
     跑一次測試讓紀錄長出來;讀不到紀錄一律不放行。
     先跑測試確認它在實作不存在時是紅的,再回來寫功能碼。
```

方向對(擋),但**完全沒提指標檔**。現場是「上游指標讀不到,
所以 provenance 豁免不成立」,訊息卻叫人去補本地紅燈 ——
而那對一個同步進來的成品**做不到**(那正是 F-074 開這條路的理由)。

訊息要能分辨三種情況:沒有 provenance 紀錄 / 有紀錄但指標檔讀不到 /
有指標但上游物件對不上。現在三種都印同一句。

## 怎樣算做完

- 擋下 `cd X && git mv A B` 時,訊息點名 `cd X` 是落出許可的那一段
- 擋下 `rm -rf x`(整條都不在許可清單)時,訊息維持現在的樣子
- provenance 的三種失敗各有各的訊息,而且都指向**真正沒滿足的那個前提**
- 每一種形狀各一條測試 —— 訊息內容要被斷言,否則下一次改動會靜默改掉它

## 增補(2026-08-14,換機器演練卡點 #6b)—— 目標欄是**空括號**

R7 誤擋字串字面量裡的 `>` 時,擋下訊息的目標欄印出來是 **`()`** ——
一對空括號。訊息說「這個 Bash 指令會寫到沒有被許可的位置(**()**)」。

**這比印出垃圾目標更糟一階。** 票 21 記的是抽取器產生 `,` 或 `7:` 這種
「具體而錯誤」的目標;空括號是**連錯誤的具體都沒有** ——
它宣告了一個位置、然後什麼都不說,人連「去查一個不存在的路徑」都做不到。

與本票既有的兩則同族(`--no-verify`「會留下紀錄」、「請改用 Write / Edit」):
**訊息在形式上完整、在內容上是空的**。前兩則描述了不存在的東西,
這一則描述了一個空白 —— 而版面看起來一樣正常。

怎樣算做完(併入下方清單):

- 抽不出可信目標時,訊息**不得留下空的目標欄**;
  要嘛不印那個欄位、要嘛明說「抽不出目標」(與票 21 候選方向 2 相扣)
- 「欄位存在但內容為空」的情況有一條測試 —— 那正是最容易在重構中悄悄產生的形狀

## 活標本(2026-08-14,票 27 負控)—— 建議了一個不存在的出口

票 27 的負控做完要撤除一個自己建的暫存檔,`rm -f <檔>` 被 R7 擋下,訊息是:

```
[R7][enforce] 這個 Bash 指令會寫到沒有被許可的位置(docs/.../zzz-negative-control-TEMP.md),請改用 Write / Edit。
```

**Write 與 Edit 都不能刪檔。** 所以這句「請改用」指向的是一條**不存在的出口** ——
不是「換個工具做同一件事」,是「這件事沒有任何被許可的做法」。

這比本票原本的標題更精確:R7 不只是**沒有**刪除出口,它還**宣稱有一個**。
與本檔另一則(`--no-verify` 那句宣稱了一個不存在的留痕機制)是同一個形狀:
**訊息描述了一個世界上不存在的東西**,而人會照著它去做,然後卡住。

處置:該次負控的暫存檔由裁決者手動刪除。**沒有繞道** ——
繞得過去的話這則就不會存在,而它正是本票要的證據。

怎樣算做完(併入下方清單):

- 刪除有一條被許可的路徑,或者訊息**明說「這件事只能由人做」**並給出指令
- 不論選哪個,訊息不得推薦一個做不到那件事的工具

## 增補(2026-08-14,票 26 併入)—— enforcement 訊息不得提示自身的繞過方式

`mode_pre_commit` 擋下時,訊息最後一行是:

```
如確定要略過:git commit --no-verify(會留下紀錄,請自行負責)
```

**擋下訊息不該教人怎麼繞過自己。** 這與本票既有判準是同一條的兩面:
訊息要說出**哪一個前提沒滿足**(讓人去修),不是提供一條**不必滿足前提的出口**
(讓人去繞)。前者把人推向修好,後者把人推向略過 ——
而被煩到的規則會被關掉,提示語等於幫它加速。

「會留下紀錄,請自行負責」那半句也撐不住:`--no-verify` 在 git 裡**不留任何紀錄**,
commit 上沒有標記、reflog 也不記。**那句話宣稱了一個不存在的機制**,
比不寫更糟 —— 它讓人以為有事後對帳,於是更放心用。

怎樣算做完(併入上方清單):

- 擋下訊息不含任何繞過指令
- 若確實需要一條逃生門,它要有**真的會留痕**的機制,而不是一句宣稱
- 訊息內容被斷言(同本票其他項:否則下一次改動會靜默改掉它)

### A(1 + 4 併案):訊息指向**真正的出口**

兩者同一個根因 —— 而正確的出口一直都在(`git` 在許可清單裡)。
**逐段比對機制一個字都沒動**,只改訊息。

```
$ cd docs && git mv a.md b.md
     **許可是逐段比對的**(`&&` / `;` / `||` 各算一段),而這幾段不在清單裡:`cd docs`
     其餘各段本來就許可 —— 把它們拿掉就過得了。
     **Write / Edit 不能刪除或改名** —— 這條的出口是 `git mv`(`git` 在許可清單裡)。
```

反控:一般寫入(`echo x > notes.txt`)的出口**仍然是 Write / Edit**,沒被蓋掉。

### B(5):刪掉繞過提示與假陳述

`--no-verify` 與「會留下紀錄」兩者都移除。後者是**假陳述** ——
git 對 `--no-verify` 不留任何痕跡,而宣稱一個不存在的機制**比不寫更糟**:
它讓人以為有事後對帳,於是更放心用。

改為:「上面每一項都指出了是哪一個前提沒滿足 —— 修掉它們再提交。」

### C(2):三態更正為**五態**,並拆開分支 3

`upstream_backed` 改回 `(bool, reason)`。五態:

| 態 | 訊息指向的修法 |
|---|---|
| 沒有 provenance 紀錄 | 這不是同步成品,紅燈責任在本地 |
| provenance 檔在但解析不了 | 修檔案(**與「沒有同步歷史」是兩件事**) |
| 上游指標檔不可用 | 修 `upstream-roots.txt` |
| 紀錄缺 `upstream_commit` | 修 **sync 產出的紀錄**,不是指標檔 |
| 上游物件問不到 / 內容漂移 | 對不上上游的樹 / 改過就回到本地責任 |

**`FileNotFoundError` 特別處理**:檔案不存在是**正常狀態**(這個 repo 從來沒同步過),
歸進「讀不動」會把正常情況說成故障,而人會去查權限與路徑 ——
與票 26 那個「讀不到清單」是同型錯誤。

**該層原因回報待後續**:`read_upstream_root()` 自己把「讀不到 / 格式不對 / 多行少行」
全收斂成 `None`,所以態三只能說「不可用(讀不到或格式不對)」——
**含糊而誠實**,不追下去。

### ⚠ 陷阱防護:tuple 恆為真

`(False, reason)` 在 `if` 裡**是真的**。呼叫端忘了解包,
**fail-closed 會被簽名改動整條翻成 fail-open** —— 每個同步進來的檔案都拿到豁免,
而測試全綠、訊息什麼都不說。

- **呼叫點清單**:`gate.py:1706` **僅此一處**(全 repo grep,含 tests)。已改為解包。
- **反控**:五個 False 分支**逐一驗證「仍然被擋」**,不是只驗 reason 對不對。
  **原因對了而擋沒了,是這一輪最貴的失敗方式。**
  這五條在改動前就是綠的,改動後必須**維持綠** —— 那才是它們的作用。

順帶:`upstream_backed` 在本輪之前**零測試涵蓋**。
