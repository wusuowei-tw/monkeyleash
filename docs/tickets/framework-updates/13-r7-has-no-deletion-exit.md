# 13 — R7 沒有刪除出口:檔案進得來,出不去

## 現象(2026-08-13,本批實際撞到兩次)

R7 把 Bash 的寫入收口回檔案工具。但檔案工具**只有寫,沒有刪**:

| 想做的事 | 走 Bash | 走檔案工具 |
|---|---|---|
| 建檔 | 被 R7 擋 | Write ✓ |
| 改檔 | 被 R7 擋 | Edit ✓ |
| **刪檔** | 被 R7 擋 | **沒有這個工具** |
| **改名** | `git mv` 被 R7 擋 | 只能 Write 新檔,舊檔留著 |

本批兩次撞到:

1. `tests/test_install_defaults.py` 不符 R3 的 `test_<name>.py` 慣例,
   對規則而言 `install.py` 沒有測試。正確處置是改名,但改名 = 寫新的 + 刪舊的。
   **權宜**:新增 `tests/test_install.py`,舊檔留著,兩個檔案並存。
2. ADR 改名(`0013` → `F-0013`)整批做不了,同一個原因。

## 為什麼這是缺陷而不是設計

R7 的理由是「從指令字串解析『寫到哪』解不完,所以入口收成一個」——
那個理由對**寫入**成立,對**刪除**一樣成立(`rm -rf` 的爆炸半徑更大)。
問題不在於它擋,而在於**收口之後那一側沒有對應的出口**:
規則把路關掉,卻沒有開另一條。

這是 F-046 家族的形狀:**沒有出路的規則,執行端會自己發明一條**(F-061 的配套判準)。
目前發明出來的那條是「留著不刪」,而它的代價是重複檔案 ——
兩個測試檔測同一個實作,下一個人不知道該改哪個。

## 候選方向(未裁決)

1. **檔案工具補一個刪除入口**,受 R1–R6 管(與 Write/Edit 同一條路徑)。
   最一致,但要動的是 harness 不是本框架。
2. **`BASH_ALLOWED_CMDS` 開一個窄口**:只允許 `git mv` 與 `git rm`(版控內、可復原),
   不允許 `rm`。理由是版控操作**可復原**,而 R7 防的是不可見的寫入。
   風險:白名單思維又回來了 —— 要寫清楚為什麼這次的窄口不會長大。
3. **人覆蓋**(ADR 0009 形狀):agent 準備好指令,人執行刪除/改名。
   最保守,但每次改名都要人插手。

## 怎樣算做完

- 改名與刪除有一條**不繞過 R7** 的路
- `tests/test_install_defaults.py` 與 `tests/test_install.py` 併回一個檔案
- ADR 的 `F-` 改名做得完(見 `docs/agents/adr-numbering.md`)
