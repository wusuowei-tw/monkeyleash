## 一、問題

### 1-1 三態全漏,而且輸出一個字都沒有

`.claude/portable/scanner.py:35`:
```python
DECODINGS = ("utf-8-sig", "utf-8", "cp950", "cp1252", "latin-1")
```
**沒有 utf-16。** `read_text` 依序試,第一個成功就回傳。**解出來的東西夾著 NUL**(`A\x00K\x00I\x00A\x00`),任何要求連續字元的 pattern 都打不到。

> ### 🔴 **修正(刀一實測,推翻本節初稿的一句話)**
>
> 票面初稿寫「前四個編碼全部拋錯,**由 `latin-1` 解出亂碼**」。
> **那句話只對偵察那三個探針成立 —— 因為它們含中文。** 逐編碼實測:
>
> | 內容 | 形態 | **第一個成功的編碼** |
> |---|---|---|
> | 含 CJK | UTF-16 LE / BE / 無 BOM | `latin-1`(第 5 格) |
> | **純 ASCII** | **UTF-16 無 BOM** | **`utf-8-sig`(第 1 格)** |
> | **純 ASCII** | **UTF-16 有 BOM** | **`cp1252`(第 4 格)** |
>
> 理由:純 ASCII 的 UTF-16 位元組**全部都是合法的 UTF-8**(ASCII 與 NUL 都是),
> 所以階梯第一格就成功;帶 BOM 的 `FF FE` 不是合法 UTF-8,但**是合法 cp1252**。
>
> **為什麼這件事要緊到得改設計**:真實世界的 `.env` 幾乎都是純 ASCII
> (`GOOGLE_API_KEY=...`),也就是**最可能發生的那個案例,失效點在階梯的第一格,
> 根本走不到 `latin-1`**。
> ⇒ **NUL 判定不能只當成 `latin-1` 的後備,它必須在 `DECODINGS` 迴圈之前(或與之並行)。**
>
> **偵察那一輪為什麼沒抓到**:三個探針的內容都含中文(為了讓輸出好讀),
> 於是三個都掉到 `latin-1`,**看起來像一條單一路徑**。
> **樣本的一個共同屬性,被讀成了機制的性質**(`F-108` 併記那條「這次沒丟 ≠ 這個方法不會丟」的同款)。

偵察實測(組裝樣本:AWS access key ID 那條,`AKIA` 開頭 + 16 個大寫字元):

| 探針 | `read_text` 成功的編碼 | 解出的文字裡還有樣本嗎 | `leak_scan` exit |
|---|---|---|---|
| UTF-8 基準 | `utf-8-sig` | **True** | **1(擋下)** |
| UTF-16 LE + BOM | **`latin-1`** | False | **0** |
| UTF-16 BE + BOM | **`latin-1`** | False | **0** |
| UTF-16 LE 無 BOM | **`latin-1`** | False | **0** |

**三個 UTF-16 檔的輸出是空的** —— 不是「印了什麼但放行」,是一個字都沒有。從 pre-commit 的角度看,它們與一個真正乾淨的檔**在畫面上完全相同**。

### 1-2 根因:兩段各自正確的程式,組合起來把 fail-closed 消掉了

`scanner.py:150-166` 的結尾:
```python
    for enc in DECODINGS:
        try:
            return raw.decode(enc), None
        except (UnicodeDecodeError, LookupError):
            continue
    return None, "任何已知編碼都解不開"
```
docstring 寫著「回 `(text, None)` 或 `(None, 理由)` —— **理由非空即 fail-closed**」。

**枚舉實測:`latin-1` 對全部 256 個位元組值都成功。**

> ### ⇒ **`return None, "任何已知編碼都解不開"` 是死碼,從來沒有被執行過。**

兩段程式各自都對:保底編碼是為了不讓 cp950 環境的檔案讀不動;fail-closed 出口是為了不讓讀不動被當成乾淨。**是它們的組合把後者消掉的** —— 而消掉的那一刻沒有任何測試會抱怨,因為**沒有測試碰過這個階梯**(見一之三)。

### 1-3 現有測試零涵蓋

```
$ grep -n "utf-16|utf16|DECODINGS|BOM|\xff\xfe" tests/test_scanner.py tests/test_leak_scan.py
tests/test_leak_scan.py:283:        """PowerShell 的 `Set-Content -Encoding utf8` 寫的是**帶 BOM** 的 UTF-8。
tests/test_leak_scan.py:285:        用 `utf-8` 讀的話 BOM 會變成第一條 pattern 的一部分,那條 pattern
```
兩行講的都是**pattern 檔自己**的編碼,與被掃檔案無關。`tests/test_scanner.py` 零命中;全庫 `.py` 搜 `utf-16` / `utf16` **零命中**。

### 1-4 🔴 更嚴重的一格:公開審查模式也放行,而且主動宣告「沒漏掉」

把同一份 UTF-16 內容存成**白名單副檔名**的 `.md`:

```
=== utf16 .md (白名單副檔名) ===
[審查模式] 未內容掃描 的檔案(0):
  (無)
exit=0
```

審查模式的存在理由逐字寫在 `leak_scan.py` 的註解裡:「清單不在,『跳過』這件事就不存在於報告上,於是等同沒發生 —— 而那正是『沒掃』被讀成『掃過沒事』的那一步。」

**而這一次清單在、而且是空的:報告主動宣告「未內容掃描的檔案(0):(無)」。**
一個為了不讓人誤讀而設計的欄位,替一個沒被真正讀過的檔案作了保。

> **順帶登記:這一格是 `F-155` 同族。**
> F-155 的結論句逐字:「**『有 0 / 無 0』與『一張票都沒有』逐字相同。分辨它們的不是數字,是那一行印出來的【來源】。**」
> 本例是同一個形狀換一個位置:「**跳過 0 個檔**」與「**掃過但其實沒讀懂**」印出來一模一樣,
> 而審查模式的那個 `0` 是**由「有沒有被放進 not_scanned」決定的,不是由「有沒有真的讀懂」決定的**。
> ⇒ **這個 `0` 回答的不是它欄名問的那個問題。**(是否另發 F- 號在刀四判。)

## 三、裁決(2026-09-05,逐字)

```
裁決:A(BOM 嗅探 → utf-16)+ B(無 BOM 時以 NUL 佔比判定,改試 utf-16-le/be)
+ C(皆不可讀 → not_scanned,fail-closed;latin-1 解出的結果必須過可讀性檢查,

**三者的關係(偵察回報第 5 節已記,這裡再釘一次)**:**C 是方向,A/B 是判準。** C 單獨無法實作 —— 它必須先有一個「什麼叫解不出可讀文字」的定義。**A 單獨上線是最危險的組合**:修好三態中的兩態,而剩下那一態的失效方式與原本**完全相同**(靜默 exit 0),於是下一個人不會知道還有一態沒守。

## 四、NUL 佔比門檻 —— 量測後的值,附來源

**先量再訂,不推。** 實測(三種內容 × 編碼):

| 內容 | utf-8 | utf-16-le | utf-16-be | utf-16-le + BOM |
|---|---|---|---|---|
| 純 ASCII | 0.0% | **50.0%** | 50.0% | 49.5% |
| 純 CJK(中文為主) | 0.0% | **28.3%** | 28.3% | 28.0% |
| ASCII + CJK 混合 | 0.0% | 39.3% | 39.3% | 39.1% |
| **全 CJK(無半形,只有換行)** | 0.0% | **4.3%** | —— | —— |

**下界是 4.3%,不是 28%。** CJK 在 UTF-16 裡兩個位元組都非零,所以**中文越多、NUL 佔比越低**;極端情形只有換行符貢獻 NUL。

> ### 🔴 **所以「訂一個夠高的門檻以避免誤判」這條路是走不通的** ——
> 任何高到能避開雜訊的門檻(比方 30%)都會**漏掉純中文的 UTF-16 檔**,
> 而那正是本 repo 與下游最可能出現的內容形態。

**誤判面(整棵樹實測)**:
```
追蹤中且讀得到的檔:252 個
含至少一個 NUL 位元組的:0 個
```

### 門檻的決定

> **觸發門檻 = 「含至少一個 NUL 位元組」(佔比 > 0)。**
> **來源**:UTF-16 內容的實測佔比範圍 **4.3% – 50.0%**(全 CJK 至純 ASCII),
> 而 252 個追蹤檔含 NUL 者 **0 個**(2026-09-05,`d2a1c67`)。

**為什麼敢用這麼鬆的觸發**:它**只決定「要不要試著用 utf-16 解一次」**,不決定結果。
真正把關的是 C 的**可讀性檢查** —— 試出來的東西不可讀就不採用。
⇒ **鬆的觸發成本是一次多餘的 decode,緊的觸發成本是漏掉一整類檔案。** 兩者不對稱。

⚠ **這個門檻的基準是「這一棵樹」,不是「這個方法」。** 下游 repo 若有真正的二進位文字混合檔,誤觸率會不同 —— 但誤觸只會多跑一次 decode,不會誤擋(誤擋由可讀性關決定)。**這句話要跟門檻一起走**(`F-109`)。

### 反控為什麼是必要的(不是湊數)

改 `read_text` 動到的是**每一支掃描器的每一個檔案**。往「更會判成 UTF-16」的方向走一步,
代價就是**中文 cp950 檔被誤判成 UTF-16 而解成亂碼** —— 那會讓現有的偵測**變少**,
而**變少的方向沒有任何既有測試會抱怨**(與 `scanner.py:608` 那條正規化反控同一個判準)。
