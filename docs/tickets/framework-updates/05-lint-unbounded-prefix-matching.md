# 05 — lint:路徑比對沒有邊界處理就告警

## 由來

「許可前綴不能替後面那段背書」這條判準,**在一天之內出現五次**:

| # | 位置 | 形狀 |
|---|---|---|
| 1 | R7 的 `BASH_ALLOWED_CMDS` | `git status && rm -rf x` 因為開頭是 git 就整條放行 |
| 2 | `.gitignore` 的 `skills/` | 沒有前導斜線 → 任何深度比對 → 正典被排除 |
| 3 | G1 的 `_SCRATCH_MARKERS` | `in` 比對且未解 `..` → traversal 命中片段 → 豁免 |
| 4 | G1 的 `_SCRATCH_PREFIXES` | `startswith("/tmp")` → `/tmpdata` 落進豁免 |
| 5 | G1 的 `ABS_PATH` | 邊界符放在**擷取**處 → 砍長度 → 整條路徑看不見 → 放行 |

每一次寫的人都是「剛處理過上一次」的狀態。**記性顯然不是機制。**

## 為什麼不是「進 code-review 檢查項」

那還是一張**要人記得看**的紙,與記性差不多可靠。
檢查項清單愈長,每一項被實際檢查的機率愈低 —— 而這條的特徵是
「當下看起來完全合理」,所以它不會在人工審查裡跳出來。

## 要立成什麼

一條 **lint**:

> 路徑變數(名稱含 `path` / `dir` / `file` / `prefix`,或值是字串常數且含 `/`)
> 用 `startswith(` 或 `in` 比對,而**沒有邊界處理** → 告警。
>
> 邊界處理指:比對式子裡出現分隔符(`+ "/"`、`"/" in`)、
> 呼叫了正規化(`normpath` / `realpath`)、或用了 `==` 精確比對。

**warn 不 block。** 誤報一定會有(有些子字串比對是對的),
而擋住開發不是這條規則的價值 —— 它的價值是**在寫的當下問一句**,
那一句就足以避免上面五次的其中四次。

## 一個要一起想的問題

第 5 次那個變體 lint **抓不到**:那是「邊界放對了但放在錯的位置」。
`(?![\w.\-])` 本身就是邊界處理,只是它出現在**擷取**而不是**放行判定**。

補充判準(靠人,lint 涵蓋不到):
**邊界要放在「決定放不放行」的那一步,不是「決定看不看得到」的那一步。**
前者的錯誤是誤擋(吵鬧),後者的錯誤是漏擋(靜默)。

## 怎樣算做完

- lint 跑在這個 repo 上,對上面五個位置**修好之前的版本**各告警一次
  (要拿舊版實際跑,不是憑記憶列)
- 對修好之後的版本不告警
- 誤報率可接受 —— 用這個 repo 的全部程式碼當語料量一次,把誤報逐條列出來看
