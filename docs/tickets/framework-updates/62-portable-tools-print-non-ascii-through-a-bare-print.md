## 為什麼這比「輸出變亂碼」嚴重

`F-059` 那次的症狀是**亂碼**(訊息讀不懂,但程式跑完)。
本票的症狀是 **`UnicodeEncodeError` 未捕捉 → 行程死掉**。

被打斷的三支工具各自的職責:

| 檔 | 它是什麼 | 崩掉的後果 |
|---|---|---|
| `verify_gates.py` | 淨室驗證 —— 唯一涵蓋「安裝後形態」的東西 | **本機從來沒看過任何一條 R1–R8 的擋下結果**(斷點在逐條實測**之前**,票 54 已於 2026-08-19 更正) |

| `shadow_review.py` | 影子模式的晉升判定 | 判定看不到 |

**三支全是「證明別的東西是對的」那一類工具。** 它們壞掉時,壞的不是功能,
是**證據的產生能力** —— 而那種壞法不會讓任何測試變紅。

## 已知的出口,以及它為什麼不算修好

`python -X utf8 <工具>` 跑得完(票 54 落差表第 24 行已載)。

**但那是使用者每次要記得加的東西,不是機制:**

- 沒有任何文件把它寫進**可執行的位置**(不在 `bootstrap.sh`、不在 CI、不在工具自己的 usage)
- **忘記加的後果不是「少了什麼」,是一個看起來像環境壞掉的 traceback**
- CI 是 Linux UTF-8,**所以永遠不會有東西提醒任何人這件事**

## 偵察題(動工前先答,全部唯讀)

1. **它以前在本機成功跑完過嗎?怎麼跑的?**
   —— 已知有 `-X utf8` 這條路(票 54:24)。要查的是**有沒有人真的走過它**:
   - `.dev/test-runs.jsonl` 有沒有淨室跑完的紀錄?
   - 重導向(`> file`)時 Python 用的是 `locale.getpreferredencoding()` 還是 UTF-8?
     **若重導向會過而主控台會炸,那麼「跑得完」與「跑得完且看得到」是兩件事** ——
     而 CI 的日誌收集正是重導向。
2. **`PYTHONIOENCODING` / `PYTHONUTF8` 有沒有被任何地方設過**(使用者層、`.env`、CI)?
   若有,那它就是一個**沒有寫下來的隱性前提**,而隱性前提會在別人的機器上消失。
3. **另外兩支(`g1_verify` / `shadow_review`)有沒有人在本機跑過?**
   `g1_verify` 特別要緊:ADR 0009 說改 G1 要跑完它的全套驗收 ——
   **若它在本機從來沒跑完過,那條「唯一合法途徑」是不是從來沒有被走完過?**
4. **修法選哪一種**(三選一,不是二選一):

   | | 做法 | 代價 |
   |---|---|---|
   | (a) | 三支統一改走 `sys.stdout.buffer.write(...encode("utf-8"))`,與 `sync.py` / `ledger_verify.py` 一致 | 改動散在 7 行;`verify_gates.py` 是 CI 紅綠燈的一部分(`tests.yml:86-87`),動它要一併確認 CI 行為不變 |
   | (b) | 在三支的入口重新包裝 `sys.stdout`(`io.TextIOWrapper(..., encoding="utf-8")`) | 一支只改一處,但**它改的是行程全域狀態**,而這三支會被別的東西 import |
   | (c) | 只把 `✓` / `✗` / `≥` 換成 ASCII | 最小改動,**但它治的是症狀** —— 下一個人寫一個中文訊息就再犯,而中文訊息在這個 repo 是常態 |

   **(c) 明確不建議**:這個 repo 的訊息本來就大量非 ASCII,把可攜性寄託在
   「以後不要打那幾個字」是**紀律,不是構造**。
5. **測試怎麼寫才不是空的?**
   在 Linux 上 `encoding="utf-8"` 恆成立,所以一條「跑得完」的測試在 CI 上**恆綠** ——
   **那正是票 58 判準說的「一個從來不會紅的綠燈是空的」。**
   要它非空,測試必須**自己造出 cp950 的輸出情境**
   (例如把輸出導進一個 `encoding="cp950"` 的緩衝,斷言不丟例外),
   而不是依賴執行環境的主控台。
