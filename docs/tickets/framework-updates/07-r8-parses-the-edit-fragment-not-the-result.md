# 07 — R8 對 Edit 只解析「片段」,fail-closed 把所有片段編輯報成 import 違規

**優先度:sync session 第一件**(2026-08-12 升級)

升級的理由**不是**「很煩」。是它已經從**稅**變成**扭曲產出**:

台股專案票 04 的 review 修復期間,為了讓片段成為「獨立合法的 Python」,
我兩次加出了沒必要的函式(`_resolve_status`、`_cost_for`)—— 兩次都在
下一步自己抓回來刪掉。那不是風格問題:**規則正在改變程式的結構**,
而改出來的結構比原本差(為配合工具而生的間接層,沒有領域上的理由)。

同一輪還留下一個**沒接上的接線**(`cost_for_channel`),因為那一行在
迴圈中間、怎麼錨都錨不到 column 0,而整檔改寫的漂移風險當下更高。
那條缺口現在掛著 xfail(strict)與一條真紅的突變檢查等它。

這是 F-049 那條路的**前段**:先誘發變形,最後被整條關掉。
F-046 目前還在「使用者繞得過去、所以忍」的階段,而每一次繞過都在
累積「這條規則讓我做不了對的事」的證據 —— 那正是關掉它的理由被攢出來的方式。

## 由來

台股分析師專案票 04 實作中**連續撞六次**(2026-08-12)。對既有 `.py` 做局部 Edit,
只要 `new_string` 不是「獨立合法的 Python」就被擋,訊息是:

```
[R8] analyst_tracker/store.py:生產程式碼不得 import research/。
```

被擋的片段裡沒有 import 任何東西。兩種實際形狀:

| # | 片段 | 真正的解析錯誤 |
|---|---|---|
| 1 | 結尾是 anchor 行 `def put_backup_status(...):`(缺 body) | `SyntaxError` |
| 2 | 開頭是縮排的 `    return _ins(...)` | `IndentationError` |

**函式內部的每一行都是縮排的**,所以「改一個函式裡的一行」在 `.py` 上幾乎必然觸發。
六次全部只能改用整檔 `Write` 才寫得進去。

## 根因

`gate.py`(約 1049 行):

```
content = ti.get("content") or ti.get("new_string") or ""
```

Edit 取的是 `new_string` —— **片段,不是套用編輯後的結果內容**。
而 `imports_research()` 用 AST 且 fail-closed:

```
try:
    tree = ast.parse(content or "")
except Exception:
    return True
```

兩者相乘,得到的判定是:**「片段不是合法 Python」⇒「它 import 了 research」**。

## 這一則的形狀

**fail-closed 只保證失敗的方向,不保證問對了問題。**

這是 F-045(一個時點 fail-closed、另一個時點 fail-open)的鏡像:那則講的是
兩個時點的方向不一致;這則講的是**同一個時點、方向對了,但判定的對象是錯的**。
R8 要守的是「**檔案最終內容**有沒有 import research」,而它拿到的是一段片段;
片段的語法完整性跟 R8 要守的東西沒有任何關係。

兩個實際代價:

1. **訊息把人指向錯誤的方向。** 讀到的是 import 違規,現場是括號沒閉合。
   誤導的訊息比沒有訊息貴 —— 它讓人去檢查一個根本沒問題的地方。
2. **繞路壓力指向更危險的做法。** 唯一走得通的出路是整檔 `Write`,而整檔重寫
   比片段編輯更容易誤刪東西。**規則把人推去做風險更高的事。**
   撞到第六次時「乾脆把 R8 關掉」已經是個有吸引力的念頭 —— 稅太高的規則
   最後會被整條關掉,而關掉之後沒有人記得它本來守什麼。

## 修法方向

R8 應該解析**套用編輯後的整檔結果**,不是編輯片段本身:

- **Edit 路徑**:讀磁碟上的現有檔案,套用 `old_string` → `new_string`,對結果解析。
  套不上(anchor 不符或不唯一)時不是 R8 該處理的情況 —— 那次編輯本來就會失敗。
- **Write 路徑**:`content` 本來就是完整檔案內容,維持現狀。
- **fail-closed 保留**:是**結果內容**解析不了才當作可能 import 了。
  那時候「看不懂這段碼」是真的,擋得有道理。

順帶檢查其他消費 `content` 的規則有沒有同一個假設(R1 掃 spec 內容、
R5 比對 SKILL.md)—— 它們是字串比對不是 AST,方向上不受影響,但
「拿到的是片段不是結果」這件事對它們一樣成立,值得一併確認語意。

## 驗收

- [ ] 對既有 `.py` 做縮排片段的 Edit(不含任何 import)→ **不被 R8 擋**
- [ ] 片段結尾是 anchor `def foo():`(缺 body)→ **不被 R8 擋**
- [ ] 編輯後的**結果**含 `import research` → **被擋**(不論片段長什麼樣)
- [ ] 編輯後的結果是語法壞掉的檔案 → **被擋**(fail-closed 仍在)
- [ ] Write 整檔含 `import research` → 照舊被擋(不得回歸)
- [ ] `research/` 底下的檔案 import 生產資料層 → 照舊放行(方向性不變)
- [ ] `import research_utils` 仍不算違規(F-051 的邊界不得回歸)

## 追加範圍(2026-08-12):兩支掃描器合一時,**「讀不動」必須 fail-closed**

原本這張票的範圍寫成「共骨架合一」。合一之前要先確定合進去的是哪一版行為 ——
因為**兩支現在的失效方向不一樣**:

| | `cookie_ban.py`(下游專案) | `.claude/portable/leak_scan.py`(框架) |
|---|---|---|
| 讀不動的檔案 | **fail-closed**:換編碼重試,連位元組都讀不到即違規 | `except Exception: continue` —— **靜默跳過** |
| 命中內容 | 已遮罩 | 已遮罩(F-067) |
| self-skip | repo 相對路徑 | 基本檔名 |

`leak_scan` 那條的實際後果:cp950 編碼的 `.ps1` / `.bat` / `.py` 裡寫著金鑰,
`utf-8` 解碼丟 `UnicodeDecodeError`,**整個檔案靜默跳過**。在 zh-TW 的 Windows 上
cp950 是預設編碼,那不是假想情況。

合一時要帶進去的:

- [ ] 讀檔改**依序嘗試多種編碼**(utf-8-sig → utf-8 → cp950 → cp1252 → latin-1);
      latin-1 永不失敗,所以最後一關保證有東西可掃。要找的 pattern 全是 ASCII,
      亂碼不影響它們的可見性。
- [ ] 連位元組都讀不到(權限、路徑壞掉)→ **計為違規**,不是跳過。
      已知的二進位副檔名在 `SKIP_SUFFIX` 就濾掉了,走到這裡還讀不動的是意料外的東西,
      而意料外的東西在掃描器裡一律擋。
- [ ] **正反控測試都要**:cp950 檔案裡的違規要被抓到(正控),
      cp950 的乾淨檔案要放行(反控)—— 少了反控,「全部當成違規」也會讓正控過。
- [ ] self-skip 統一成 repo 相對路徑(基本檔名版本的豁免鑰匙握在要規避的人手上)。

**下游已修、上游未修**,所以現在是分岔狀態:合一時若以 `leak_scan` 為基準,
會把這個洞一起合進去 —— 那正好是 F-058 家族「一個事實兩個來源」再繞一圈。
