## 為什麼是缺口

R3 的契約是「**先跑測試確認它在實作不存在時是紅的**」。
**純註解沒有行為可以先紅** —— 造不出那種紅燈。

於是在現行 R3 之下,**對一個不在凍結清單上的原始碼檔加一行註解,是做不到的**
(除非那一票剛好同時改了行為並留下紅燈)。

**⚠ 證據等級要標清楚**:`sync.py` 那一次是**實撞**;
「對任何非清單檔都如此」是**從 R3 的判定條件推的**,**沒有再撞第二個檔去驗**
(驗它會製造一次無關的擋下紀錄)。動工前若要那個證據,得先裁要不要製造它。

## ⚠ 設計陷阱 —— 出口**不見得**是「偵測純註解」

最直覺的修法是「判斷這次修改是不是純註解,是的話豁免 R3」。**那條路有本 repo 已經裁過的坑:**

> 判斷「這是純註解」**需要解析**(哪些行是註解、docstring 算不算、
> 字串裡的 `#` 算不算、跨行 docstring 的邊界在哪)。
> 而本 repo 對 R7 的裁決逐字寫著:
> **「半套的解析器比零涵蓋更危險 —— 零涵蓋你知道它是零。」**

一個「大致上判得出純註解」的偵測器,判錯的方向是**放行** ——
有人把一行程式藏進看起來像註解的地方,就繞過了 R3。
**那比現在這個「擋住做對事的人」的問題更貴。**

所以本票**不預設修法**。可能的方向(**都要裁,不在立案時定死**):

| 方向 | 做什麼 | 疑慮 |
|---|---|---|
| 甲 | 偵測純註解並豁免 | 上面那個坑。**除非解析是 AST 級的**(`ast.parse` 前後比對可執行碼),而那才可能是零誤判 |
| 乙 | 擴大 `legacy-no-redlight` 的用法 | **清單只減不增**(R6 的設計),方向相反 |
| 丙 | 給「文件性修改」一個顯式的宣告出口(像 `Untested by decision` 那樣寫在票面) | 與既有豁免機制同形、可審計;但**豁免可自助**的老問題要一起解 |
| 丁 | **不修** —— 承認這是 R3 的已知代價,把它寫進 `CLAUDE.md` 讓人不要浪費時間 | 最省。但見下面的家族分析 |

## 家族:規則判錯對象 + `F-031`

**這一則屬於兩個家族的交集:**

**(一)規則判錯對象。** R3 要問的是「這次修改有沒有先紅過」,
而它實際問的是「這個**檔案**有沒有本票的紅燈」——
**對象是檔案,不是修改**。純註解暴露的正是這個差。

**(二)`F-031`:誤擋不修,繞路成本累積,規則終被整條關掉。**
`CLAUDE.md` 逐字:

> 擋的卻是做對事的人,而**那種規則最後會被整條關掉**。

本次的實際處置是**放棄那兩行註解**(票 114 裁決 A)——
也就是說**已經繞過一次了**,方式是「不做那件事」。
**繞路成本每次都很小,而那正是這一族危險的地方**:
沒有任何一次值得抗議,而累積起來會讓人開始覺得 R3 很煩。
