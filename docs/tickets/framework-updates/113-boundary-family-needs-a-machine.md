**邊界族有判準,沒有機制。** 判準寫在 `CLAUDE.md`(「最外圈」那一段),
逐點修在票 76 / 77 / 78 / 111 —— 而**新增一個無邊界的放行比對時,沒有任何東西會紅**。

證據是這個家族還在長:

修過一次不代表那個面被守住了。

## 為什麼是缺口不是設計

`tests/test_gate_boundaries.py` 名字看起來像在守這件事,**而它不是**:
該檔 docstring 自述「三件事的共同根源是 F-042」——它管的是**例外處置與跨行程編碼**。

而**現成的形狀已經存在**:`tests/test_source_hygiene.py` 有兩條**全庫式機器判定**
(閉區間規則範圍、裸票號),兩條都是「掃原始碼、發現新違規就紅」。
**本票要的就是第三條那樣的東西。**

## 設計方向(待裁,不在立案時定死)

**靜態掃描 `gate.py` 的放行判定,配一份已審白名單;新增未登記的 `startswith` / `in` 即紅。**

三個必須先答的問題:

1. **「放行判定」怎麼界定?** 全檔的 `startswith` / `in` 掃下去會撈到大量無關的
   (讀設定檔、切字串、組訊息)。**過寬的掃描會製造噪音,而噪音會讓人把整條關掉**(F-031)。
   候選判準:只掃**回傳布林、且該布林會餵給「要不要放行」**的函式 ——
   而那件事**靜態判不出來**,所以最可能的落點是「**函式白名單 + 該函式內全掃**」。
2. **白名單長什麼樣?** 一行一個 `符號名 + 受害字串 + 為什麼這一處是對的`。
   **理由欄是硬性的** —— 與三份非原始碼清單、`BASH_ALLOWED_*` 同一個規矩
   (`test_every_exception_carries_a_reason` 已經是那個形狀)。
3. **掃描器住哪裡?** `tests/test_source_hygiene.py`(與另外兩條同居)還是新開一支?
   前者的好處是「全庫式機器判定」集中在一個地方,人找得到。

## 刀一(偵察)的題目

> **列出現有放行比對的全清單,帶行號**與符號名。

- **行號是給這一輪用的工作資料**,而**票面與白名單只寫符號名** ——
  行號會漂(票 111 / 112 之後 `gate.py` 的六處行號全漂了,見
  `.dev/reports/2026-09-07T125706Z-arch-b-bucket.md` 的對照表)。
- 清單要**釘一個 commit**:「以 `<sha>` 的 `gate.py` 為底」。
  沒有基準的清單過期之後**看起來像算錯**(F-109)。
- 範圍問清楚:只掃 `gate.py`,還是連 `g1_guard.py` / `scanner.py` / `leak_scan.py` 一起?
  **後三支都有自己的放行/跳過判定**,而 F-086 的標本就是 `scanner.py`。

## 紅燈形狀(一句)

> 把它登記進白名單(附理由)之後轉綠。
